### Rust Edition 2021: The Complete Production Review Guide

> **Edition**: Rust 2021 (`edition = "2021"` in `Cargo.toml`), stabilised with **Rust 1.56.0 (2021-10-21)**.[^1][^6]
> **Compilers**: a 2021 crate may be built by any rustc from **1.56.0** up to the current stable **1.99.1 (2026-10-15)**. Rust 1.99.0 shipped on 2026-10-01; **1.100.0** is in beta and scheduled for 2026-11-12.[^1][^14]
> **Support status (October 2026)**: editions do not expire — every current and future compiler builds 2021 code, and crates of different editions link together freely. Rust has **no LTS releases**: only the latest stable receives point releases and security fixes.[^33] The newest edition is **Rust 2024** (Rust 1.85.0, 2025-02-20); no later edition is stable.[^4][^5]
> **Scope**: language semantics of edition 2021 (versus 2018 and versus 2024), every relevant compiler/std/Cargo change from 1.57 to 1.99, and idioms, pitfalls and review rules for production Rust: ownership, errors, panics, integers, strings, collections, traits, closures, unsafe/FFI, threads, async/Tokio, macros, API/semver, performance, testing, Cargo, Clippy, security, observability.
> **Note**: this document is self-contained. Examples were compiled and run with rustc 1.99.1, 1.85.0 and 1.56.0 (plus the release boundary toolchains named in the text) using `--edition 2021` unless stated otherwise.

***

#### Overview

Rust 2021 is the third edition of Rust. An edition is an opt-in, per-crate set of source-level changes (keywords, prelude contents, method resolution, lint levels, closure capture rules, Cargo defaults). It does **not** select a compiler or a standard library version: a crate with `edition = "2021"` compiled by rustc 1.99.1 has access to everything stabilised up to 1.99 — **except** the handful of features that are gated on edition 2024. Reviewing 2021 code therefore means keeping **two independent axes** in view:

1. **Edition semantics** — what `edition = "2021"` means. The 2021 changes over 2018 (disjoint closure captures, `IntoIterator` for arrays via method-call syntax, `TryFrom`/`TryInto`/`FromIterator` in the prelude, consistent `panic!` formatting, reserved prefixes, `pat` matching `A | B` in `macro_rules!`, Cargo feature resolver `"2"` by default, bare trait objects and `...` range patterns as hard errors) all apply. The 2024 changes (RPIT lifetime capture, `if let` and tail-expression temporary scopes, required `unsafe extern`/`#[unsafe(...)]`, `static mut` reference errors, `!` fallback, let chains, `gen` keyword, `Future` in the prelude, `Box<[T]>` by-value `into_iter()`, resolver `"3"`) **do not** apply, no matter how new the compiler is.
2. **Compiler/std version** — which rustc the crate must support. The minimum supported Rust version (MSRV, `rust-version` in `Cargo.toml`) decides whether `let`-`else` (1.65), `OnceLock` (1.70), `async fn` in traits (1.75), `LazyLock` (1.80), `#[expect]` (1.81), `&raw const` (1.82), trait upcasting (1.86), `if let` guards (1.95) or `assert_matches!` (1.96) are allowed.

Global truths about Rust 2021 code:

- **Ownership is the memory model.** Every value has one owner; it is dropped when the owner goes out of scope. Borrows (`&T`, `&mut T`) are checked at compile time: any number of shared borrows **or** one exclusive borrow.
- **Safe Rust has no undefined behaviour.** Data races, use-after-free, dangling references and out-of-bounds accesses are impossible without `unsafe`. Every `unsafe` block is a proof obligation the reviewer must check.
- **Errors are values.** Recoverable failures are `Result<T, E>`, propagated with `?`. Panics are for bugs, not for expected failures.
- **Integer overflow panics in debug builds and wraps in release builds** (unless `overflow-checks` is set). Neither is a correct result.
- **`&str`/`String` are always valid UTF-8**; byte indexing that splits a character panics.
- **Zero-cost abstractions.** Iterators, closures and generics are monomorphised; `dyn Trait` is the opt-in for dynamic dispatch.
- **No implicit async runtime.** `async fn` produces an inert future; something (usually Tokio) must poll it. Futures do nothing until awaited and are cancelled by being dropped.
- **Editions mix.** A 2021 crate can depend on 2015, 2018 and 2024 crates and vice versa; the edition of each crate governs only that crate's source.

#### Version-Aware Review: Check the MSRV First

Before claiming that an API or syntax is unavailable — or recommending one — determine which compilers the crate must support. Look, in this order, for:

1. `rust-version` in `[package]` or `[workspace.package]` (stabilised in Cargo 1.56).[^7]
2. `rust-toolchain.toml` / `rust-toolchain` (`channel = "1.75.0"` pins an exact toolchain; `channel = "stable"` means "latest").
3. CI configuration (a toolchain matrix with an explicit MSRV job, e.g. `cargo +1.70.0 check`), a `Dockerfile` (`FROM rust:1.80`), or `msrv = "1.70"` in `clippy.toml`.
4. If nothing pins a version, the crate effectively targets recent stable. Do not invent an MSRV; suggest declaring one if the crate is a published library.

Review rules:

- **Say "not available in this crate" only when the declared MSRV proves it.** `LazyLock` in a crate with `rust-version = "1.80"` is fine; in a crate with `rust-version = "1.70"` it is a build break on the MSRV toolchain. Use the table in *Compiler and Standard Library Changes 1.57 → 1.99* below.
- **Edition-gated features are unavailable regardless of compiler version.** Let chains in `if`/`while` are an error in edition 2021 even on 1.99.1 (`error: let chains are only allowed in Rust 2024 or later`). Never suggest them for a 2021 crate.
- **Prefer the newest idiom the MSRV allows.** With MSRV ≥ 1.80, replace `lazy_static!`/`once_cell::sync::Lazy` with `std::sync::LazyLock`; with MSRV ≥ 1.70, `OnceLock`; with MSRV ≥ 1.65, `let`-`else` instead of `match … { _ => return }`.
- **When the MSRV is raised, it is a semver-relevant decision for libraries.** Flag MSRV bumps hidden in a patch release of a widely used library; many ecosystems treat an MSRV increase as requiring at least a minor version bump (Tokio, for example, raises its MSRV only in minor releases and only to versions at least six months old).[^16]

What the toolchain does and does not check:

- Cargo **refuses to build** a package whose `rust-version` is newer than the active compiler (verified with Cargo 1.65 and `rust-version = "1.70"`: "package `a v0.1.0 (…)` cannot be built because it requires rustc 1.70 or newer, while the currently active rustc version is 1.65.0"). `--ignore-rust-version` overrides it.[^7]
- A **new** compiler does **not** warn when code uses something newer than `rust-version`. Clippy's `incompatible_msrv` lint (warn-by-default) reads `rust-version` and flags **standard-library items** that were stabilised later (verified on Clippy 0.1.99: `LazyLock` with MSRV 1.70 → "this item is stable since `1.80.0`"), but it does **not** flag **language syntax**: `let`-`else` (1.65) and inline format arguments `{name}` (1.58) in a crate with `rust-version = "1.60"` produce no warning from rustc or Clippy on 1.99.1. Only a CI job that builds with the MSRV toolchain proves MSRV compliance.
- `Cargo.lock` format: Cargo ≥ 1.83 writes **lockfile version 4** unless `rust-version` is below 1.83 (verified: `rust-version = "1.82"` → `version = 3`, `"1.83"` or unset → `version = 4`). Cargo older than 1.78 cannot read v4 ("lock file version `4` was found, but this version of Cargo does not understand this lock file"). A committed v4 lockfile in a crate whose CI tests an older MSRV breaks that job.
- Manifest syntax also has versions: `dep:` and `?` in `[features]` need Cargo 1.60 (Cargo 1.56 rejects `dep:` with "namespaced features with the `dep:` prefix are only allowed on the nightly channel"); `workspace = true` inheritance needs 1.64 (Cargo 1.56 fails to parse it); the `[lints]` table needs 1.74 — **older Cargo only prints `unused manifest key: lints` and silently ignores it**, so `unsafe_code = "forbid"` is not enforced on an MSRV toolchain below 1.74.[^9][^10][^11]
- Dependency resolution is not MSRV-aware by default in edition 2021: `cargo update` happily selects a dependency whose own `rust-version` is above yours (Tokio 1.54.1, released 2026-10-21, requires Rust 1.85).[^16] (`cargo add` alone has picked MSRV-compatible version requirements since 1.79.) Since Cargo 1.84, opt in with `resolver = "3"` (allowed in a 2021 crate) or `[resolver] incompatible-rust-versions = "fallback"` in `.cargo/config.toml`.[^8][^37]

Security floor: Rust 1.56.1 fixed CVE-2021-42574 (bidirectional-override "Trojan Source" characters) by adding deny-by-default lints; 1.58.1 fixed the `std::fs::remove_dir_all` race CVE-2022-21658; 1.77.2 and 1.81.0 fixed Windows batch-file argument injection in `std::process::Command` (CVE-2024-24576, CVE-2024-43402).[^1][^23][^24] An MSRV below these is acceptable for *supporting* old compilers, but production binaries should be built with a current stable.

#### What Edition 2021 Changes Compared with 2018

Each item below was compiled on the **same** compiler (1.56.0, and again on 1.99.1) with `--edition 2018` and `--edition 2021`.[^2][^3]

##### 1. Disjoint capture in closures ★★★

Closures capture the **individual fields (places)** they use, not whole variables.

```rust
struct S { a: String, b: String }

fn main() {
    let mut s = S { a: "a".into(), b: "b".into() };
    let c = || println!("{}", s.a); // 2021: captures only `s.a` (by reference)
    s.b.push('!');                  // 2018: E0502, `s` is borrowed by the closure
    c();
    println!("{}", s.b);
}
```

Consequences a reviewer must know:

- **Drop timing changes for `move` closures.** A `move` closure that uses only `p.x` moves only `p.x`; `p.y` stays with `p` and is dropped at the end of the enclosing scope, not when the closure is dropped. In 2018 the program below does not even compile (`p` moved); in 2021 it prints `drop x`, `closure dropped`, `end of main`, `drop y`.

```rust
struct D(&'static str);
impl Drop for D { fn drop(&mut self) { println!("drop {}", self.0); } }
struct P { x: D, y: D }

fn main() {
    let p = P { x: D("x"), y: D("y") };
    {
        let c = move || { let _ = &p.x; };
        drop(c);                    // drops the captured `p.x` only
        println!("closure dropped");
    }
    println!("end of main");
    let _ = &p.y;                   // `p.y` is still owned by `p`
}
```

- **Auto traits follow the captured places.** A `move` closure that uses only `m.name` of a struct that also holds an `Rc` is `Send` in 2021 (2018: E0277, `Rc<u32>` cannot be sent). Conversely, a `Send` newtype around a raw pointer is **bypassed**: the closure captures the inner `*mut T` field, which is not `Send`.

```rust
use std::thread;

struct Ptr(*mut i32);
unsafe impl Send for Ptr {}

fn main() {
    let mut x = 5;
    let px = Ptr(&mut x as *mut i32);
    // 2018: compiles. 2021: E0277 "`*mut i32` cannot be sent between threads safely",
    // because only `px.0` is captured.
    // let h = thread::spawn(move || unsafe { *(px.0) += 10; });
    let h = thread::spawn(move || {
        let px = px;                 // GOOD: capture the whole wrapper
        unsafe { *(px.0) += 10; }
    });
    h.join().unwrap();
    // (`x` is accessed through the pointer only; reading `x` while the
    // thread runs would be a data race.)
}
```

- Code that relied on capturing a whole guard or handle (to keep it alive inside a closure) may now capture only a field and release the rest early. `cargo fix --edition` inserts `let _ = &x;` to force whole-variable capture where drop order or auto traits would change (lint `rust_2021_incompatible_closure_captures`); many of these dummy lets can be removed after review. `let _ = x;` (without `&`) captures nothing.[^2]

##### 2. `IntoIterator` for arrays via method-call syntax ★★

`[T; N]` implements `IntoIterator` by value in every edition (since 1.53), so `for x in [1, 2]` yields `i32` everywhere. The edition changes only the **method call** `array.into_iter()`: in 2015/2018 it still resolves to `<&[T; N]>::into_iter` (yielding `&T`, with lint `array_into_iter`); in 2021 it yields `T`.

```rust
fn main() {
    let a = [1, 2, 3];
    for x in a.into_iter() {
        let y: i32 = x; // 2021: `x: i32`. 2018: `x: &i32` → E0308 mismatched types
        println!("{}", y);
    }
}
```

Review: in 2021 code, `arr.into_iter()` consumes (copies) the array. Code ported from 2018 that relied on `&T` items must use `.iter()`. The same trick is used for `Box<[T]>` in edition 2024 — **not** in 2021 (see below).

##### 3. Prelude additions: `TryFrom`, `TryInto`, `FromIterator` ★★

```rust
fn main() {
    let x: u8 = 300i32.try_into().unwrap_or(255);   // 2018: E0599 without `use std::convert::TryInto`
    let overflow = u16::try_from(70000u32).is_err(); // 2018: E0599
    let v = Vec::<i32>::from_iter(1..4);             // 2018: E0599
    println!("{} {} {:?}", x, overflow, v);
}
```

Explicit `use std::convert::TryFrom;` lines are now redundant (harmless). A crate-local trait with a method named `try_into`/`try_from`/`from_iter` can become ambiguous with the prelude trait; the migration lint `rust_2021_prelude_collisions` catches it.[^2]

##### 4. `panic!` formatting consistency ★★

In 2021, `panic!`, `assert!` and friends always treat the first argument as a format string.

```rust
fn main() {
    // BAD: `panic!("{}")` — 2018: compiles (warning) and panics with the literal message "{}";
    //      2021: compile error "1 positional argument in format string, but no arguments were given".
    // GOOD in every edition:
    let r = std::panic::catch_unwind(|| panic!("{}", "{}"));
    println!("{:?}", r.is_err());
    // Non-string payload (2021 rejects `panic!(42)`):
    let r = std::panic::catch_unwind(|| std::panic::panic_any(42));
    println!("{:?}", r.unwrap_err().downcast_ref::<i32>()); // Some(42)
}
```

- `panic!(123)` / `panic!(some_string)` / `assert!(cond, msg_string)` are errors in 2021 ("format argument must be a string literal"). Use `panic!("{}", msg)`, or `std::panic::panic_any(value)` to panic with a non-string payload.
- `panic!("{x}")` uses inline format-argument capture (Rust 1.58+), it is no longer a literal message.

##### 5. Reserved prefixes ★

`ident#…`, `ident"…"` and `ident'…'` are reserved tokens. `z"hey"` inside a macro invocation tokenised as `z "hey"` in 2018 and is an error in 2021 ("prefix `z` is unknown"). Insert whitespace (`z "hey"`) in macro inputs. The reservation is what later enabled `c"…"` C-string literals (Rust 1.77; an error in edition 2018 even on 1.99.1) and raw lifetimes `'r#ident` (1.83; also 2021+ only).

##### 6. Or-patterns in `macro_rules!` ★

`$p:pat` now matches top-level or-patterns, so `m!(1 | 2)` works with `($p:pat) => …` (2018: "no rules expected the token `|`"). A macro that wrote `$a:pat | $b:pat` must switch to `$a:pat_param | $b:pat_param` (the `pat_param` fragment, which excludes top-level `|`) or it becomes ambiguous.

```rust
macro_rules! is_small { ($p:pat) => { |x: u8| matches!(x, $p) } }

fn main() {
    let f = is_small!(1 | 2);
    println!("{}", f(2)); // true
}
```

##### 7. Warnings promoted to errors ★★

- **Bare trait objects**: `fn f(_: &Trait)` is a hard error (E0782) — write `&dyn Trait`.
- **`...` range patterns**: `0...9 =>` is a hard error (E0783) — write `0..=9`.

##### 8. Cargo feature resolver `"2"` by default ★★★

A package with `edition = "2021"` uses resolver `"2"`: features enabled on a dependency only for build-dependencies or proc-macros are not unified with normal dependencies, target-specific dependencies for other platforms do not activate features, and dev-dependency features are not unified into normal builds unless a dev target is being built.[^8]

**Pitfall — virtual workspaces.** A workspace root without `[package]` does **not** inherit the edition of its members. Verified on Cargo 1.99.1:

```text
warning: virtual workspace defaulting to `resolver = "1"` despite one or more workspace members
being on edition 2021 which implies `resolver = "2"`
```

Every virtual workspace must state `resolver = "2"` (or `"3"`) under `[workspace]`. The resolver is a workspace-wide setting: a missing line silently selects resolver `"1"` for every member, so build-dependency, target-specific and dev-dependency features are unified again despite the members being on edition 2021.

#### What Edition 2021 Does NOT Get (Edition 2024 Semantics)

Rust 2024 (1.85.0) changed the following. **None of it applies to a 2021 crate on any compiler.** Each row was verified on rustc 1.99.1 with `--edition 2021` vs `--edition 2024`.[^4][^5]

| 2024 change | Behaviour in a 2021 crate (what the reviewer must assume) |
|---|---|
| RPIT captures all in-scope lifetimes | `fn f(s: &str) -> impl Iterator<Item = usize>` returning something borrowing `s` is **E0700** ("hidden type … captures lifetime that does not appear in bounds"); write `+ '_`/`+ 'a`, or `+ use<'a>` (1.82+). |
| `if let` scrutinee temporaries dropped before `else` | Temporaries (e.g. a `MutexGuard`) in the `if let` scrutinee live through the **`else` block** — locking again in `else` deadlocks. |
| Tail-expression temporaries dropped before locals | `c.borrow().len()` as the last expression of a block whose local `c` is a `RefCell` is **E0597** ("`c` does not live long enough"). |
| Let chains (`if let A = a && cond`) — 1.88, 2024-only | **Error**: "let chains are only allowed in Rust 2024 or later". Exception: inside an `if let` **match guard** (1.95+), `&&` chains also compile in 2021. |
| `extern` blocks must be `unsafe extern` | Plain `extern "C" { … }` compiles. `unsafe extern` with `safe fn` items is **also accepted since 1.82**. |
| `#[no_mangle]`, `#[export_name]`, `#[link_section]` must be `#[unsafe(...)]` | Plain form compiles. `#[unsafe(no_mangle)]` is accepted since 1.82. |
| `static_mut_refs` is deny-by-default | `&STATIC_MUT` is only a **warning** ("creating a shared reference to mutable static") — still UB-prone; treat as an error. |
| `std::env::set_var`/`remove_var` are `unsafe` | Callable without `unsafe`, and an `unsafe {}` around them produces no warning on 1.85+ (1.56 warns "unnecessary `unsafe` block"). The data race with concurrent `getenv` exists in every edition. |
| `unsafe_op_in_unsafe_fn` warns | The body of an `unsafe fn` is implicitly an `unsafe` block; the lint is allow-by-default. |
| Never type fallback to `!` | Fallback is to `()`. Code relying on it gets `dependency_on_unit_never_type_fallback`: a warning on 1.85, **deny-by-default (error) since 1.92**. |
| `gen` is a reserved keyword | `let gen = 5;` is fine in 2021 (an error in 2024). |
| `#"…"#` / `##` guarded strings reserved | Tokenises as before in 2021. |
| `Future`/`IntoFuture` in the prelude | Must be imported: `use std::future::Future;` (E0405 otherwise). |
| `Box<[T]>::into_iter()` yields `T` | Method call yields `&T` (lint `boxed_slice_into_iter`); `for x in boxed_slice` (no method call) yields `T` since 1.80. |
| `expr` fragment matches `const {}` and `_` | `$e:expr` keeps the 2021 behaviour (`expr_2021`). |
| Match ergonomics reservations | `mut`/`ref`/`&` under a by-reference default binding mode remain legal in 2021 with 2021 semantics: `let [mut x] = &[1i32];` makes `x` an owned, mutable `i32` (an error in 2024). |
| Cargo resolver `"3"` (MSRV-aware) default | Default resolver is `"2"`; `"3"` can be opted into (Cargo 1.84+). |
| Cargo 1.99: members may override inherited `default-features` | On edition 2021, `default-features = false` next to `workspace = true` is **ignored with a warning**.[^1] |
| Rustfmt style edition 2024, doctest merging, `include!` changes | Not applied. |

##### `if let` scrutinee temporaries (2021 behaviour)

```rust
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(None::<i32>);
    if let Some(v) = *m.lock().unwrap() {
        println!("got {}", v);
    } else {
        // 2021: the guard from the scrutinee is still alive here → prints `false`;
        // a blocking `m.lock()` here would deadlock. 2024 prints `true`.
        println!("else: try_lock ok = {}", m.try_lock().is_ok());
    };
}
```

In **both** editions the guard is alive inside the `then` branch, and in both editions the temporaries in a **`match` scrutinee** live until the end of the whole `match` (2024 did not change `match`). Hoist the value out first:

```rust
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(vec![1]);
    // BAD (every edition): the guard lives for the entire match
    match m.lock().unwrap().first() {
        Some(_) => println!("arm: try_lock ok = {}", m.try_lock().is_ok()), // false
        None => {}
    };
    // GOOD: the guard is dropped at the end of this statement
    let first = m.lock().unwrap().first().copied();
    match first {
        Some(_) => println!("hoisted: try_lock ok = {}", m.try_lock().is_ok()), // true
        None => {}
    };
}
```

##### Tail-expression temporaries (2021 behaviour)

```rust
use std::cell::RefCell;

fn len() -> usize {
    let c = RefCell::new(vec![1, 2, 3]);
    // BAD in 2021: E0597 — the `Ref` temporary outlives `c`
    // c.borrow().len()
    let n = c.borrow().len(); // GOOD: bind first
    n
}

fn main() { println!("{}", len()); }
```

##### RPIT lifetime capture (2021 behaviour)

```rust
// BAD in 2021 (E0700): the iterator borrows `s` but the return type does not say so
// fn word_lens(s: &str) -> impl Iterator<Item = usize> { s.split(' ').map(|w| w.len()) }

// GOOD on every compiler since 1.56:
fn word_lens<'a>(s: &'a str) -> impl Iterator<Item = usize> + 'a {
    s.split(' ').map(|w| w.len())
}

// GOOD with MSRV >= 1.82 (precise capturing), closest to the 2024 meaning:
fn word_lens2<'a>(s: &'a str) -> impl Iterator<Item = usize> + use<'a> {
    s.split(' ').map(|w| w.len())
}

fn main() {
    println!("{:?}", word_lens("a bb").collect::<Vec<_>>());
    println!("{:?}", word_lens2("a bb ccc").collect::<Vec<_>>());
}
```

In 2021, return-position `impl Trait` in a **free function or inherent method** captures all type parameters but only the lifetimes that are named in its bounds. Return-position `impl Trait` **in traits** (1.75+) and `async fn` always capture all lifetimes in every edition.[^27][^28] `+ 'a` and `use<'a>` are not identical: `+ 'a` additionally asserts that the hidden type outlives `'a`, which over-constrains when several lifetimes are involved; with MSRV ≥ 1.82 prefer `use<..>`.

##### Never-type fallback (2021 behaviour)

```rust
fn f<T: Default>() -> Result<T, ()> { Ok(T::default()) }

fn main() -> Result<(), ()> {
    let _: () = f()?; // GOOD: state the type explicitly
    // f()?;          // BAD: `T` is inferred only through never-type fallback to `()`.
    //                // rustc 1.85: warning; rustc >= 1.92: error
    //                // (dependency_on_unit_never_type_fallback, deny-by-default).
    Ok(())
}
```

Review: a 2021 crate that compiled warning-free on an old compiler may fail on ≥ 1.92 for this reason; the fix is an explicit type annotation, which is also correct for 2024.

#### Compiler and Standard Library Changes 1.57 → 1.99

A 2021 crate gets every item below **if and only if its MSRV is at least the listed version**. Every language and library entry was compiled with `--edition 2021` on rustc 1.N.0 (compiles) and on 1.(N−1).0 (fails), except behavioural changes (the `mpsc` rewrite, debug precondition checks, sort algorithms, `extern "C"` abort), naked functions, `use<..>` in traits and C-variadic definitions; those, and the Cargo and lint entries, are taken from the release notes.[^1] Release dates are those of the `.0` release.

| 1.58 (2022-01-13) | inline format args `println!("{name}")`, `{x:>w$}` | `Option::unwrap_unchecked` | |
| 1.59 (2022-02-24) | destructuring assignment `(a, b) = (b, a)`; `asm!`; const-generic defaults | `thread::available_parallelism` | profile `strip` |
| 1.60 (2022-04-07) | | `abs_diff` | `dep:` / `pkg?/feat` feature syntax; `--timings` |
| 1.61 (2022-05-19) | | `process::ExitCode`, `Termination`; `Vec::retain_mut` | |
| 1.62 (2022-06-30) | `#[derive(Default)]` on enums with `#[default]` | `bool::then_some`, `f32/f64::total_cmp` | `cargo add` |
| 1.63 (2022-08-11) | | `thread::scope`; `array::from_fn`; `const` `Mutex::new`/`RwLock::new`/`Condvar::new`; I/O safety types `OwnedFd`/`BorrowedFd` (`std::os::unix::io`) | |

#### Do Not Use or Recommend

##### Edition 2024 only (unavailable in a 2021 crate on every compiler)

- **Let chains** in `if`/`while`: `if let Some(x) = a && x > 2 { … }` (1.88, edition 2024).[^32] In 2021 write nested `if let`, `let`-`else`, a `match` with an `if let` guard (1.95+), or `matches!`. Do **not** say "let chains need Rust 1.88" to a 2021 crate — they need the 2024 edition.
- Relying on 2024 **temporary scopes** (`if let` scrutinee dropped before `else`; tail-expression temporaries dropped before locals) or on **2024 RPIT capture** (all lifetimes captured implicitly).
- `Future`/`IntoFuture` **without import** (2024 prelude).
- `boxed_slice.into_iter()` yielding owned items (2024).
- Treating `gen` as a keyword, or `#"…"#` guarded strings.
- Treating `std::env::set_var` as requiring `unsafe` as a *compile-time* fact (it is unsafe *in practice* in every edition; see Concurrency).

##### Nightly-only (never valid on stable; all verified to fail on 1.99.1)

`#![feature(...)]` of any kind; `try { … }` blocks; `!` as a general type (`let x: ! = …`, `never_type`); `type Alias = impl Trait` (TAIT); `default fn` / specialization; `generic_const_exprs` (`[u8; N + 1]` in a generic signature); `&'static str` or other non-integer const generic parameters (`adt_const_params`); `gen { yield … }` blocks and `yield`; `f16`/`f128`; `const { … }` **as a pattern**; `Iterator::intersperse`, `Iterator::array_chunks`, `Iterator::try_collect`; `OnceLock::get_or_try_init` / `OnceCell::get_or_try_init`; `MutexGuard::map` (`mapped_lock_guards`); `BTreeMap::lower_bound`/cursors; `HashMap::raw_entry_mut` (not in std at all; it exists in `hashbrown`); trait aliases (`trait Num = Copy + Default;`); negative impls (`impl !Send for S {}`); `std::simd` (`portable_simd`); `std::async_iter::AsyncIterator`; `#[derive(CoercePointee)]`; deref patterns; `#[bench]` (fully destabilised in 1.88); `-Z` compiler/Cargo flags, `cargo-features = [...]`, and nightly-only rustfmt options (`imports_granularity`, `group_imports`).

##### Beyond the declared MSRV

Anything in the table above whose version exceeds `rust-version`. Frequent mistakes: suggesting `LazyLock` (1.80) to an MSRV-1.70 crate (use `OnceLock`), `let`-`else` to MSRV < 1.65, `#[expect]` to MSRV < 1.81 (use `#[allow]`), `is_none_or` to MSRV < 1.82 (use `map_or(true, …)`), `Vec::extract_if` to MSRV < 1.87 (use `retain` or `drain`), `assert_matches!` to MSRV < 1.96 (use `assert!(matches!(…))`), `async fn` in a trait to MSRV < 1.75 (use `async-trait` or a boxed future).

##### Deprecated or discouraged

- `std::i32::MAX`, `std::u64::MIN` (legacy integer-module constants) and `i32::max_value()`-style functions: use `i32::MAX`, `u64::MIN` (associated constants since 1.43). The legacy integer modules are fully deprecated in 1.99 (verified: both forms warn on 1.99.1, neither warns on 1.85), which breaks `-D warnings` builds.
- `std::mem::uninitialized()` and `std::mem::zeroed()` for types with invalid all-zero values — use `MaybeUninit`.
- `try!(…)` (2015 macro; `try` is a reserved keyword since 2018) — use `?`.
- `lazy_static!` / `once_cell` in crates whose MSRV allows `LazyLock`/`OnceLock`.
- `Error::description()` and `Error::cause()` — implement `Display` and `source()`.
- `#[macro_use] extern crate foo;` — import macros with `use foo::mac;` (2018+).
- `std::sync::mpsc` for new async code — use the runtime's channels (`tokio::sync::mpsc`); `std::sync::mpsc` is fine for threads.

#### Code Style and Naming

- `snake_case` for functions, methods, variables, modules and crates; `UpperCamelCase` for types, traits and enum variants; `SCREAMING_SNAKE_CASE` for `const` and `static`; lifetimes short and lowercase (`'a`, `'de`). Acronyms are words: `HttpClient`, not `HTTPClient`.[^25]
- Conversion naming: `as_*` (cheap, borrowed view), `to_*` (expensive or owned), `into_*` (consumes `self`). Getters have no `get_` prefix (`fn len(&self)`), except `get`/`get_mut` for keyed or fallible access.
- Format with `rustfmt` (`cargo fmt --check` in CI). In a 2021 crate rustfmt uses the 2021 style edition; the 2024 style edition (different import sorting) is applied only when the edition or `style_edition = "2024"` in `rustfmt.toml` says so — a formatting-only diff after such a change is not a review finding.
- Imports: group `std`/`core`/`alloc`, external crates, then `crate::`/`super::`. Use `crate::` paths (2018+); `extern crate` is needed essentially only for `alloc` in `no_std` crates.
- Document every public item (`///`), with `# Errors`, `# Panics` and `# Safety` sections where they apply (Clippy `missing_errors_doc`, `missing_panics_doc`, `missing_safety_doc`).
- Prefer `impl Trait` in argument position only for simple callbacks; use a named generic parameter when callers may need turbofish (`f::<T>()`) — the type of an `impl Trait` argument can never be specified explicitly.

#### Ownership, Borrowing and Lifetimes

##### Borrow instead of clone

```rust
// BAD: forces callers to allocate, clones needlessly
fn greet_bad(name: String) -> String { format!("hello {}", name.clone()) }

// GOOD: accept the most general borrowed form
fn greet(name: &str) -> String { format!("hello {name}") }

// GOOD: take ownership only when you store the value; let the caller decide to clone
struct User { name: String }
impl User {
    fn new(name: impl Into<String>) -> Self { Self { name: name.into() } }
}

fn main() {
    let n = String::from("ann");
    println!("{} {} {}", greet_bad(n.clone()), greet(&n), User::new(n).name);
}
```

Review rules:

- Parameters: `&str` over `&String`, `&[T]` over `&Vec<T>`, `&Path` over `&PathBuf`, `impl AsRef<Path>` for path-like inputs (Clippy `ptr_arg`).
- A `.clone()` added to "fix the borrow checker" deserves scrutiny: it may hide a design problem (holding a borrow too long) or cost an allocation per loop iteration. `Rc`/`Arc` clones are cheap (a counter increment) and clearer as `Arc::clone(&x)` (Clippy `clone_on_ref_ptr`, restriction).
- Return owned values (`String`, `Vec<T>`) from constructors and builders; return borrows from accessors.
- `Cow<'a, str>` when a function usually returns its input unchanged but sometimes must allocate.

##### Lifetime elision and explicitness

- Elision rules: each elided input lifetime becomes a distinct parameter; if there is exactly one input lifetime, or a `&self`/`&mut self`, it is used for all elided output lifetimes.
- Write `'_` in paths for elided lifetimes (`Formatter<'_>`, `Ref<'_, T>`) so that borrows are visible; the allow-by-default lint `elided_lifetimes_in_paths` enforces this. Since 1.89 the warn-by-default `mismatched_lifetime_syntaxes` flags signatures that hide in the output a lifetime that is visible in the input (`fn f(x: &u8) -> Ref<u8>` style).
- `'static` bounds (`T: 'static`) mean "contains no non-static borrows", not "lives forever". `thread::spawn` and `tokio::spawn` require it; `thread::scope` (1.63) does not.

##### Drop order and RAII guards

Locals are dropped in **reverse declaration order**; struct fields in **declaration order**; temporaries at the end of the enclosing statement (with the 2021 exceptions for `if let`, `match` and tail expressions shown above).[^13]

```rust
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(0);
    // On rustc < 1.65 this compiles and drops the guard immediately — no lock is held.
    // Since 1.65 the deny-by-default lint `let_underscore_lock` rejects it:
    // let _ = m.lock().unwrap();
    let _guard = m.lock().unwrap(); // GOOD: a named binding keeps the guard to end of scope
    println!("held: try_lock ok = {}", m.try_lock().is_ok()); // false
}
```

`let _ = expr;` drops `expr` immediately; `let _name = expr;` keeps it. The lint covers only standard lock guards — the same mistake with a tracing span guard (`let _ = span.enter();`), a temp-dir handle, a Tokio permit or a custom RAII type compiles silently. `let_underscore_drop` (allow-by-default) and Clippy `let_underscore_future`/`let_underscore_must_use` cover more cases.

##### Interior mutability

| Type | Thread-safe | Failure mode |
|---|---|---|
| `Cell<T>` | no | none (`Copy`/`take`/`replace` only) |
| `RefCell<T>` | no | **panics** on a conflicting borrow at runtime (1.99: `RefCell already borrowed`) |
| `OnceCell<T>` (1.70) / `LazyCell<T>` (1.80) | no | — |
| `Mutex<T>` / `RwLock<T>` | yes | poisoning after a panic; deadlock |
| `OnceLock<T>` (1.70) / `LazyLock<T>` (1.80) | yes | `LazyLock` poisons if its initialiser panics |
| atomics | yes | ordering bugs |

Holding a `RefCell` borrow across a call that re-borrows panics; holding a `Ref`/`RefMut` across `.await` is a bug even on a single-threaded runtime (Clippy `await_holding_refcell_ref`).

#### Error Handling

##### `Result` and `?`

```rust
use std::fmt;
use std::num::ParseIntError;

#[derive(Debug)]
pub enum ConfigError {
    Missing(&'static str),
    BadPort(ParseIntError),
}

impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            ConfigError::Missing(k) => write!(f, "missing key {k}"),
            ConfigError::BadPort(_) => write!(f, "invalid port"),
        }
    }
}

impl std::error::Error for ConfigError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            ConfigError::BadPort(e) => Some(e),
            ConfigError::Missing(_) => None,
        }
    }
}

impl From<ParseIntError> for ConfigError {
    fn from(e: ParseIntError) -> Self { ConfigError::BadPort(e) }
}

fn port(raw: Option<&str>) -> Result<u16, ConfigError> {
    let raw = raw.ok_or(ConfigError::Missing("port"))?;
    Ok(raw.trim().parse::<u16>()?) // `?` converts via From
}

fn main() {
    println!("{:?} {:?}", port(Some("8080")), port(None).map_err(|e| e.to_string()));
}
```

Rules:

- **Libraries** expose typed errors (an enum, usually derived with `thiserror`), implement `std::error::Error`, `Display` and `Debug`, and are `Send + Sync + 'static` so callers can box them. Either put the cause in `Display` **or** return it from `source()`, not both — reporters that walk the chain print it twice.
- **Applications** may use `anyhow::Result` (or `Box<dyn Error + Send + Sync>`) and add context at each layer (`.context("reading config")`).
- Mark error enums `#[non_exhaustive]` if variants may be added in minor releases.
- `core::error::Error` (1.81) lets `no_std` libraries implement the error trait; with an older MSRV, gate it behind a `std` feature.
- `main` may return `Result<(), E: Debug>`; the error is printed with `Debug` and the exit code is 1. For a custom exit code return `std::process::ExitCode` (1.61).
- `Result<T, E>` and `Option<T>` are `#[must_use]`; an ignored `Result` is a warning that CI should deny. `let _ = fallible();` silences it explicitly — acceptable only with a comment explaining why the error does not matter.

##### Anti-patterns

```rust
use std::fs;
use std::io;

// BAD: loses the error kind and the path
fn load_bad(p: &str) -> Option<String> { fs::read_to_string(p).ok() }

// BAD: stringly-typed errors cannot be matched by callers
fn load_bad2(p: &str) -> Result<String, String> { fs::read_to_string(p).map_err(|e| e.to_string()) }

// BETTER: keep the error kind, add the path (or wrap the io::Error in a typed error)
fn load(p: &str) -> io::Result<String> {
    fs::read_to_string(p).map_err(|e| io::Error::new(e.kind(), format!("{p}: {e}")))
}

fn main() {
    let _ = (load_bad("/nonexistent"), load_bad2("/nonexistent"));
    match load("/nonexistent") {
        Err(e) if e.kind() == io::ErrorKind::NotFound => println!("not found: {e}"),
        other => println!("{other:?}"),
    }
}
```

- `io::Error::other(e)` (1.74) instead of `io::Error::new(ErrorKind::Other, e)`.
- Do not `match` on error **message text**; match on kinds or variants.
- `Box<dyn Error>` without `+ Send + Sync` cannot cross `tokio::spawn` or thread boundaries.

#### Panics

- **Panics are for bugs** (violated invariants), not for input validation, I/O failures or network errors. Library code that panics on bad input is a finding unless the panic is documented (`# Panics`).
- `unwrap()`/`expect()` in production paths: acceptable when the invariant is local and obvious (`"static regex compiles"`), and then `expect("why this cannot fail")` is preferred. On request/input paths, propagate with `?`.
- Indexing (`v[i]`, `&s[a..b]`, `map[&k]`), integer division by zero, `RefCell` conflicts, overflow in debug builds, `Duration - Duration` underflow (`overflow when subtracting durations`; note that `Instant - Instant` saturates to zero since 1.60), `slice::split_at`, `Vec::remove` out of range, `copy_from_slice` length mismatch and `sort` with an invalid `Ord` (1.81+) all panic. Use `get`, `checked_*`, `split_at_checked` (1.80), `try_borrow`.
- `panic = "abort"` in a profile turns every panic into process abort: `catch_unwind`, `Drop` during unwinding and Tokio's per-task panic isolation stop working. Check the profile before relying on them.
- A panic in a spawned thread is returned by `JoinHandle::join()` as `Err`; a panic in a Tokio task surfaces as `JoinError::is_panic()` — ignoring the join result loses it.
- A panic while holding a `std::sync::Mutex` **poisons** it; later `lock()` returns `Err(PoisonError)`.[^19]

```rust
use std::sync::{Arc, Mutex};

fn main() {
    let m = Arc::new(Mutex::new(vec![1]));
    let m2 = Arc::clone(&m);
    let _ = std::thread::spawn(move || {
        let _g = m2.lock().unwrap();
        panic!("boom");
    })
    .join();
    println!("poisoned = {}", m.is_poisoned()); // true
    // Recover only if the protected data is still consistent:
    let v = m.lock().unwrap_or_else(|e| e.into_inner());
    println!("{:?}", *v);
}
```

- Since 1.81 a panic that tries to unwind out of an `extern "C"` function aborts the process (verified: on 1.56 the panic unwinds into the Rust caller and `catch_unwind` catches it — undefined behaviour; 1.85 and 1.99 print `panic in a function that cannot unwind` and abort with SIGABRT). FFI callbacks must `catch_unwind` and return an error code; use `extern "C-unwind"` (1.71) only when the foreign side is built to propagate unwinding.
- Panic messages include the thread ID since 1.91 (`thread 'main' (12345) panicked at …`); log-parsing regexes written for older output may need updating.

#### Integers, Floats and Casting

```rust
fn main() {
    let x = std::hint::black_box(200u8);
    // Explicit overflow semantics — the reviewer should see one of these, not bare `+`,
    // wherever overflow is possible:
    println!("{} {:?} {}", x.wrapping_add(100), x.checked_add(100), x.saturating_add(100));
    // `as` never fails: it truncates, wraps sign, and saturates float→int (NaN → 0)
    println!("{} {} {} {} {}", -1i32 as u32, 300i32 as u8, f64::NAN as i32, 1e10f64 as i32, -5.7f64 as u8);
    // prints: 44 None 255 / 4294967295 44 0 2147483647 0
    let checked: Result<u8, _> = u8::try_from(300i32); // GOOD: fallible conversion
    println!("{:?}", checked.is_err());
    // let y = x + 100; // debug: panics "attempt to add with overflow"; release: wraps to 44
}
```

- Plain `+ - *` on integers from untrusted input (lengths, offsets, prices, timestamps) must use `checked_*` (return an error), `saturating_*`, or `wrapping_*` when wrap-around is intended (hashes, sequence numbers). `strict_*` (1.91) always panics on overflow, also in release builds. Consider `overflow-checks = true` in `[profile.release]` for security-sensitive code.
- `as` casts between integers silently truncate. Use `T::try_from(x)` / `x.try_into()` (prelude in 2021) for narrowing; `u64::from(x)` / `.into()` for lossless widening. Clippy `cast_possible_truncation`, `cast_sign_loss`, `cast_possible_wrap`, `as_conversions` (pedantic/restriction) find them.
- `usize` is 32 bits on 32-bit and wasm32 targets: `u64 as usize` truncates there.
- Integer division truncates toward zero; `%` keeps the sign of the dividend; use `rem_euclid` for a non-negative modulus. Unsigned `div_ceil` is 1.73.
- `x.is_multiple_of(0)` (1.87) returns `false` for `x != 0` instead of panicking like `x % 0`.
- Floats: never compare money with `f64`; use integer minor units or a decimal crate. `NaN != NaN`; sort floats with `total_cmp` (1.62); `f64` does not implement `Ord`/`Eq`/`Hash`, so it cannot be a `BTreeMap`/`HashMap` key without a wrapper.

#### Strings and Text

- `String`/`&str` are UTF-8; `len()` is in **bytes**. `&s[..n]` panics if `n` is not on a character boundary — `"héllo"[..2]` panics with `end byte index 2 is not a char boundary; it is inside 'é' (bytes 1..3 of string)`. Use `s.get(..n)` (returns `None`), `char_indices()`, `str::floor_char_boundary` (1.91) for truncation, or a grapheme crate for user-visible text.
- Truncating user input "to N characters" with byte slicing is both a panic risk and wrong for non-ASCII text.
- `to_lowercase()`/`to_uppercase()` are Unicode-aware and may change length; for protocol keywords and header names use `eq_ignore_ascii_case` and `to_ascii_lowercase`.
- Build strings with `String::with_capacity` + `push_str`, `write!` into a `String` (`use std::fmt::Write`), or `format!` — not repeated `s = s + &x` in loops.
- `OsStr`/`OsString` and `Path` are not UTF-8. `to_str()` returns `Option`; `to_string_lossy()` replaces invalid sequences. `OsStr::display()` (1.87) formats without allocation.
- `String::from_utf8(bytes)` validates; `String::from_utf8_lossy` returns `Cow<str>`; `String::from_utf8_unchecked` on unvalidated input is undefined behaviour.
- Formatting: `{:?}` of user-controlled strings in logs escapes control characters (good against log injection); `{}` does not.

```rust
fn truncate(s: &str, max_bytes: usize) -> &str {
    // MSRV >= 1.91: &s[..s.floor_char_boundary(max_bytes)]
    let mut end = max_bytes.min(s.len());
    while !s.is_char_boundary(end) { end -= 1; }
    &s[..end]
}

fn main() {
    let s = String::from("héllo");
    println!("{:?} {:?}", s.get(..2), truncate(&s, 2)); // None "h"
}
```

#### Collections and Iterators

##### Choosing collections

- `Vec<T>` by default; `VecDeque` for queues; `HashMap`/`HashSet` for lookup (iteration order is **random per process** — never depend on it in output, tests or hashing); `BTreeMap`/`BTreeSet` for ordered iteration and range queries; `BinaryHeap` for priority queues (max-heap; wrap in `Reverse` for min).
- `HashMap` uses SipHash-1-3 with random keys (DoS-resistant). Faster hashers (`ahash`, `rustc-hash`/`FxHash`) are fine for trusted keys and a finding when keys are attacker-controlled.
- `Vec::with_capacity(n)` when `n` is known; never pre-allocate from an **untrusted length field** (a `u32` length in a packet → 4 GiB allocation). Cap it or grow incrementally; `try_reserve` (1.57) returns an error instead of aborting.
- Removing in a loop: `retain`/`retain_mut` (1.61), `extract_if` (1.87) or `drain(..)` — never index-based `remove(i)` while iterating forward (skips elements, O(n²)).

##### Entry API

```rust
use std::collections::HashMap;

fn main() {
    let text = "a b a c b a";
    let mut counts: HashMap<&str, usize> = HashMap::new();
    for w in text.split_whitespace() {
        *counts.entry(w).or_insert(0) += 1; // one lookup, no unwrap
    }
    // BAD: double lookup and a panic path
    // if counts.contains_key(w) { *counts.get_mut(w).unwrap() += 1 } else { counts.insert(w, 1); }
    let mut v: Vec<_> = counts.into_iter().collect();
    v.sort(); // deterministic output despite random HashMap order
    println!("{:?}", v);
}
```

##### Iterators

- Prefer iterator chains to index loops: they avoid bounds checks and off-by-one errors. `for i in 0..v.len() { v[i] … }` is a review smell (Clippy `needless_range_loop`).
- Iterators are **lazy**: `v.iter().map(|x| side_effect(x));` without a consumer does nothing (warning `unused_must_use`). Use `for` or `for_each` for side effects.
- `collect::<Result<Vec<_>, _>>()` stops at the first error; `collect::<Option<Vec<_>>>()` likewise. Use it instead of `unwrap` in a `map`.
- Avoid `collect()` just to call `.len()`, `.is_empty()` or iterate again (Clippy `needless_collect`).
- `zip` stops at the shorter iterator silently — assert equal lengths when they must match.
- `chunks_exact`, `windows`, `array_windows` (1.94), `as_chunks` (1.88), `chunk_by` (1.77) avoid manual index arithmetic.
- `iter()` vs `into_iter()` vs `iter_mut()`: in 2021, `array.into_iter()` yields values (see edition section). For `Vec`, `vec.into_iter()` consumes the vector.
- 1.99 changed how `RangeInclusive` (`a..=b`) iterates; the `start()`/`end()` values of an **exhausted** `RangeInclusive`, and using one as a slice index, may differ from older compilers (never guaranteed). Do not reuse a range after iterating it.[^1]

```rust
fn parse_all(input: &[&str]) -> Result<Vec<u32>, std::num::ParseIntError> {
    input.iter().map(|s| s.parse::<u32>()).collect()
}

fn main() {
    println!("{:?}", parse_all(&["1", "2"]));
    println!("{}", parse_all(&["1", "x"]).is_err());
    let total: u32 = [1u32, 2, 3].iter().copied().filter(|x| x % 2 == 1).sum();
    println!("{total}");
}
```

##### Sorting

- `sort`/`sort_by` are stable; `sort_unstable*` are faster and allocation-free when stability is not needed.
- Since **1.81**, the sort implementations **may panic** if the comparator is not a total order (verified: a random comparator on 200 elements panics on 1.99.1 with `user-provided comparison function does not correctly implement a total order`; 1.65 returns an arbitrary order). Comparators such as `a.partial_cmp(b).unwrap_or(Ordering::Equal)` on floats containing NaN, or inconsistent multi-key comparisons, are now crash bugs.[^20]
- `sort_by_key` with a key that allocates (`|p| p.name.clone()`) calls the key function O(n log n) times — use `sort_by_cached_key` or `sort_by(|a, b| a.name.cmp(&b.name))`.
- `binary_search` on a slice with duplicate keys may return any matching index; 1.82 changed which one (never guaranteed).

#### Traits and Generics

##### Static vs dynamic dispatch

- Generics (`fn f<T: Trait>(t: T)` / `impl Trait`) are monomorphised: fastest, but each instantiation adds code size. `dyn Trait` (`&dyn`, `Box<dyn>`, `Arc<dyn>`) has one copy and a vtable call. In 2021 the `dyn` keyword is mandatory.
- A trait is usable as `dyn Trait` ("dyn compatible", formerly "object safe") only if it has no `Sized` supertrait, no associated constants and no generic associated types, and every method not marked `where Self: Sized` has no type parameters, mentions `Self` only in the receiver, and is neither `async fn` nor returns `impl Trait`. **A trait with an `async fn` method (1.75) is not dyn compatible** (E0038 "the trait `A` is not dyn compatible"); use a boxed-future method or the `async-trait` crate when `dyn` is needed.
- **Trait upcasting** (`&dyn Sub` → `&dyn Super`) requires MSRV 1.86; before that, add an `fn as_super(&self) -> &dyn Super` method.

```rust
trait Shape { fn area(&self) -> f64; }
trait Named: Shape { fn name(&self) -> &str; }

struct Sq(f64);
impl Shape for Sq { fn area(&self) -> f64 { self.0 * self.0 } }
impl Named for Sq { fn name(&self) -> &str { "square" } }

fn total(shapes: &[Box<dyn Named>]) -> f64 { shapes.iter().map(|s| s.area()).sum() }

fn main() {
    let v: Vec<Box<dyn Named>> = vec![Box::new(Sq(2.0))];
    println!("{} {}", v[0].name(), total(&v));
    let s: &dyn Named = &Sq(1.0);
    let base: &dyn Shape = s; // trait upcasting: MSRV >= 1.86
    println!("{}", base.area());
}
```

##### Generic associated types, `async fn` and RPITIT in traits

- GATs (1.65)[^30] enable lending iterators and borrowed associated types (`type Item<'a> where Self: 'a;`).
- `async fn` in traits (1.75)[^29] is **not object-safe** and its future has **no `Send` bound** that generic callers can rely on. A generic function that `tokio::spawn`s `t.fetch()` fails to compile (`future cannot be sent between threads safely`). For public traits, rustc warns (`async_fn_in_trait`: "use of `async fn` in public traits is discouraged as auto trait bounds cannot be specified"). Declare the method as `fn fetch(&self) -> impl Future<Output = T> + Send;` — implementors may still write `async fn`.

```rust
use std::future::Future; // not in the 2021 prelude

pub trait Fetch {
    fn fetch(&self) -> impl Future<Output = u32> + Send; // MSRV >= 1.75
}

struct F;
impl Fetch for F {
    async fn fetch(&self) -> u32 { 1 }
}

fn assert_send<Fut: Future + Send>(_: Fut) {}

fn check<T: Fetch + Sync>(t: &T) {
    // compiles only because the trait promises a Send future;
    // with `async fn fetch(&self) -> u32;` in the trait this is an error
    assert_send(t.fetch());
}

fn main() { check(&F); }
```

##### Coherence, blanket impls and sealed traits

- Implementing a foreign trait for a foreign type is forbidden (orphan rule); wrap the type in a newtype.
- Adding a **blanket impl** (`impl<T: Display> MyTrait for T`) to a published crate is a breaking change.
- Public traits that downstream crates must not implement should be **sealed** (a supertrait in a private module), so methods can be added later without breaking changes.
- Derive the standard traits users expect on public types: `Debug` always; `Clone`, `Copy`, `PartialEq`, `Eq`, `Hash`, `PartialOrd`, `Ord`, `Default` where meaningful. `Eq`/`Hash`/`Ord` must agree with `PartialEq` — a manual `PartialEq` with derived `Hash` breaks `HashMap`; a manual `PartialOrd` inconsistent with `Ord` breaks sorting. Since 1.98, `#[derive(PartialOrd, Ord)]` makes `partial_cmp` delegate to the derived `Ord`, so a field type whose `PartialOrd` and `Ord` disagree changes behaviour (verified: `Some(Less)` on 1.85, `Some(Greater)` on 1.99.1).[^1]
- `#[derive(Default)]` on enums with `#[default]` needs MSRV 1.62.

##### Generic bounds hygiene

- Put bounds on `impl` blocks and functions, not on the struct definition (`struct Wrapper<T: Clone>` forces the bound everywhere).
- `where` clauses for long bounds; associated type bounds `I: Iterator<Item: Display>` need MSRV 1.79 (otherwise `where I::Item: Display`).
- Prefer `AsRef<str>`/`Into<String>` sparingly; each generic parameter multiplies monomorphisations. The "inner function" pattern (generic wrapper calling a non-generic `fn inner(p: &Path)`) limits code bloat.

#### Closures

- Closure capture in 2021 is **per field** (see the edition section) — the most common source of surprising borrow-checker successes and drop-order changes in migrated code.
- `move` closures move every captured place; to move a clone of an `Arc` into a thread, clone first: `let a = Arc::clone(&a); thread::spawn(move || consume(a));`.
- `Fn` (shared), `FnMut` (mutable), `FnOnce` (consuming): accept the most permissive bound the callee needs (`FnOnce` for one-shot callbacks, `FnMut` for repeated mutation).
- Returning closures: `impl Fn(u32) -> u32` (static dispatch) or `Box<dyn Fn(u32) -> u32 + Send + 'static>`.
- Async closures `async |x| …` and `AsyncFn*` bounds require MSRV **1.85** (not edition 2024). Before that, use `|x| async move { … }` with `F: Fn(T) -> Fut, Fut: Future`.

```rust
fn make_adder(n: u32) -> impl Fn(u32) -> u32 { move |x| x + n }

fn apply_twice<F: FnMut()>(mut f: F) { f(); f(); }

fn main() {
    let add5 = make_adder(5);
    let mut count = 0;
    apply_twice(|| count += 1);
    println!("{} {}", add5(1), count);
}
```

#### Smart Pointers and Shared Ownership

- `Box<T>`: single owner on the heap; recursive types; trait objects.
- `Rc<T>` (single-threaded) / `Arc<T>` (thread-safe) shared ownership. `Rc` is `!Send`; using `Arc` where `Rc` suffices costs atomic operations.
- **Reference cycles leak** (`Rc<RefCell<Node>>` parent ↔ child). Use `Weak` for back-pointers.
- `Arc<Mutex<T>>` is the default shared-mutable pattern for threads; `Arc<RwLock<T>>` only when reads dominate and critical sections are long (an `RwLock` is not automatically faster).
- `Arc::make_mut` / `Rc::make_mut` for clone-on-write; `Arc::unwrap_or_clone` (1.76) to take ownership when possibly unique.
- `Arc<str>` / `Arc<[T]>` instead of `Arc<String>` / `Arc<Vec<T>>` for immutable shared data (one allocation and indirection less; Clippy `rc_buffer`).
- `Pin<Box<T>>` / `pin!` (1.68) for self-referential futures; never move out of a pinned value in `unsafe` code.
- `std::mem::forget` and `Box::leak` are safe but leak; `Rc` cycles also leak. Memory safety does not include leak freedom — code must never rely on `Drop` running for soundness.

#### Unsafe Code and Soundness

Every `unsafe` block asserts that the code upholds invariants the compiler cannot check. A reviewer treats each one as a proof to verify, and treats unsound **safe** APIs (a safe function that can cause UB for some input) as critical bugs even if no current caller triggers them.[^21][^22]

##### Rules

- Keep `unsafe` blocks minimal and wrap them in a safe abstraction that enforces the invariant (bounds check, alignment check, lifetime tie).
- Every `unsafe` block gets a `// SAFETY:` comment; every `unsafe fn` and `unsafe trait` gets a `# Safety` doc section (Clippy `undocumented_unsafe_blocks`, `missing_safety_doc`, `multiple_unsafe_ops_per_block`).
- In edition 2021 the body of an `unsafe fn` is implicitly an `unsafe` block. Enable `#![warn(unsafe_op_in_unsafe_fn)]` (stable since 1.52, allow-by-default in 2021, warn-by-default in 2024) so each unsafe operation inside is scoped and justified.
- Crates that need no unsafe code: `#![forbid(unsafe_code)]` (or `[lints.rust] unsafe_code = "forbid"`, MSRV ≥ 1.74 for the table to be honoured).
- `unsafe impl Send/Sync` must be justified: what synchronisation makes cross-thread access sound? A wrapper around a raw pointer is not automatically thread-safe.

##### Common sources of undefined behaviour

- Creating a `&mut T` that aliases another live reference, or a `&T` while something mutates through a raw pointer.
- `static mut`: any reference (`&STATIC`, `&mut STATIC`, method calls with autoref) is UB-prone; in 2021 `static_mut_refs` only warns. Use atomics, `Mutex`, `OnceLock`/`LazyLock`, or `&raw const STATIC`/`&raw mut STATIC` (1.82; `ptr::addr_of!`/`addr_of_mut!` for older MSRV) and access through raw pointers.
- Uninitialised memory: `mem::uninitialized()` (deprecated), `mem::zeroed()` for types where all-zero is invalid (references, `Box`, function pointers, `NonZero*`, many enums), `Vec::set_len` before writing the elements. Use `MaybeUninit<T>` and `assume_init` only after full initialisation.
- `slice::from_raw_parts(ptr, len)` with a null or unaligned pointer (even for `len == 0`), or a length whose byte size exceeds `isize::MAX`.
- `str::from_utf8_unchecked` / `String::from_utf8_unchecked` on unvalidated bytes.
- `mem::transmute` between types with different layout or validity (`u8` → `bool`, integer → reference, `Vec<T>` → `Vec<U>`). Prefer `from_ne_bytes`, `f32::from_bits`, `ptr::cast`, `bytemuck`/`zerocopy`. Since 1.91 `integer_to_ptr_transmutes` warns on integer-to-pointer transmutes.
- References to fields of `#[repr(packed)]` structs are a hard error since 1.69 (E0793; 1.56 only warns) — read them by value (`{ p.b }`) or through `&raw const` (1.82) / `ptr::addr_of!` plus `read_unaligned`.
- Matching a `union` together with another value in one pattern can read the union before the rest of the pattern is checked — the Rust Reference stopped recommending this in 1.99 because it can cause UB.[^1]

Since **1.78**, many `unsafe` standard-library functions check their preconditions **in debug builds** (`debug_assertions` on) and abort with a clear message (verified on 1.99.1; in a release build the same program silently continues):

```rust
fn main() {
    let p: *const u32 = std::hint::black_box(std::ptr::null());
    // debug build: "unsafe precondition(s) violated: slice::from_raw_parts requires the
    // pointer to be aligned and non-null, and the total size of the slice not to exceed
    // `isize::MAX`" and the process aborts. Release build: no check — UB.
    let s = unsafe { std::slice::from_raw_parts(p, 0) };
    println!("{}", s.len());
}
```

With a literal `std::ptr::null()` argument the deny-by-default lint `invalid_null_arguments` (1.88) already rejects the call at compile time.

Run tests that touch `unsafe` under **Miri** (`cargo +nightly miri test`; Miri needs a nightly toolchain but checks stable-language code) and, for FFI-heavy code, under AddressSanitizer in CI.

##### FFI

```rust
use std::ffi::{CStr, CString};
use std::os::raw::c_char;

extern "C" {
    fn strlen(s: *const c_char) -> usize;
}

fn c_len(s: &str) -> Result<usize, std::ffi::NulError> {
    let owned = CString::new(s)?; // fails on interior NUL — never unwrap untrusted input
    // BAD: `CString::new(s).unwrap().as_ptr()` dangles immediately
    //      (warning dangling_pointers_from_temporaries).
    // SAFETY: `owned` outlives the call and is NUL-terminated.
    Ok(unsafe { strlen(owned.as_ptr()) })
}

fn main() {
    println!("{:?}", c_len("hello"));
    let raw: &CStr = CStr::from_bytes_until_nul(b"hi\0rest").unwrap(); // 1.69
    println!("{:?}", raw);
}
```

- Types crossing FFI need `#[repr(C)]` (or `#[repr(transparent)]`); Rust enums without `#[repr(C)]`/`#[repr(u8)]` have no stable layout (1.97 changed the encoding of some enums without layout guarantees). Never pass a Rust `String`, `Vec`, `&str` or trait object to C directly.
- In edition 2021, `extern "C" { … }` blocks and `#[no_mangle]` are accepted without `unsafe`; with MSRV ≥ 1.82, prefer `unsafe extern "C" { pub safe fn …; }` and `#[unsafe(no_mangle)]` — they make the obligation explicit and are what edition 2024 requires.
- Callbacks called from C must not unwind (see Panics). Return error codes; catch panics with `std::panic::catch_unwind`.
- Memory allocated by C must be freed by C, memory allocated by Rust must be freed by Rust (`Box::into_raw` / `Box::from_raw` pairs).
- Rust 1.99.0 miscompiled FFI `bool` return values on x86_64; 1.99.1 fixes it.[^1]
- Prefer `bindgen`/`cbindgen` generated declarations over hand-written signatures; a mismatched signature is UB without any diagnostic.

#### Concurrency (Threads and Synchronisation)

##### Scoped threads (1.63)

```rust
fn main() {
    let mut data = vec![1, 2, 3, 4];
    let (left, right) = data.split_at_mut(2);
    std::thread::scope(|s| {
        s.spawn(|| left.iter_mut().for_each(|x| *x *= 10));
        s.spawn(|| right.iter_mut().for_each(|x| *x += 1));
    }); // all scoped threads are joined here; panics propagate
    println!("{:?}", data); // [10, 20, 4, 5]
}
```

`thread::scope` removes the need for `Arc` + `'static` when threads only borrow local data. With MSRV < 1.63 use `crossbeam::scope`.

##### Locks

- Keep critical sections short; never call unknown code (callbacks, logging that may lock, `await`) while holding a lock.
- Acquire multiple locks in a **globally consistent order**; otherwise deadlock.
- `std::sync::Mutex` is fine for most uses (futex-based on Linux since 1.62); `parking_lot` has no poisoning and a smaller footprint. Choosing between them is not a review finding by itself.
- `Mutex::new` is `const` since 1.63: `static M: Mutex<Vec<T>> = Mutex::new(Vec::new());` needs no `lazy_static`.
- `RwLock` writer starvation and fairness are platform-dependent; `RwLockWriteGuard::downgrade` needs 1.92.
- `Condvar::wait` must be in a loop that re-checks the predicate (spurious wake-ups) — or use `wait_while`.

##### Atomics

- `Relaxed` is enough for independent counters and statistics. Publishing data to another thread needs `Release` on the store and `Acquire` on the load. `SeqCst` when several atomics must be observed in one global order. If the justification for an ordering is not written down, ask for it.
- A check-then-act on an atomic (`if a.load() == 0 { a.store(1) }`) is a race; use `compare_exchange`, `fetch_update`, or `update`/`try_update` (1.95).
- `AtomicU64` is not available on every 32-bit target; check `cfg(target_has_atomic = "64")` in portable code.

##### Process-global state

- `std::env::set_var`/`remove_var` are safe functions in edition 2021, but on most Unix platforms they race with any concurrent `getenv` (including inside libc and other libraries) and can cause UB. The standard library documents that "in multi-threaded programs on other operating systems [than Windows], the only sound option is to not use `set_var` or `remove_var` at all" — even `std::net::ToSocketAddrs` may read the environment.[^34] Set environment variables for child processes with `Command::env` instead; read configuration once at startup.
- `std::process::exit` does not run destructors of the current or other threads (buffered writers are not flushed).

##### Channels

- `std::sync::mpsc` (crossbeam-based since 1.67; `Sender: Sync` since 1.72) for threads; `crossbeam-channel` or `flume` for multi-consumer. Bounded channels (`sync_channel(n)`) give back-pressure; unbounded channels are a memory-exhaustion risk under load.
- Dropping all `Sender`s ends the receiver's iteration — keep a stray clone alive and the consumer never terminates.

#### Async Rust and Tokio

Async functions return futures that do nothing until polled. Most production code uses **Tokio**: latest **1.54.1 (2026-10-21)**, MSRV **1.85** for 1.54.x; the LTS lines **1.51.x (until March 2027)** and **1.53.x (until September 2027)** keep MSRV **1.71**.[^16] A 2021 crate with an MSRV below 1.85 must constrain Tokio, e.g. `tokio = { version = "~1.53", features = [...] }`, or its lockfile will move to an incompatible release.

##### Never block the runtime

```rust
use std::time::{Duration, Instant};

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let start = Instant::now();
    let ticker = tokio::spawn(async move {
        tokio::time::sleep(Duration::from_millis(10)).await;
        start.elapsed()
    });
    // BAD: blocks the runtime thread; the 10 ms timer fires after ~200 ms
    std::thread::sleep(Duration::from_millis(200));
    println!("timer woke after {:?}", ticker.await.unwrap());

    // GOOD: blocking work goes to the blocking pool
    let start = Instant::now();
    let ticker = tokio::spawn(async move {
        tokio::time::sleep(Duration::from_millis(10)).await;
        start.elapsed()
    });
    tokio::task::spawn_blocking(|| std::thread::sleep(Duration::from_millis(200)))
        .await
        .unwrap();
    println!("timer woke after {:?}", ticker.await.unwrap()); // ~10 ms
}
```

Blocking calls include `std::fs`, `std::net`, `std::thread::sleep`, `std::sync::Mutex` contention, synchronous HTTP/database clients, CPU-heavy work (hashing passwords, compression, large JSON) and `reqwest::blocking`. Use `tokio::fs`/`tokio::net`, `spawn_blocking`, or a dedicated thread pool (`rayon`) for CPU work.[^18] Calling `Runtime::block_on` (or `Handle::block_on`) from inside the runtime panics: `Cannot start a runtime from within a runtime`.

##### Locks across `.await`

```rust
use std::sync::Mutex;

static COUNTER: Mutex<u32> = Mutex::new(0);

async fn bump() {
    // BAD: the guard lives across the await → the future is !Send and
    // `tokio::spawn(bump())` fails: "future cannot be sent between threads safely"
    // let mut g = COUNTER.lock().unwrap();
    // tokio::time::sleep(std::time::Duration::from_millis(1)).await;
    // *g += 1;

    // GOOD: scope the guard so it is dropped before the await
    {
        let mut g = COUNTER.lock().unwrap();
        *g += 1;
    }
    tokio::time::sleep(std::time::Duration::from_millis(1)).await;
}

#[tokio::main]
async fn main() {
    tokio::spawn(bump()).await.unwrap();
    println!("{}", *COUNTER.lock().unwrap());
}
```

- A `std::sync::Mutex` is correct in async code when the critical section is short and contains no `.await`. Use `tokio::sync::Mutex` only when the lock must be held across an `.await` (it is slower). Clippy: `await_holding_lock`, `await_holding_refcell_ref`.
- With MSRV < 1.74, `drop(guard)` before the `.await` is **not** enough for the `Send` analysis (verified: 1.65 still reports "future cannot be sent between threads safely"; 1.85 accepts it — MIR-based drop tracking arrived in 1.74). An explicit block scope works on every compiler.

##### Cancellation safety

Dropping a future cancels it at its current `.await`. In `tokio::select!`, every branch that does not complete is dropped. Work that a cancelled branch already did is lost unless the operation is documented as cancel-safe.[^17]

```rust
use std::time::Duration;
use tokio::sync::mpsc;

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let (tx, mut rx) = mpsc::channel::<u32>(8);
    tx.send(1).await.unwrap();
    // BAD: not cancel-safe — the first recv() completes, then the timeout
    // drops the future while it waits for the second message: `1` is lost.
    let pair = async {
        let a = rx.recv().await;
        let b = rx.recv().await;
        (a, b)
    };
    tokio::select! {
        p = pair => println!("pair {:?}", p),
        _ = tokio::time::sleep(Duration::from_millis(20)) => println!("timeout"),
    }
    tx.send(2).await.unwrap();
    println!("next recv: {:?}", rx.recv().await); // Some(2) — the 1 is gone
}
```

- Cancel-safe (per the Tokio `select!` docs): `mpsc::Receiver::recv`, `broadcast::Receiver::recv`, `watch::Receiver::changed`, `TcpListener::accept`, `AsyncReadExt::read`/`read_buf`, `AsyncWriteExt::write`/`write_buf`, `StreamExt::next`. **Not** cancel-safe (data loss): `read_exact`, `read_to_end`, `read_to_string`, `write_all`. **Not** cancel-safe (lose their place in a fairness queue): `tokio::sync::Mutex::lock`, `RwLock::read`/`write`, `Semaphore::acquire`, `Notify::notified`. Hand-written futures that buffer partial progress across `.await`s are not cancel-safe unless designed to be.
- In a `loop { select! { … } }`, create long-lived futures once outside the loop and pass `&mut fut` (pinned with `tokio::pin!` or `std::pin::pin!`) so progress is not reset every iteration.
- `select!` polls branches in random order; use `biased;` when priority matters (e.g. shutdown first).
- `tokio::time::timeout(d, fut)` cancels `fut` on expiry — same rules apply.
- Request handlers in axum/hyper are cancelled when the client disconnects; side effects after an `.await` may never run. Put must-complete work in a spawned task.

##### Tasks

- `tokio::spawn` requires `Send + 'static`. Dropping a `JoinHandle` **detaches** the task (it keeps running); call `abort()` to cancel it. Use `JoinSet` (or `tokio_util::task::TaskTracker`) to own groups of tasks and to observe their panics (`JoinError::is_panic()`).
- Spawned tasks that loop forever need a shutdown signal (`tokio_util::sync::CancellationToken`, a `watch` channel) and the main task must wait for them; otherwise the runtime drops them mid-operation on exit.
- Unbounded channels (`mpsc::unbounded_channel`) and unbounded `spawn` per request are memory-exhaustion risks; use bounded channels and a `Semaphore`.
- Recursive `async fn` needs `Box::pin` around the recursive call (allowed since 1.77; earlier MSRVs need the `async-recursion` crate or a manually boxed future).
- `#[must_use]`: a future that is created but not awaited does nothing (`unused_must_use` warning: "futures do nothing unless you `.await` or poll them").
- Large futures (big arrays or buffers held across `.await`) bloat every task; Clippy `large_futures` (pedantic) finds them — box them or move the data to the heap.

##### Mixing runtimes and blocking APIs

- Do not combine `async-std`/`smol` and Tokio types unless a compatibility layer is used; Tokio I/O types panic outside a Tokio runtime ("there is no reactor running").
- `futures::executor::block_on` inside a Tokio task blocks a worker thread and can deadlock.
- In libraries, do not pick a runtime for the user; expose `async fn` and let the application choose (or gate runtime-specific code behind features).

#### Macros

- `#[diagnostic::on_unimplemented]` (1.78) and `#[diagnostic::do_not_recommend]` (1.85) are forward-compatible: a compiler that knows the `diagnostic` namespace but not the attribute only warns (`unknown diagnostic attribute`, verified on 1.80 for `do_not_recommend`). Compilers before 1.78 reject the whole namespace.
- Prefer functions, generics and traits; use `macro_rules!` for syntax that functions cannot express (variadic arguments, DSLs, repetitive impls).
- Inside exported macros refer to items as `$crate::path::item` and to std as `::core::`/`::std::` so expansion works regardless of the caller's imports.
- `$x:pat` matches `A | B` in 2021; when a macro needs to split on `|`, use `pat_param`. `$e:expr` does **not** match `const { … }` blocks or `_` in 2021 (it does in 2024).
- A `macro_rules!` macro used in expression position whose body ends in `;` (`macro_rules! m { () => { 1; } }` then `let x = m!();`) is a **hard error since 1.91** (warning on 1.85: "trailing semicolon in macro used in expression position"). Since 1.99 the warning also fires for macros from other crates (`semicolon_in_expressions_from_non_local_macros`).[^1]
- `cfg_select!` (1.95) replaces the `cfg-if` crate only when the MSRV allows it.
- Unhygienic identifiers: local variables introduced by a `macro_rules!` body are hygienic, but items (`fn`, `struct`) and `$crate`-less paths are not.
- Procedural macros run arbitrary code at build time and add compile time; review new proc-macro dependencies like build scripts (supply chain).
- A missing fragment specifier (`$x` without `:kind`) in a macro matcher has been a hard error since 1.89.

#### API Design and Semver

Published library crates follow semver; the Cargo SemVer reference lists what is breaking.[^26] Review items:

- **Breaking**: removing or renaming public items; adding a required method to a public trait; adding a blanket impl; adding a public field to a struct with all-public fields (breaks struct literals and exhaustive patterns); adding an enum variant to an exhaustive enum; changing a type so it loses `Send`/`Sync`/`Unpin` (auto traits leak through public types, e.g. adding an `Rc` field); tightening generic bounds; raising the MSRV (by convention at least a minor bump — check the project's policy); bumping a **public dependency** (a dependency whose types appear in your API) to a new major version.
- **Not breaking**: adding a defaulted trait method (may cause method-resolution ambiguity downstream — "minor" per Cargo's guide), adding inherent methods, adding a variant to a `#[non_exhaustive]` enum, adding impls of local traits for local types.
- Use `#[non_exhaustive]` on public enums and config/error structs that may grow; provide constructors/builders instead of public fields.
- Seal traits that users should not implement.
- Return `impl Iterator<Item = T>` (or a named iterator type) instead of `Vec<T>` when callers usually iterate; but remember the 2021 lifetime-capture rules for RPIT.
- Mark constructors and pure functions `#[must_use]` where ignoring the result is a bug; builders' methods that return `Self` especially.
- Use `#[deprecated(since = "1.4.0", note = "use foo_v2 instead")]` for one release before removal.
- Public types should implement `Debug`; implement `Clone`, `PartialEq`, `Eq`, `Hash`, `Default`, `Display`, `From`, `serde` traits (behind a `serde` feature) where meaningful (C-COMMON-TRAITS).[^25]
- Run `cargo semver-checks` in CI for libraries.

#### Performance

- Measure first (`cargo build --release`, `perf`, `cargo flamegraph`, `criterion` benchmarks). `#[bench]` is nightly-only.
- **Debug builds are not representative.** Never judge performance or timing-sensitive behaviour from `cargo run` without `--release`.
- I/O: wrap `File`/`TcpStream` in `BufReader`/`BufWriter` — every unbuffered `write` is a syscall. `BufWriter` must be flushed (dropping it flushes but **ignores errors**; call `flush()` and handle the result). `println!` locks stdout per call; for bulk output use `let mut out = std::io::stdout().lock();` with `writeln!`.
- Allocation: `Vec::with_capacity`, `String::with_capacity`, reuse buffers (`clear()` keeps capacity), avoid `clone()`/`to_string()`/`format!` in hot loops, prefer `&str` keys with `HashMap::get` via `Borrow`.
- `collect::<Vec<_>>()` in the middle of a chain allocates; keep iterators lazy until the end.
- `Box<dyn Trait>` per element costs an allocation and an indirect call; an `enum` of known variants is often faster.
- `Rc`/`Arc` clone is cheap; `Arc` contention on a hot counter is not.
- `#[inline]` matters only across crates for non-generic functions; generic functions are already inlinable. `#[inline(always)]` needs a benchmark to justify it.
- Release profile knobs: `lto = "thin"`/`"fat"`, `codegen-units = 1`, `opt-level = 3` (default), `panic = "abort"` (smaller/faster, but changes semantics — see Panics), `debug = "line-tables-only"` for symbolised production backtraces. `strip = true` (1.59) removes symbols.
- Since 1.90 x86_64 Linux links with `lld` by default (faster links); if a project relies on GNU `ld`-specific linker scripts or flags, check the build.[^1]
- `HashMap` with SipHash is slower than FxHash/ahash for integer keys; acceptable only when keys are trusted.
- Large values moved by value (`[u8; 65536]` on the stack, big futures) cause memcpy and stack overflows in threads (default 2 MiB for spawned threads); `Box` them.

```rust
use std::io::{self, BufWriter, Write};

fn main() -> io::Result<()> {
    let stdout = io::stdout();
    let mut out = BufWriter::new(stdout.lock()); // one lock, buffered
    for i in 0..3 {
        writeln!(out, "line {i}")?;
    }
    out.flush()?; // surface write errors instead of losing them in Drop
    Ok(())
}
```

#### Testing

- Unit tests in `#[cfg(test)] mod tests` beside the code; integration tests in `tests/`; doctests in `///` examples (they compile and run — keep them correct; `no_run`/`ignore`/`compile_fail` annotations where appropriate).
- Test names describe behaviour: `parses_port_with_whitespace`, `rejects_zero_length`.
- Table-driven tests with a loop over cases and a case name in the assertion message.
- `#[should_panic(expected = "substring")]` — always with `expected`, otherwise any panic passes. Invalid `#[should_panic]` attributes are errors since 1.91.
- Tests returning `Result<(), E>` may use `?`.
- `assert_eq!(left, right, "context {x}")`; `assert!(matches!(v, Pattern))`, or `std::assert_matches!` with MSRV ≥ 1.96 (import it: `use std::assert_matches;`).
- `#[test]` placed on items where it has no meaning (trait methods, types) is an error since 1.93.
- `cargo test -- --no-capture` is the spelling since 1.88 (rejected by the 1.85 test harness); `--nocapture` is deprecated but still accepted without a warning — keep `--nocapture` in scripts that must run on older toolchains.
- Do not depend on `HashMap` iteration order, wall-clock time, or test execution order (tests run in parallel threads by default; global state such as env vars and the current directory races between tests).
- Async tests: `#[tokio::test]` (current-thread runtime by default; `flavor = "multi_thread"` to test `Send`/parallel behaviour). Use `tokio::time::pause()` / `#[tokio::test(start_paused = true)]` (feature `test-util`) instead of real sleeps.
- Concurrency: `loom` for lock-free code; Miri for `unsafe`; `proptest`/`quickcheck` for parsers and invariants; `cargo fuzz` (nightly) for untrusted-input parsers; `insta` for snapshot tests.
- CI matrix: stable + MSRV (`cargo +<msrv> check --all-targets --all-features`), `--no-default-features`, each feature alone for libraries with many features (`cargo hack --each-feature`).

```rust
pub fn parse_port(s: &str) -> Result<u16, std::num::ParseIntError> {
    s.trim().parse()
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn parse_port_cases() {
        let cases = [("80", Some(80)), (" 8080 ", Some(8080)), ("70000", None), ("", None)];
        for (input, want) in cases {
            assert_eq!(parse_port(input).ok(), want, "input {input:?}");
        }
    }

    #[test]
    #[should_panic(expected = "index out of bounds")]
    fn indexing_panics() {
        let v: Vec<u8> = Vec::new();
        let _ = v[std::hint::black_box(0)];
    }
}

fn main() { println!("{:?}", parse_port("443")); }
```

#### Cargo, Dependencies and Workspaces

##### Manifest essentials for a 2021 crate

```toml
[package]
name = "svc"
version = "0.3.1"
edition = "2021"
rust-version = "1.75"        # MSRV: CI must build with exactly this toolchain
license = "MIT OR Apache-2.0"

[dependencies]
serde = { version = "1", features = ["derive"], optional = true }
tokio = { version = "~1.53", features = ["rt-multi-thread", "macros", "net", "time"] } # LTS, MSRV 1.71

[features]
default = []
serde = ["dep:serde"]          # Cargo 1.60+: no implicit `serde` feature leaks

[lints.rust]                   # Cargo 1.74+ (ignored with a warning by older Cargo)
unsafe_code = "forbid"
unexpected_cfgs = { level = "warn", check-cfg = ["cfg(tokio_unstable)"] }

[lints.clippy]
await_holding_lock = "deny"
```

##### Features must be additive

Cargo unifies features: if any crate in the graph enables `foo/std`, every user of `foo` gets it. Therefore:

- A feature must only **add** API or functionality; never remove items or change behaviour incompatibly. Mutually exclusive features (`backend-a` vs `backend-b`) break when two dependents choose differently — use runtime configuration or a `compile_error!` with a clear message as last resort.
- `default-features = false` in your `Cargo.toml` does not guarantee the feature is off — another dependent can turn it on.
- `--all-features` must compile, and so should `--no-default-features`.
- Optional dependencies create an implicit feature with the dependency's name unless any feature references it with `dep:` (1.60). Use `dep:` to keep internal dependency names out of the public feature set; `serde?/std` (weak dependency feature, 1.60) enables `std` on `serde` only if `serde` is already enabled.[^9]
- Feature-gated code: `#[cfg(feature = "serde")]`. Since 1.80, misspelled feature names in `cfg` are reported by `unexpected_cfgs`; custom cfgs must be declared (`[lints.rust] unexpected_cfgs = { level = "warn", check-cfg = [...] }` or `cargo::rustc-check-cfg` in `build.rs`).
- Document features (`#[cfg_attr(docsrs, doc(cfg(feature = "x")))]` is a nightly docs.rs convention — keep it behind `docsrs`).

##### Resolver

- Single-package 2021 crates use resolver `"2"` automatically; **virtual workspaces must set `resolver = "2"`** (or `"3"`) explicitly (see edition section).
- With resolver 2, a dependency used both as a normal and as a build-dependency may be compiled twice with different features — expected, not a bug.
- Resolver `"3"` (Cargo 1.84+) prefers dependency versions compatible with `rust-version` (`incompatible-rust-versions = "fallback"`); it is the 2024 default and can be set in 2021 projects whose development toolchain is ≥ 1.84.[^37]

##### Workspaces (1.64+ inheritance)

```toml
[workspace]
members = ["crates/*"]
resolver = "2"

[workspace.package]
edition = "2021"
rust-version = "1.75"

[workspace.dependencies]
serde = { version = "1.0.200", default-features = false }

[workspace.lints.rust]
unsafe_code = "forbid"
```

Members use `edition.workspace = true`, `serde = { workspace = true, features = ["derive"] }`, and `[lints] workspace = true`. Note: on a 2021 member, `default-features = false` next to `workspace = true` is **ignored with a warning** when the workspace entry enables default features — only 2024 members can override it (Cargo 1.99).[^1] Put `default-features = false` in `[workspace.dependencies]` and opt in per member.

##### Lockfile and dependency hygiene

- Commit `Cargo.lock` for binaries and services (and, per current Cargo guidance, it is fine for libraries too); CI should use `--locked`.
- Mind the lockfile format vs MSRV (v4 needs Cargo 1.78+; see Version-Aware Review).
- Version requirements: `"1.2"` means `^1.2` (`>=1.2.0, <2.0.0`); `"=1.2.3"` pins exactly and causes resolution conflicts in libraries — avoid in libraries. `"*"` is rejected by crates.io.
- Git and path dependencies cannot be published; `[patch]` sections in a library are ignored by downstream users.
- Build scripts (`build.rs`) and proc macros execute arbitrary code at build time. Review new ones; emit `cargo:rerun-if-changed=` so they do not rerun on every build. The `cargo::` (double colon) directive syntax requires Cargo **1.77** — Cargo 1.73–1.76 rejects it with an error — so crates with an older MSRV must keep the single-colon `cargo:` form.
- Audit with `cargo audit` (RustSec database) or `cargo deny check` (advisories, licenses, bans, duplicate versions, sources) in CI.[^35]
- Since 1.88 Cargo garbage-collects its download cache automatically; since 1.99 incremental compilation is disabled by default when the `CI` environment variable is set.[^1]

#### Tooling: Clippy, Rustfmt, Rustdoc

- `cargo clippy --all-targets --all-features -- -D warnings` in CI, run with the **current** stable Clippy (it understands `rust-version` via `incompatible_msrv` and MSRV-gated suggestions such as `manual_let_else`). Since 1.97 the Cargo config `build.warnings = "deny"` is a stable alternative to `RUSTFLAGS=-D warnings` for local packages.
- Useful non-default Clippy lints for production code (verified to exist in Clippy 0.1.99): `undocumented_unsafe_blocks`, `multiple_unsafe_ops_per_block`, `unwrap_used`, `expect_used`, `indexing_slicing`, `arithmetic_side_effects`, `as_conversions`, `cast_possible_truncation`, `cast_sign_loss`, `string_slice`, `dbg_macro`, `todo`, `print_stdout`, `mem_forget`, `clone_on_ref_ptr`, `rc_buffer`, `large_futures`, `future_not_send`, `significant_drop_tightening`, `missing_errors_doc`, `missing_panics_doc`. Default-on lints worth denying: `await_holding_lock`, `await_holding_refcell_ref`, `let_underscore_future`, `significant_drop_in_scrutinee`.[^15]
- Configure lints in `[lints.clippy]` (Cargo 1.74+) or with crate attributes (`#![deny(clippy::unwrap_used)]`) for older MSRVs. Prefer `#[expect(clippy::lint, reason = "…")]` (1.81) over `#[allow]` for local exceptions — it fails once the exception is no longer needed.
- Rustfmt: `cargo fmt --check`; nightly-only options in `rustfmt.toml` (e.g. `imports_granularity`) are ignored on stable with only a warning, so they do not enforce anything in CI.
- Rustdoc: `cargo doc --no-deps`; `#![warn(missing_docs)]` for libraries; `RUSTDOCFLAGS="-D warnings"` catches broken intra-doc links. Doctests compile with the crate's edition (2021).
- `cargo fix` applies compiler suggestions; `cargo fix --edition` performs edition migrations (see Migration).

#### Security

##### Input handling

```rust
use std::path::{Component, Path, PathBuf};

// `Path::join` with an absolute path REPLACES the base, and `..` is not resolved:
//   Path::new("/srv/uploads").join("/etc/passwd")        == "/etc/passwd"
//   Path::new("/srv/uploads").join("../../etc/passwd")   == "/srv/uploads/../../etc/passwd"
//   ... and `.starts_with("/srv/uploads")` on the latter is TRUE (component-wise, no normalisation).
fn safe_join(base: &Path, user: &str) -> Option<PathBuf> {
    let rel = Path::new(user);
    if rel.components().any(|c| !matches!(c, Component::Normal(_))) {
        return None; // rejects "/abs", "..", "." (and Windows prefixes on Windows)
    }
    Some(base.join(rel))
}

fn main() {
    let base = Path::new("/srv/uploads");
    println!("{:?}", base.join("/etc/passwd"));
    println!("{:?}", base.join("../../etc/passwd").starts_with(base)); // true!
    println!("{:?} {:?}", safe_join(base, "a/b.txt"), safe_join(base, "../x"));
}
```

- For symlink-safe containment, canonicalise (`fs::canonicalize`) after joining and compare with the canonicalised base — and be aware of TOCTOU races; open with `O_NOFOLLOW`-style APIs (`cap-std`) for high-assurance code.
- `std::process::Command` does not invoke a shell: pass user data as separate `.arg()`s. `Command::new("sh").arg("-c").arg(format!("… {user}"))` is command injection. On Windows, `.bat`/`.cmd` argument escaping was fixed in 1.77.2 (CVE-2024-24576) and 1.81.0 (CVE-2024-43402) — build with a current compiler.[^23]
- SQL: bind parameters (`sqlx::query!("… WHERE id = $1", id)`, `diesel`), never `format!` into SQL.
- Deserialisation: set size/depth limits for untrusted input (body size limits in HTTP frameworks, `bincode` limits); `serde_json` has a default recursion limit (verified with serde_json 1.x: 127 nested arrays parse, 128 fail with "recursion limit exceeded"); do not disable it (`unbounded_depth`) for untrusted input. `#[serde(deny_unknown_fields)]` for strict configs.
- Never pre-allocate from untrusted lengths (see Collections); use `checked_*` arithmetic on offsets and sizes (see Integers).
- Regex: the `regex` crate guarantees linear-time matching; backtracking engines (`fancy-regex`, `pcre2`) are ReDoS risks on untrusted patterns or input. Compile regexes once (`LazyLock`/`OnceLock`), not per call.
- `std::fs::remove_dir_all` had a symlink race (CVE-2022-21658) fixed in 1.58.1.[^24]

##### Secrets and cryptography

- Do not `#[derive(Debug)]` on types holding secrets — it prints them in logs and panics. Implement `Debug` manually or use `secrecy::SecretString`; zero sensitive buffers with `zeroize`.
- Compare secrets in constant time (`subtle::ConstantTimeEq`, or the crypto library's verify function), never with `==`.
- Randomness for keys/tokens: `getrandom` / `rand::rngs::OsRng`; never a seeded PRNG or `HashMap` iteration order.
- Use `rustls` or `native-tls` with certificate verification on; flag `danger_accept_invalid_certs(true)` and custom verifiers that accept everything.
- Password hashing: `argon2`, `scrypt` or `bcrypt` — in `spawn_blocking` inside async code.

##### Supply chain

- New dependencies: check maintenance, download counts, `unsafe` usage, build scripts and proc macros (they run on developer machines and CI). Prefer few, well-known crates.
- `cargo audit`/`cargo deny` in CI; `cargo vet` or `cargo crev` for high-assurance projects.
- `Cargo.lock` with `--locked` builds; avoid wildcard or git dependencies in production.
- Unicode bidi control characters in source are rejected by deny-by-default lints since 1.56.1 (CVE-2021-42574).[^1]

#### Observability

- Use the `tracing` crate for structured, span-based diagnostics (or `log` for simple libraries); libraries emit events, applications install the subscriber (`tracing-subscriber`). Never initialise a global logger in a library.
- Prefer fields over interpolated strings: `tracing::info!(user_id = %id, "login")`.
- `#[tracing::instrument(skip(password), err)]` — `skip`/`skip_all` arguments that are large or secret; by default all arguments are recorded with `Debug`.
- Span guards: `let _guard = span.enter();` keeps the span active; `let _ = span.enter();` exits immediately (no lint catches it). **Do not hold `span.enter()` guards across `.await`** — use `.instrument(span)` on the future.
- Log errors once, at the boundary that handles them, with the full chain (`{:#}` with `anyhow`, or iterate `source()`); do not log-and-return at every layer.
- Panics: install a panic hook (or rely on `tracing-panic`/`sentry`) in services so panics in threads/tasks reach logs; check `JoinHandle`/`JoinError` results.
- Metrics: `metrics` or OpenTelemetry crates; label cardinality must be bounded (no user IDs as labels).
- Since 1.97 rustc uses the v0 symbol-mangling scheme by default; old debuggers/profilers may show mangled names — update tooling rather than downgrading.[^1]

#### Migration Notes

##### 2018 → 2021

1. On the 2018 edition, with a clean working tree, run `cargo fix --edition` (all targets and features you build: `cargo fix --edition --all-targets --all-features`).[^12]
2. Set `edition = "2021"` (and `resolver = "2"` in a virtual workspace root), then `cargo build`/`cargo test`.
3. Review what the tool changed. Verified on Cargo 1.99.1, starting from 2018 code:
   - `a.into_iter()` on an array where items were used as `&T` → `a.iter()`.
   - A `move` closure capturing a field of a `Send` wrapper → `{ let _ = &px; … }` (whole-variable capture is preserved).
   - `panic!("{}")` with a literal brace message → `panic!("{}", "{}")`.

   Per the edition guide it also rewrites:[^2]
   - Calls to crate-local `try_into`/`try_from`/`from_iter` that would become ambiguous → fully qualified syntax.
   - `ident"…"` in macro invocations → `ident "…"`.
   - `$x:pat` followed by `|` in macro matchers → `$x:pat_param`.
4. Remove the dummy `let _ = &x;` lines where drop order and auto traits do not matter.
5. Requires every toolchain in CI to be ≥ 1.56.

##### 2021 → 2024 (when the project decides to move)

Edition 2024 requires **rustc ≥ 1.85** — raising the MSRV is part of the migration. `cargo fix --edition` on a 2021 crate (verified on Cargo 1.99.1) rewrites:

- `extern "C" { … }` → `unsafe extern "C" { … }`; `#[no_mangle]` → `#[unsafe(no_mangle)]`.
- `if let … else` whose scrutinee has a significant destructor (e.g. a `MutexGuard`) → an equivalent `match`, preserving the 2021 drop timing (lint `if_let_rescope`).
- RPIT whose capture set would grow → adds `+ use<'a, T>` (lint `impl_trait_overcaptures`).
- Identifiers named `gen` → `r#gen`.
- `std::env::set_var(..)` → `unsafe { std::env::set_var(..) }` with a `// FIXME: Audit that the environment access only happens in single-threaded code.` comment.
- `$e:expr` → `$e:expr_2021` where a macro's behaviour would change (per the edition guide; not exercised in the test above).

Not automatically fixable — review by hand: tail-expression drop-order changes (`tail_expr_drop_order` only warns), never-type fallback (add type annotations), `static mut` references (now an error), unsafe operations inside `unsafe fn` (`unsafe_op_in_unsafe_fn` now warns), `Box<[T]>::into_iter()` semantics, the Cargo resolver becoming `"3"`, rustfmt's 2024 style edition, and doctest merging. Do not suggest this migration in a review unless the project has decided to raise its MSRV to 1.85 or later.[^4]

#### Removed or Changed Behaviour Across Compiler Versions (Same Edition)

A 2021 crate that compiled cleanly on an older compiler can change behaviour or fail on a newer one. When reviewing a toolchain bump, check these (all from the release notes;[^1] items marked "verified" were reproduced):

| Since | Change | Impact on 2021 code |
|---|---|---|
| 1.65 | `let_underscore_lock` deny-by-default | `let _ = m.lock().unwrap();` no longer compiles (verified) |
| 1.69 | references to packed fields are a hard error | E0793 (verified; 1.56 warns) |
| 1.74 | MIR-based drop tracking in `async` | `drop(guard)` before `.await` now makes the future `Send` (verified 1.65 vs 1.85) |
| 1.78 | debug-build precondition checks in `unsafe` std functions | latent UB now aborts in debug builds (verified) |
| 1.80 | `unexpected_cfgs` on by default | warnings for undeclared custom `cfg`s and misspelled features |
| 1.81 | new sort implementations | panic on non-total-order comparators (verified) |
| 1.81 | panics escaping `extern "C"` abort | callbacks that relied on unwinding into Rust now abort (verified 1.56 vs 1.85) |
| 1.83 | Cargo.lock v4 default | older Cargo (< 1.78) cannot read new lockfiles unless `rust-version` < 1.83 (verified) |

#### Production Review Checklist

##### Version and edition

- [ ] `edition = "2021"` confirmed; no 2024-only constructs (let chains outside match guards, reliance on 2024 temporary scopes or RPIT capture, `Future` without import)
- [ ] `rust-version` declared for libraries; every API/syntax used is ≤ MSRV (table above); CI builds with the MSRV toolchain
- [ ] Virtual workspace sets `resolver = "2"` (or `"3"`)
- [ ] Lockfile format and dependency MSRVs (e.g. Tokio 1.54 needs 1.85; LTS `~1.53` needs 1.71) compatible with the MSRV
- [ ] `[lints]` only relied upon with Cargo ≥ 1.74; `cargo::` build directives only with MSRV ≥ 1.77
- [ ] Production binaries built with a current stable (security fixes, e.g. CVE-2024-24576 / CVE-2024-43402 on Windows)

##### Correctness

- [ ] No `unwrap`/`expect`/indexing/slicing on untrusted input; panics documented under `# Panics`
- [ ] Integer arithmetic on external values uses `checked_*`/`saturating_*`; narrowing uses `try_from`, not `as`
- [ ] String slicing only on char boundaries; byte vs char length confusion absent
- [ ] Comparators implement total orders (1.81+ sort panics); `Eq`/`Hash`/`Ord` consistent with `PartialEq`/`PartialOrd`
- [ ] No reliance on `HashMap` iteration order
- [ ] RAII guards bound to named variables (`let _guard`), not `let _`
- [ ] No lock guard or `RefCell` borrow alive in an `if let … else`, `match` scrutinee or tail expression where re-locking happens (2021 temporary scopes)
- [ ] Closures that must keep a whole value alive or `Send` capture it explicitly (2021 disjoint captures)

##### Errors

- [ ] Library errors are typed, implement `Error + Send + Sync + 'static`, `#[non_exhaustive]` where they may grow
- [ ] Context added when propagating; no matching on error strings; no silently discarded `Result`s

##### Unsafe and FFI

- [ ] Every `unsafe` block has a `// SAFETY:` justification; `unsafe_op_in_unsafe_fn` enabled
- [ ] No `static mut` references, no `mem::uninitialized`, no `set_len` before initialisation, no unchecked UTF-8
- [ ] FFI types `#[repr(C)]`; `CString` outlives its pointer; callbacks catch panics
- [ ] Miri / sanitizers run on unsafe-heavy code

##### Concurrency and async

- [ ] No blocking calls on async worker threads (`spawn_blocking` / `rayon` for blocking and CPU work)
- [ ] No `std::sync::MutexGuard` / `RefCell` borrow across `.await`; `tokio::sync::Mutex` only where needed
- [ ] `select!` branches cancel-safe; long-lived futures pinned outside loops
- [ ] Spawned tasks owned (`JoinSet`/tracker), cancellable, and their panics observed
- [ ] Bounded channels; no unbounded per-request spawning
- [ ] Consistent lock ordering; atomics orderings justified
- [ ] No `std::env::set_var`/`remove_var` after threads start

##### Cargo and supply chain

- [ ] Features additive; `--all-features` and `--no-default-features` build
- [ ] `dep:` used for optional dependencies; custom cfgs declared for `unexpected_cfgs`
- [ ] `cargo audit`/`cargo deny` in CI; new build scripts and proc macros reviewed
- [ ] `--locked` builds; no wildcard/git dependencies in production

##### API (libraries)

- [ ] No accidental semver breaks (auto traits, public fields, new required trait methods, public dependency majors, MSRV)
- [ ] Public types implement `Debug` and the expected common traits; secrets do not derive `Debug`
- [ ] `cargo semver-checks` and docs (`missing_docs`, intra-doc links) clean

##### Tooling and observability

- [ ] `cargo fmt --check`, `cargo clippy -- -D warnings` (current stable Clippy) in CI
- [ ] Tests cover error paths; `should_panic` has `expected`; async tests use paused time
- [ ] `tracing` spans not entered across `.await`; secrets skipped in `#[instrument]`
- [ ] Release profile reviewed (`panic`, `lto`, `overflow-checks`, `debug`)

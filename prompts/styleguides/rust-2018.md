### Rust 2018 Edition (and Rust 2015): The Complete Production Review Guide

> **Edition**: Rust 2018 (`edition = "2018"` in `Cargo.toml`), introduced with **Rust 1.31.0 on 2018-12-06**.[^1] The same guide covers **edition 2015** crates — a `Cargo.toml` *without* an `edition` key is edition 2015.
> **Compiler**: any rustc from **1.31.0** up to the current stable **1.99.1 (2026-10-15)**. Rust 1.100.0 is in beta and scheduled for 2026-11-12; nightly is 1.101.[^2][^3]
> **Support status (October 2026)**: editions never expire — every current rustc still compiles 2015 and 2018 code, and crates of different editions link together freely. There are no LTS releases: fixes are backported only to the current stable and beta branches, so a project pinned to an old rustc gets no security or soundness fixes.[^4] The newest edition is **2024** (Rust 1.85.0, 2025-02-20); 2021 arrived with Rust 1.56.0 (2021-10-21).
> **Note**: This document is self-contained. Sections marked **[2015 ≠ 2018]** describe edition differences; **[NOT in 2018]** marks 2021/2024 semantics that a 2018 crate does *not* get; **(1.NN+)** marks compiler features stabilised after 1.31 that need at least that rustc.

Rust 2018 code bases are typically old: they were written between 2019 and 2021, often pin a toolchain, and carry the ecosystem of that era (`failure`, `error-chain`, `lazy_static`, futures 0.1 / tokio 0.1, `#[macro_use] extern crate`, `try!`, `mem::uninitialized`). A reviewer of such a crate must keep **two independent axes** apart:

| Axis | Set by | Controls | Example |
|---|---|---|---|
| **Edition** (2015 / 2018 / 2021 / 2024) | `edition` in `Cargo.toml` (per crate) | Syntax, keywords, name resolution, prelude contents, closure capture, a few method-resolution and drop-scope rules, Cargo's default feature resolver | `async` is a keyword in 2018 but an identifier in 2015; `array.into_iter()` yields `&T` in 2018 but `T` in 2021 |
| **Compiler / std version** (1.31 … 1.99) | `rust-toolchain(.toml)`, `rust-version`, CI image, `Cargo.lock` of the consumers | Which language features, std APIs, lints and Cargo features exist | `let … else` needs rustc 1.65+, `OnceLock` 1.70+, `LazyLock` 1.80+ — *in every edition, including 2018* |

Almost every language feature stabilised after 1.31 is available in edition 2018 as soon as the compiler supports it (GATs, `let … else`, const generics, `async fn` in traits, `if let` guards …). Only a small set is **edition-gated** to 2021 or 2024 (let chains, `c"…"` literals, disjoint closure captures, the 2021/2024 prelude additions, the 2024 drop-scope changes). The reviewer must check both axes before suggesting anything.

Global truths about Rust 2018 code:

- **Ownership is enforced at compile time.** Every value has one owner; references are either one `&mut` or any number of `&`. Edition 2018 has used the **non-lexical lifetimes (NLL)** borrow checker since 1.31; edition 2015 got it in 1.36 (warnings until 1.40, old checker removed in 1.63).[^5]
- **No exceptions.** Recoverable errors are `Result<T, E>` propagated with `?`; panics are for bugs and may abort instead of unwind (`panic = "abort"`).
- **`unsafe` is a contract, not a switch.** It permits a few extra operations (dereferencing raw pointers, calling `unsafe fn`, accessing `static mut` and extern statics, reading union fields, implementing `unsafe trait`); it does not turn off the borrow checker. Undefined behaviour (UB) anywhere invalidates the whole program.
- **Integer overflow panics in debug and wraps in release** (unless `overflow-checks` is set) — it is never UB.
- **Trait objects are written `dyn Trait`.** Bare `Box<Trait>` still compiles in 2015/2018 with a warning; it is a hard error from 2021.
- **The edition is a crate property.** A 2018 crate may depend on 2015, 2021 and 2024 crates — but only if the *compiler* is new enough to build them (a 2021 dependency needs rustc 1.56+, a 2024 dependency 1.85+).

#### Version-Aware Review: Determine Edition and Toolchain First

Before commenting on any Rust 2018/2015 code, establish **both** the edition and the minimum compiler. Never say "X is not available" or "use X instead" without checking the pinned version; say "not available in 1.NN" only when the project's pinned toolchain proves it.

##### Where the edition comes from

```toml
# Cargo.toml
[package]
name = "billing"
version = "0.4.2"
edition = "2018"          # absent => edition 2015 (!)
```

- **No `edition` key means 2015**, not "latest". Current Cargo warns: ``warning: Cargo.toml: `package.edition` is unspecified, defaulting to `2015` while the latest is `2024` ``. Review such a crate with the 2015 rules below.
- Each workspace member has its own edition; `edition.workspace = true` (workspace inheritance, Cargo 1.64+) takes it from `[workspace.package]`.
- Targets can override it (`[lib] edition = "2015"`), and `rustc --edition` is passed per crate, so a 2018 crate can depend on a 2015 or 2024 crate.
- rustfmt reads the edition from `Cargo.toml` via `cargo fmt`; a stand-alone `rustfmt` call without `--edition` (or `edition` in `rustfmt.toml`) formats as 2015.

##### Where the compiler version comes from

Check, in this order:

1. **`rust-toolchain.toml`** or the legacy **`rust-toolchain`** file (plain text, e.g. `1.41.1`) in the repository — rustup selects that toolchain for every `cargo`/`rustc` call in the directory. The TOML form needs rustup 1.23+.[^6]
2. **`rust-version = "1.NN"`** in `[package]` (the MSRV). Cargo **1.56+** refuses to build a package whose `rust-version` is newer than the active rustc; older Cargo prints `warning: unused manifest key: package.rust-version` and ignores it (verified on 1.31.0 and 1.56.0). Clippy also reads it and suppresses lints that would suggest newer APIs.
3. **CI configuration and Dockerfiles** (`rust:1.41-slim`, `dtolnay/rust-toolchain@1.56`, `toolchain: 1.46.0` in `actions-rs`), `clippy.toml` (`msrv = "1.40"`), and README "minimum supported Rust version" statements.
4. **`Cargo.lock`**: a lockfile with `version = 4` (the default written by Cargo **1.83+**) cannot be read by Cargo before 1.78 (`lock file version 4 was found, but this version of Cargo does not understand this lock file`, verified with 1.56.0). Current Cargo picks the newest format the declared `rust-version` can read (v4 from 1.83, v3 from 1.53, older formats below); a v3 lockfile is unreadable by Cargo 1.31 (`invalid serialized PackageId`, verified).[^7]

If nothing pins the toolchain, the crate is built with whatever stable the developer or CI has — assume a modern compiler for *availability* questions, but keep the **edition semantics** of 2018.

##### Review rules for the two axes

- **Edition questions** (Is `async` a keyword? Does `array.into_iter()` move? Is `TryFrom` in scope? Does the closure capture the whole struct? Is `panic!("{}")` a format string?) are answered by the `edition` key — **never** by the compiler version. A 2018 crate built with rustc 1.99 still has 2018 semantics.
- **Availability questions** (Can I use `let … else`, `OnceLock`, `std::thread::scope`, GATs?) are answered by the pinned compiler — **not** by the edition. With an MSRV of 1.31–1.64, `let … else` is unavailable even though nothing in edition 2018 forbids it.
- **Dependency questions** are answered by the dependencies' own `rust-version`/edition: an edition-2021 dependency requires rustc 1.56+, edition-2024 requires 1.85+. Many current crates require 1.70–1.85+ (October 2026, from crates.io metadata: tokio 1.54 → 1.85, serde_json 1.0.154 → 1.71, regex 1.13 → 1.65, anyhow 1.0.104 → 1.68, thiserror 2.0 → 1.77, once_cell 1.21 → 1.65).[^8] Recommending "upgrade to the latest X" on a project pinned to 1.41 breaks its build.
- When the MSRV is unknown, phrase advice conditionally: "on Rust 1.70+ prefer `std::sync::OnceLock` over `lazy_static!`".

#### Edition 2015 vs 2018

Edition 2018 is opted into with `edition = "2018"`. Everything below was compiled with `rustc --edition 2015` and `--edition 2018` on the same compiler (1.31.0, 1.56.0, 1.99.1).[^9]

##### Paths and the module system **[2015 ≠ 2018]**

| Item | Edition 2015 | Edition 2018 |
|---|---|---|
| `use a::b;` | `a` is resolved from the **crate root** | `a` is an **extern crate name** or a name **in scope** in the current module ("uniform paths", 1.32+); on 1.31 only extern crates, `crate::`, `self::`, `super::` |
| `::a::b` | crate root | extern crate `a` only |
| `crate::a::b` | crate root (1.30+) | crate root |
| `extern crate foo;` | **required** for every dependency | not needed — Cargo's `--extern` crates are in the *extern prelude*; still needed for sysroot crates such as `alloc` and `test`, and for `proc_macro` before 1.42 |
| Importing a `#[macro_export]` macro | `#[macro_use] extern crate foo;` | `use foo::mac;` (or still `#[macro_use]`) |
| `mod.rs` | `foo/mod.rs`; `foo.rs` + `foo/bar.rs` also accepted since 1.30 | both forms; `foo.rs` + `foo/` is the preferred layout |

```rust
// edition 2015: compiles; edition 2018: error[E0432] unresolved import `util`
mod util { pub fn hi() -> &'static str { "hi" } }
mod inner {
    use util::hi;                   // 2015: crate-relative; 2018: `util` is not in scope here
    pub fn call() -> &'static str { hi() }
}
fn main() { println!("{}", inner::call()); }
```

```rust
// both editions (1.31+): `crate::` is the portable spelling
mod util { pub fn hi() -> &'static str { "hi" } }
mod inner {
    use crate::util::hi;
    pub fn call() -> &'static str { hi() }
}
fn main() { println!("{}", inner::call()); }
```

```rust
// edition 2018, rustc 1.32+: uniform paths — `use` may name something in scope.
// rustc 1.31 rejects this ("imports can only refer to extern crate names passed with
// `--extern` on stable channel"); write `use self::util::hi;` for 1.31 compatibility.
mod inner {
    mod util { pub fn hi() -> &'static str { "hi" } }
    use util::hi;
    pub fn call() -> &'static str { hi() }
}
fn main() { println!("{}", inner::call()); }
```

A **leading `::`** changed meaning: `::util::hi()` is the crate-root `util` module in 2015 but "an extern crate named `util`" in 2018 (`error[E0433]: failed to resolve: could not find util in the list of imported crates`). `cargo fix --edition` rewrites these to `crate::util::hi()`.

Review points:

- In a 2015 crate, `use std::…` and `use some_dep::…` work only because the crate root has an implicit `extern crate std` and an explicit `extern crate some_dep;`. A missing `extern crate` in 2015 code is a compile error, not a style issue.
- In a 2018 crate, flag leftover `extern crate foo;` lines for ordinary dependencies (the `unused_extern_crates` lint in the `rust_2018_idioms` group reports them) — except for `extern crate alloc;` in `no_std` crates, `extern crate test;` for nightly benches, `extern crate self as name;`, and `extern crate proc_macro;` when the MSRV is below 1.42.[^10]
- A name that is both a local module and an extern crate is resolved differently by different compilers (see [Modules](#modules-paths-crates-and-visibility)); disambiguate with `crate::name` or `::name`.

##### `dyn Trait` and bare trait objects **[2015 ≠ 2018]**

`dyn Trait` syntax works in both editions (since 1.27). Bare trait objects (`Box<Trait>`, `&Trait`) still compile in 2015 and 2018 but emit `warning: trait objects without an explicit dyn are deprecated` on current compilers; they are a hard error (E0782) from edition 2021. In 2015, `dyn` is a contextual keyword (`let dyn = 1;` compiles); in 2018 it is a strict keyword.

```rust
// BAD (2015/2018: warning; 2021+: error[E0782])
trait Shape { fn area(&self) -> f64; }
fn total(shapes: &[Box<Shape>]) -> f64 { shapes.iter().map(|s| s.area()).sum() }
```

```rust
// GOOD (every edition, 1.27+)
trait Shape { fn area(&self) -> f64; }
fn total(shapes: &[Box<dyn Shape>]) -> f64 { shapes.iter().map(|s| s.area()).sum() }
```

`Box<dyn Trait>` means `Box<dyn Trait + 'static>`; `&'a dyn Trait` means `&'a (dyn Trait + 'a)`. Add `+ Send + Sync` explicitly when the object crosses threads.

##### Anonymous trait-method parameters **[2015 ≠ 2018]**

```rust
// edition 2015: compiles (warning "anonymous parameters are deprecated");
// edition 2018: syntax error "expected one of `:`, `@`, or `|`, found `)`"
trait Shape { fn scale(&self, f64) -> f64; }
```

Fix: `fn scale(&self, _: f64) -> f64;` (what `cargo fix --edition` writes) or, better, a real name.

##### New keywords **[2015 ≠ 2018]**

| Keyword | 2015 | 2018 |
|---|---|---|
| `dyn` | contextual (valid identifier) | strict keyword |
| `async`, `await` | identifiers | keywords (`async fn` usable since 1.39; in 2015 `async fn` is error E0670 "`async fn` is not permitted in Rust 2015") |
| `try` | identifier; `try!(…)` macro works | reserved keyword: `try!(…)` is an error ("use of deprecated `try` macro"); write `r#try!(…)` or, better, `?` |

Raw identifiers `r#name` (1.30+) let a 2018 crate call a 2015 crate's function named `async`, `await`, `dyn` or `try`.

```rust
// 2015: compiles (with a deprecation warning on current rustc); 2018: error
use std::num::ParseIntError;
fn parse(s: &str) -> Result<i32, ParseIntError> { let n = try!(s.parse::<i32>()); Ok(n) }
```

```rust
// every edition: `?` (1.13+) — the only form to accept in review
use std::num::ParseIntError;
fn parse(s: &str) -> Result<i32, ParseIntError> { let n = s.parse::<i32>()?; Ok(n) }
```

##### Non-lexical lifetimes (NLL) **[2015 ≠ 2018 on old compilers]**

Edition 2018 shipped NLL in 1.31; edition 2015 used the old lexical (AST) borrow checker until **1.36** (NLL "migrate mode": old-checker-accepted code that NLL rejects only warned), the warnings became **errors in 1.40** (2015) / **1.39** (2018), and migrate mode was removed in **1.63**.[^5] On every compiler from 1.36 on, both editions use NLL.

```rust
// rustc 1.31 --edition 2015: error[E0502]; --edition 2018 (and 2015 on 1.36+): OK
fn main() {
    let mut v = vec![1, 2, 3];
    let first = &v[0];
    println!("{}", first);
    v.push(4);              // the borrow `first` is no longer live
    println!("{:?}", v);
}
```

Review implication: old 2015 code often contains contortions (extra blocks, clones, `let tmp = …;` splits) that existed only to satisfy the lexical checker. They can be removed on 1.36+. Conversely, code that compiled on a pre-1.36 2015 compiler may be *rejected* by NLL because the old checker had soundness bugs; such errors on a toolchain upgrade are real bugs, not compiler regressions.

##### Macro `?` repetition (`$(…)?`) **[2015 ≠ 2018 before 1.37]**

The "at most once" macro repetition `$(…)?` became stable in **1.32 for edition 2018** and in **1.37 for edition 2015** (verified: 1.32.0 accepts it in 2018 and rejects it in 2015; 1.56.0 accepts it in 2015).[^11]

```rust
// edition 2018: rustc 1.32+; edition 2015: rustc 1.37+
macro_rules! sum {
    ($a:expr $(, $b:expr)?) => { $a $(+ $b)? };
}
fn main() { println!("{} {}", sum!(1), sum!(1, 2)); }
```

##### Other 2018 changes

- **`'_` anonymous lifetime and in-band elision in impl headers**: `impl fmt::Display for Wrapper<'_>`; `fn iter(&self) -> Iter<'_, T>`. Valid in both editions on 1.31+, but the 2018 idiom lint `elided_lifetimes_in_paths` (in `rust_2018_idioms`, allow-by-default) flags `fmt::Formatter` without `<'_>`.
- **`impl Trait`** (1.26), **`?` in `main`** (1.26), **`dyn`** (1.27), **`#[must_use]` on functions** (1.27), **`crate` visibility `pub(crate)`** (1.18), **raw identifiers** (1.30), **procedural macros** (attribute/function-like 1.30) are compiler features, available to 2015 crates on the same compiler.
- **`pub(in path)`** must start with `crate`, `self` or `super` in 2018 (`pub(in crate::net)`); 2015 accepted crate-relative `pub(in net)`.
- **Method calls on raw pointers to inference variables** (`tyvar_behind_raw_pointer`, e.g. `let p = &x as *const _; p.is_null()` where `_` is still unknown) are a hard error in 2018 and only a warning in 2015.
- **Cargo** (edition 2018 packages): an explicit `[[bin]]`/`[[example]]`/`[[test]]` entry no longer disables auto-discovery of the other targets; `src/{name}.rs` is no longer inferred as the path of a target without `path`; `cargo install` in the package directory requires `cargo install --path .`.[^9]

#### What a 2018 Crate Does NOT Get: Editions 2021 and 2024

A newer compiler does **not** give a 2018 crate 2021/2024 semantics. Each item below was compiled on rustc 1.99.1 with `--edition 2018`, `2021` and `2024`; the reviewer must apply the **2018 column**.[^12][^13]

##### Edition 2021 changes that do NOT apply to 2018 **[NOT in 2018]**

###### Closures capture whole variables, not disjoint fields

In 2018 a closure that mentions `s.a` captures **all of `s`**. This affects borrow checking, `Send`/`Sync` of the closure and **drop order**.

```rust
// edition 2018: error[E0502] cannot borrow `s.b` as mutable (the closure borrows all of `s`)
// edition 2021: compiles (the closure borrows only `s.a`)
struct S { a: String, b: String }
fn main() {
    let mut s = S { a: "a".into(), b: "b".into() };
    let c = || println!("{}", s.a);
    s.b.push('!');
    c();
}
```

```rust
// Drop order differs: 2018 prints "closure done, drop a, drop b, end of main";
// 2021 prints "closure done, drop a, end of main, drop b".
struct Noisy(&'static str);
impl Drop for Noisy { fn drop(&mut self) { println!("drop {}", self.0); } }
struct Pair { a: Noisy, b: Noisy }
fn main() {
    let p = Pair { a: Noisy("a"), b: Noisy("b") };
    {
        let c = move || { let _x = &p.a; };
        c();
        println!("closure done");
    } // 2018: the closure owned all of `p`
    println!("end of main");
}
```

Review: in 2018, `move` closures passed to `thread::spawn` move the **entire** struct even if they only touch one field; to move just one field, bind it first (`let a = s.a; move || use(a)`). Do not suggest 2021-style "the closure only borrows that field" reasoning.

###### `array.into_iter()` yields references

`IntoIterator` for arrays by value exists since **1.53** in every edition, so `for x in [a, b]` moves the elements. But the *method-call* syntax `array.into_iter()` in 2015/2018 still resolves to `(&array).into_iter()` and yields `&T` (with the `array_into_iter` warning); only 2021+ yields `T`.

```rust
// edition 2018 on rustc 1.99: compiles, `x` is &i32, warning:
// "this method call resolves to `<&[T; N] as IntoIterator>::into_iter` (due to backwards compatibility)"
fn main() {
    let a = [1, 2, 3];
    for x in a.into_iter() { let _r: &i32 = x; }
}
```

```rust
// edition 2018, rustc 1.53+: by-value iteration over an array
fn main() {
    let a = [String::from("a"), String::from("b")];
    for s in a { let owned: String = s; println!("{}", owned); }        // 1.53+
    let b = [1, 2, 3];
    let v: Vec<i32> = b.iter().copied().collect();                       // any version (copied: 1.36+)
    println!("{:?}", v);
}
```

In 2018 write `a.iter()` when references are meant; use `IntoIterator::into_iter(a)` or `for x in a` (1.53+) when values are meant. The same backwards-compatibility hack applies to `Box<[T]>::into_iter()` (yields `&T` until edition 2024).

###### `TryFrom`, `TryInto` and `FromIterator` are not in the prelude

```rust
// edition 2018: error[E0599] no method named `try_into` found (needs `use std::convert::TryInto;`)
// edition 2021: compiles
fn main() { let x: Result<u8, _> = 300i32.try_into(); println!("{:?}", x.is_err()); }
```

```rust
// edition 2018, rustc 1.34+
use std::convert::{TryFrom, TryInto};
use std::iter::FromIterator;
fn main() {
    let a: Result<u8, _> = 300i32.try_into();
    let b = u8::try_from(200i32);
    let v = Vec::from_iter(0..3);       // without the `use`: error[E0599] in 2018
    println!("{:?} {:?} {:?}", a.is_err(), b, v);
}
```

A 2018 crate that defines its own `try_into`/`try_from` methods or traits is unaffected by name clashes that the 2021 prelude would create — but a reviewer suggesting "just call `.try_into()`" must add the `use`.

###### `panic!` with a single argument is not a format string

In 2015/2018, `panic!(x)` with one argument passes `x` through **unformatted** — `panic!("{}")` panics with the literal message `{}`, and `panic!("value {x}")` panics with the literal text `value {x}` (the implicit-capture syntax is ignored). Any type can be the payload (`panic!(42)`, `panic!(my_struct)`). In 2021+ the first argument is always a format string. The same applies to `assert!(cond, msg)` and `debug_assert!`. Current compilers warn (`non_fmt_panics`: "panic message contains an unused formatting placeholder").

```rust
// edition 2018: the payload is the literal "x = {x}"; edition 2021: "x = 5"
fn main() {
    std::panic::set_hook(Box::new(|info| {
        let p = info.payload();
        let msg = p.downcast_ref::<&str>().map(|s| s.to_string())
            .or_else(|| p.downcast_ref::<String>().cloned());
        println!("msg={:?}", msg);
    }));
    let x = 5;
    let _ = std::panic::catch_unwind(|| { panic!("x = {x}"); });
}
```

Review rule for 2018: single-argument `panic!`, `assert!(c, "…{}…")` and `unreachable!("{}")` must be written with explicit arguments (`panic!("x = {}", x)`), or with `panic!("{}", msg)` when forwarding a message string. `std::panic::panic_any(payload)` (1.51+) is the explicit way to panic with a non-string payload.

###### Or-patterns in `macro_rules!` `$p:pat`

Top-level or-patterns (`A | B`) are valid patterns since 1.53, but in 2015/2018 a `$p:pat` macro fragment does **not** match a top-level `|` (`error: no rules expected the token |`). 2021 changed `:pat` to accept it (the 2018 behaviour is available as `:pat_param`).

```rust
// edition 2018: error "no rules expected `|`"; 2021: prints true
macro_rules! is { ($e:expr, $p:pat) => { match $e { $p => true, _ => false } } }
fn main() { println!("{}", is!(3, 1 | 3)); }
```

###### Reserved prefixes are not reserved

In 2021+, `ident#`, `ident"…"` and `ident'…'` are reserved tokens (enabling `c"…"`, `cr"…"`, `k#…`). In 2018, `z#x` inside a macro call is three tokens `z`, `#`, `x`, and `c"hi"` is a syntax error — **C-string literals `c"…"` (1.77) are 2021+ only**; use `CStr::from_bytes_with_nul(b"hi\0")` (1.10+) or `CString::new`.

###### Warnings that are hard errors in 2021

`bare_trait_objects` (`Box<Trait>`) and `ellipsis_inclusive_range_patterns` (`0...9` in patterns) only **warn** in 2018; they are errors (E0782 / E0783) in 2021. Fix them anyway — `cargo fix --edition` will need to.

###### Cargo: the default feature resolver is `"1"`

An edition-2018 package (and a virtual workspace without `resolver`) uses **feature resolver 1**: features requested by *any* use of a dependency — normal, `[build-dependencies]`, `[dev-dependencies]`, proc-macro dependencies, and target-specific dependencies for *other* platforms — are **unified** into one build. Edition 2021 implies `resolver = "2"` (Cargo 1.51+), which keeps build/dev/proc-macro/inactive-target features separate.[^14]

Verified with a workspace where `app` depends on `dep` without features and on `dep` with `features = ["std"]` as a build-dependency: with edition 2018 and no `resolver` key the **runtime** binary is built with `std` enabled; with `resolver = "2"` it is not.

Consequences to look for in 2018 crates:

- `no_std`/embedded/WASM builds that fail or bloat because a build script, proc-macro or dev-dependency enables `std` (or `default` features) on a shared dependency.
- Tests passing only because a dev-dependency enabled a feature the library forgot to enable for itself.
- Slow builds because Windows-only or macOS-only dependency features are compiled everywhere.

`resolver = "2"` can be set on a 2018 package (`[package] resolver = "2"`, Cargo 1.51+) or must be set in `[workspace]` for a virtual workspace. Current Cargo warns: `virtual workspace defaulting to resolver = "1" despite one or more workspace members being on edition 2021`. Cargo before 1.51 ignores the key with `warning: unused manifest key: package.resolver` (verified on 1.31.0).

##### Edition 2024 changes that do NOT apply to 2018 **[NOT in 2018]**

| 2024 change (rustc 1.85+) | Behaviour in a 2018 crate |
|---|---|
| **Let chains** `if let Some(x) = a && x > 2` (1.88, 2024 only) | Error: "let chains are only allowed in Rust 2024 or later" — on every compiler. Use nested `if let`, `match`, or `if let (Some(x), true) = …` patterns |
| **`if let` scrutinee temporaries dropped before `else`** | In 2018 the temporaries of `if let Some(_) = *m.lock().unwrap() { … } else { … }` live through the **`else` block** — locking `m` again in `else` deadlocks (verified: `try_lock()` in the `else` branch reports the lock still held in 2018/2021, free in 2024) |
| **Tail-expression temporaries dropped before locals** | In 2018 a temporary in a block's tail expression (e.g. `cell.borrow().len()`) outlives the block's locals; this can produce "does not live long enough" errors and late `RefCell`/`Mutex` releases |
| **RPIT captures all in-scope lifetimes** | In 2018 `fn f(v: &Vec<u32>) -> impl Fn() -> usize` does **not** capture the borrow of `v` (2024 does, and then rejects using `v` mutably while the closure lives); when a 2018 RPIT *must* borrow, it needs `+ 'a` |
| **`unsafe extern "C" { … }` required, `#[unsafe(no_mangle)]` required** | Plain `extern "C" { … }` and `#[no_mangle]` compile; `unsafe extern` and `#[unsafe(...)]` attributes are *accepted* in 2018 on 1.82+ |
| **`unsafe_op_in_unsafe_fn` warns** | The body of an `unsafe fn` is one big unsafe block in 2018 — unsafe operations inside it are silent; enable `#![warn(unsafe_op_in_unsafe_fn)]` (lint available 1.52+) |
| **`static_mut_refs` is deny-by-default** | `&STATIC_MUT` only **warns** in 2018 (warning "creating a shared reference to mutable static") — still UB-prone |
| **`std::env::set_var` / `remove_var` are `unsafe fn`** | Safe to call in 2018 — but still unsound with concurrent `getenv` from other threads (e.g. C libraries); treat it as unsafe in review |
| **Never-type fallback to `!`** | Fallback to `()` on every stable compiler up to 1.99.1; code depending on it is a **deny-by-default** error on rustc 1.92+ even in 2018. Exception ahead: Rust 1.100 (beta, due 2026-11-12) stabilises `!` and switches the fallback to `!` in **all** editions, 2018 included (see "Newer compilers breaking old 2018 code") |
| **`Future` and `IntoFuture` in the prelude** | Not in scope: `fn f() -> impl Future<Output = u8>` needs `use std::future::Future;` (error E0405 otherwise) |
| **`Box<[T]>::into_iter()` yields `T`** | Yields `&T` (warning `boxed_slice_into_iter`) |
| **Match-ergonomics reservations**: `mut`/`ref` on a binding inside an implicitly borrowing pattern is an error | `let [x, mut y] = &[1u8, 2u8];` compiles and silently makes `y` a `u8` **by value** (the `mut` resets the binding mode) while `x` is `&u8` (verified; error "cannot mutably bind by value within an implicitly-borrowing pattern" in 2024) |
| **`gen` is a reserved keyword** | `gen` is an ordinary identifier |
| **`expr` macro fragment also matches `const { … }` and `_`** | `$e:expr` keeps the 2021 behaviour |
| **Cargo: `resolver = "3"` (MSRV-aware) default, `dev_dependencies`/`build_dependencies`/`crate_type` spellings rejected, `default-features` inheritance rules** | Resolver 1 default; underscore spellings still accepted with the warning "`dev_dependencies` is deprecated in favor of `dev-dependencies` and will not work in the 2024 edition" |
| **rustfmt "style edition 2024"** (version-sorting of imports etc.) | Style edition 2015 rules |

#### Do Not Use or Recommend

##### Edition-gated features — never valid in a 2018 (or 2015) crate, on any compiler

- **Let chains** — `if let Some(x) = a && cond`, `while let … && …` (2024 only, 1.88).
- **`c"…"` / `cr"…"` C-string literals** (2021+, 1.77) and **raw lifetimes `'r#name`** (2021+, 1.83; a syntax error in 2018 on 1.99.1, verified).
- **Calling `.try_into()`, `.try_from()`, `Vec::from_iter` without `use`** — the 2021 prelude additions (`TryFrom`, `TryInto`, `FromIterator`) are not in the 2018 prelude.
- **Naming `Future`/`IntoFuture` without `use std::future::Future;`** (2024 prelude).
- **Relying on disjoint closure captures** (2021) — "the closure only captures `self.field`" is false in 2018.
- **Expecting `array.into_iter()` or `boxed_slice.into_iter()` to yield values** (2021 / 2024).
- **Implicit format strings in single-argument `panic!`/`assert!`** (`panic!("{x}")` prints `{x}` literally in 2018).
- **`$p:pat` matching `A | B`** in `macro_rules!` (2021).
- **`gen` blocks** (nightly; `gen` is reserved only in 2024), **`unsafe extern` / `#[unsafe(…)]` as *requirements*** (they are optional in 2018 on 1.82+; do not flag their absence as an error).
- **Edition-2024 drop-scope reasoning** (`if let` temporaries dropped before `else`, tail-expression temporaries dropped before locals).
- **Resolver-2 feature isolation** without an explicit `resolver = "2"`.

#### Newer Compilers Breaking Old 2018 Code

Upgrading the *compiler* (not the edition) of an old crate is usually smooth, but these changes break or alter real 2018 code. A reviewer seeing a toolchain bump should look for them.[^2]

- **Never-type fallback (1.92)**: `dependency_on_unit_never_type_fallback` and `never_type_fallback_flowing_into_unsafe` are **deny-by-default in every edition**. Code compiled on 1.85 with a warning now fails:

```rust
// rustc 1.85 --edition 2018: OK with warning "this function depends on never type fallback being `()`"
// rustc 1.99 --edition 2018: error (deny-by-default)
fn create<T: Default>() -> Result<T, ()> { Ok(T::default()) }
fn run() -> Result<(), ()> { create()?; Ok(()) }
fn main() { println!("{:?}", run()); }
```

  Fix: name the type — `create::<()>()?;`. The annotation also keeps the code correct on Rust 1.100 (in beta, due 2026-11-12; not executed here), which stabilises the never type and makes the fallback `!` in every edition, including 2018.[^21]

- **Trailing semicolons in expression macros (1.91)**: `semicolon_in_expressions_from_macros` is deny-by-default; `macro_rules! one { () => { 1; } }` used as `let x = one!();` compiled silently on 1.31, warned on 1.85, and fails on 1.99. Since 1.99 the lint also fires for macros from other crates (`semicolon_in_expressions_from_non_local_macros`, warn).
- **`time` crate before 0.3.35 (1.80)**: new `FromIterator for Box<str>` impls broke type inference in `time` ≤ 0.3.34 — old lockfiles fail to build on 1.80+; `cargo update -p time` (needs a compiler that the newer `time` supports).
- **`unexpected_cfgs` (1.80)**: Cargo passes `--check-cfg`; `#[cfg(feature = "typo")]`, `cfg(nightly)`, `cfg(tarpaulin)` etc. warn. Declare custom cfgs with `[lints.rust] unexpected_cfgs = { level = "warn", check-cfg = ['cfg(nightly)'] }` or in `build.rs` with `cargo::rustc-check-cfg` (the `cargo::` prefix needs Cargo 1.77; `cargo:rustc-check-cfg` single-colon works with older Cargo).
- **Panic in `extern "C"` functions aborts (1.81)**: unwinding out of an `extern "C" fn` was UB that "worked" (verified: on 1.56 `catch_unwind` caught a panic raised inside an `extern "C" fn`; since 1.81 the process aborts with "panic in a function that cannot unwind"). Callbacks passed to C must catch panics themselves, or use `extern "C-unwind"` (1.71).
- **Sorting with an inconsistent `Ord`/comparator (1.81)**: the new sort implementations may **panic** when the comparison is not a total order (e.g. `partial_cmp(..).unwrap()` on NaN-containing floats, or comparators that are not transitive). Previously the result was an unspecified order.
- **`#![deny(warnings)]` in library code**: every new deprecation (1.99 legacy constants, 1.97 `std::char`) or lint turns into a build failure for downstream users on a newer compiler. Flag `#![deny(warnings)]` in published crates; use `RUSTFLAGS="-D warnings"` in CI instead.
- **Float→int casts (1.45)** changed from UB to saturating: code that "worked" on ≤ 1.44 can produce different values (verified: a runtime `300.7_f32 as u8` gave `44`, `80` or `192` on 1.31/1.44 depending on the build — and `255` when constant-folded — but always `255` on 1.45+; `NaN as i32` gave `-2147483648` on 1.44 and is `0` on 1.45+).
- **`#[bench]` without `#![feature(test)]`** is a hard error since 1.88 (future-incompat lint since 1.77).
- **`lld` default linker on `x86_64-unknown-linux-gnu` (1.90)**: linker-script or `-C link-arg` hacks written for GNU `ld` may behave differently; `-C linker-features=-lld` reverts to the system linker.[^15]
- **Cargo**: lockfile v4 written by Cargo 1.83+ is unreadable by Cargo < 1.78 (Cargo 1.99.1 writes v3 while `rust-version` is below 1.83 — verified with `"1.60"` and `"1.82"`; with `"1.83"` or without `rust-version` it writes v4) — a developer running `cargo update` with a new toolchain can break a CI job pinned to an old one; Cargo 1.99 disables incremental compilation by default when `CI` is set.
- **NLL soundness fixes**: pre-1.36 2015 code accepted by the AST borrow checker may be rejected — the error is a real bug.

#### Modules, Paths, Crates and Visibility

##### Idiomatic 2018 layout

```text
Cargo.toml          # edition = "2018", rust-version = "1.NN" (honoured by Cargo 1.56+)
src/lib.rs          # library root: `pub mod`, re-exports, crate docs
src/main.rs         # thin binary: parse args, call into the library, map errors to exit codes
src/net.rs          # `mod net;` — preferred over src/net/mod.rs in 2018
src/net/tcp.rs      # `mod tcp;` inside net.rs
tests/api.rs        # integration tests (separate crates, public API only)
benches/, examples/
```

- `use` order: `std`/`core`/`alloc`, external crates, then `crate::`/`super::`/`self::` — rustfmt keeps groups as written; separate them with blank lines.
- Prefer `crate::` absolute paths for cross-module imports; `super::` only for the parent (common in `#[cfg(test)] mod tests { use super::*; }`).
- `pub(crate)` for crate-internal items; `pub` only for the API. A `pub` item in a private module is unreachable from outside unless re-exported, which makes the intended API unclear — the allow-by-default `unreachable_pub` lint suggests `pub(crate)` for such items.
- Glob imports (`use foo::*`) only for preludes and test modules.
- A crate-root `mod log;` next to the `log` dependency: `use log::info;` at the root is error E0659 "`log` is ambiguous" on older compilers (verified on 1.31.0, 1.56.0 and 1.65.0), while compilers since 1.72 ("remove artificial import ambiguity errors") silently pick the local module (verified 1.85.0–1.99.1) — and inside a submodule `log::` means the extern crate. Write `crate::log` or `::log` explicitly, or rename the module.

##### Re-exports and public dependencies

- Types from dependencies that appear in your public API (`pub fn f() -> reqwest::Client`) make that dependency's major version part of **your** SemVer contract. Re-export it (`pub use reqwest;`) or wrap it.
- `#[doc(inline)]`/`pub use self::inner::Type;` for flattening; keep the module tree an implementation detail.

#### Ownership, Borrowing and Lifetimes

##### Rules the reviewer checks

- Take `&str`, `&[T]`, `&Path`, `impl AsRef<Path>` in parameters, not `&String`, `&Vec<T>`, `&PathBuf` (clippy `ptr_arg`).
- Return owned values (`String`, `Vec<T>`) from constructors and builders; return borrowed data only when it is tied to `self`.
- `clone()` to satisfy the borrow checker is acceptable for small/`Rc`/`Arc` values; repeated clones of large `String`/`Vec` values in loops are a performance finding.
- `Rc<RefCell<T>>` graphs: look for reference cycles (memory leak) — use `Weak` for back-pointers.
- `'static` bounds on public generics (`T: 'static`) are often unnecessary and over-restrictive, except for `thread::spawn`, `Box<dyn Any>` and global registries.
- `&mut` aliasing via `unsafe` (two `&mut` to the same data) is UB even if never "used at the same time".

##### NLL-era idioms

```rust
// edition 2018, rustc 1.31+: one hash lookup per word through the entry API
use std::collections::HashMap;
fn count_words(text: &str) -> HashMap<&str, usize> {
    let mut counts = HashMap::new();
    for w in text.split_whitespace() {
        *counts.entry(w).or_insert(0) += 1;
    }
    counts
}
fn main() { println!("{:?}", count_words("a b a").get("a")); }
```

NLL still rejects the "conditional return of a borrow" pattern (Polonius problem case #3):

```rust
// does not compile on any stable rustc (1.31–1.99: error[E0502]): the borrow returned from the `if`
// is treated as live for the rest of the function
use std::collections::HashMap;
fn get_or_insert(map: &mut HashMap<u32, String>, k: u32) -> &String {
    if let Some(v) = map.get(&k) { return v; }
    map.insert(k, String::new());
    map.get(&k).unwrap()
}
```

```rust
// GOOD: use the entry API (rustc 1.31+)
use std::collections::HashMap;
fn get_or_insert(map: &mut HashMap<u32, String>, k: u32) -> &String {
    map.entry(k).or_insert_with(String::new)
}
fn main() { let mut m = HashMap::new(); println!("{:?}", get_or_insert(&mut m, 1)); }
```

##### Lifetime elision and `'_`

```rust
// edition 2018 idiom: make hidden lifetimes visible with '_ (rust_2018_idioms lint group)
use std::fmt;
struct Name<'a>(&'a str);
impl fmt::Display for Name<'_> {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result { write!(f, "{}", self.0) }
}
fn first_word(s: &str) -> std::str::SplitWhitespace<'_> { s.split_whitespace() }
fn main() { println!("{} {:?}", Name("x"), first_word("a b").next()); }
```

With `#![warn(rust_2018_idioms)]`, `fmt::Formatter` without `<'_>` reports "hidden lifetime parameters in types are deprecated" and a leftover `extern crate core;` reports "unused extern crate" (verified on 1.99.1).

##### `impl Trait` that borrows (RPIT capture rules in 2018)

In editions before 2024, a return-position `impl Trait` captures **type** parameters but **not** lifetime parameters unless they appear in the bounds. An iterator that borrows its argument needs an explicit `+ 'a`:

```rust
// edition 2018, rustc 1.31+
fn evens<'a>(v: &'a [u32]) -> impl Iterator<Item = u32> + 'a {
    v.iter().cloned().filter(|x| x % 2 == 0)
}
fn main() { println!("{:?}", evens(&[1, 2, 4]).collect::<Vec<_>>()); }
```

Without `+ 'a` the code fails with "hidden type … captures lifetime that does not appear in bounds". The `+ 'a` trick over-constrains when there are several lifetimes; the precise form `impl Iterator<Item = u32> + use<'a>` needs 1.82.

#### Error Handling

##### Library errors: typed enums implementing `std::error::Error`

```rust
// edition 2018, rustc 1.31+ (no external crates)
use std::error::Error;
use std::fmt;
use std::io;
use std::num::ParseIntError;

#[derive(Debug)]
pub enum ConfigError {
    Io(io::Error),
    BadPort { line: usize, source: ParseIntError },
    Missing(&'static str),
}

impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            ConfigError::Io(_) => write!(f, "cannot read config"),
            ConfigError::BadPort { line, .. } => write!(f, "invalid port on line {}", line),
            ConfigError::Missing(key) => write!(f, "missing key `{}`", key),
        }
    }
}

impl Error for ConfigError {
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        match self {
            ConfigError::Io(e) => Some(e),
            ConfigError::BadPort { source, .. } => Some(source),
            ConfigError::Missing(_) => None,
        }
    }
}

impl From<io::Error> for ConfigError {
    fn from(e: io::Error) -> Self { ConfigError::Io(e) }
}

pub fn parse_port(line_no: usize, s: &str) -> Result<u16, ConfigError> {
    s.trim().parse().map_err(|e| ConfigError::BadPort { line: line_no, source: e })
}

fn main() {
    let e = parse_port(3, "80x").unwrap_err();
    println!("{} (caused by: {})", e, e.source().unwrap());
}
```

Review rules:

- **Do not implement `description()` or `cause()`**; implement `Display` and `source()` (1.30+). `description` warns since 1.42.
- **`Display` should not repeat the source's message** when `source()` returns it — reporters print the chain and the text would appear twice. Pick one: include the inner message in `Display` *or* return it from `source()`.
- `#[derive(Debug)]` on every error type; `Error` requires `Debug + Display`.
- Errors that cross threads or go into `Box<dyn Error>` should be `Send + Sync + 'static`. Storing `Rc` or non-`Send` handles in an error type is a finding.
- Public error enums: add `#[non_exhaustive]` (1.40+) so new variants are not breaking; on older MSRV use a hidden variant.
- `thiserror` derives exactly this boilerplate. **Check its MSRV**: thiserror 2.x declares `rust-version = 1.77` (October 2026 release 2.0.21); thiserror 1.x supported much older compilers. Pin the major version that the toolchain supports.

##### Applications: `Box<dyn Error + Send + Sync>` or `anyhow`

```rust
// edition 2018, rustc 1.31+: `?` in main (1.26+) and boxed errors
use std::error::Error;
use std::fs;

type AppResult<T> = Result<T, Box<dyn Error + Send + Sync + 'static>>;

fn read_port(path: &str) -> AppResult<u16> {
    let text = fs::read_to_string(path)?;           // io::Error -> Box<dyn Error>
    let port = text.trim().parse::<u16>()?;         // ParseIntError -> Box<dyn Error>
    Ok(port)
}

fn main() -> AppResult<()> {
    match read_port("/nonexistent/port.txt") {
        Ok(p) => println!("port {}", p),
        Err(e) => eprintln!("error: {}", e),
    }
    Ok(())
}
```

- `fn main() -> Result<(), E>` prints `Error: {:?}` (the **Debug** form) and exits with code 1; for user-facing messages, handle the error in `main` and call `std::process::exit` (or return `ExitCode`, 1.61+).
- `anyhow` (current releases need 1.68) adds context (`.context("reading config")`) and backtraces; `anyhow` 1.0.x releases from the 2019–2022 era support older compilers — check the lockfile.
- **`failure`**: unmaintained since 2020 and unsound (RUSTSEC-2019-0036). `failure::Error` does not implement `std::error::Error`, so it does not compose with `?` into `Box<dyn Error>`. Migrate to `std::error::Error` + `thiserror`/`anyhow`.
- **`error-chain`**: macro-generated error types, no releases since 2020; migrate the same way.

##### Panics vs errors

- `unwrap()`/`expect()` in library code on data that comes from outside (I/O, parsing, user input, network) is a bug — return `Result`.
- `expect("reason")` is acceptable for invariants; the message should state the invariant ("config validated in load()"), not the action ("failed to get value").
- `unwrap()` on `Mutex::lock()` is the accepted idiom (propagates poisoning as a panic); see Concurrency.
- Never `panic!` across an FFI boundary (see Unsafe).

##### `?` details

- `?` converts with `From::from`; a missing `From` impl gives "the trait `From<X>` is not implemented for `Y`".
- `?` on `Option` in a function returning `Option` works (1.22+); mixing `Option` and `Result` needs `.ok_or(..)?` / `.ok()?`.
- `?` in closures returns from the **closure**, not the enclosing function.
- `NoneError`-style `?` from `Option` into `Result` does not exist on stable.

#### Option and Result Idioms

```rust
// edition 2018, rustc 1.40+ (as_deref; everything else 1.31+)
use std::collections::HashMap;
fn lookup(env: &HashMap<String, String>, key: &str) -> Option<u16> {
    env.get(key)
        .map(|s| s.trim())
        .filter(|s| !s.is_empty())          // 1.27
        .and_then(|s| s.parse().ok())
}
fn name(o: &Option<String>) -> &str { o.as_deref().unwrap_or("anonymous") }   // as_deref: 1.40
fn main() {
    let mut env = HashMap::new();
    env.insert("PORT".to_string(), " 8080 ".to_string());
    println!("{:?} {}", lookup(&env, "PORT"), name(&None));
}
```

- `unwrap_or(expensive())` evaluates eagerly — use `unwrap_or_else(|| expensive())` (clippy `or_fun_call`).
- `map_or(false, |x| …)` is fine on old compilers; `is_some_and` (1.70) / `is_none_or` (1.82) only on new ones.
- `if let Some(x) = opt { … } else { return … }` is the pre-1.65 spelling of `let Some(x) = opt else { return … };`.
- `Option<&T>::cloned()`/`copied()` (`copied` 1.35) instead of `map(|x| x.clone())`.
- `ok_or_else(|| Error::new(..))` instead of `ok_or(Error::new(..))` when building the error allocates.
- `Result<T, String>` in public APIs loses structure — prefer typed errors.
- `transpose()` (1.33) turns `Option<Result<T, E>>` into `Result<Option<T>, E>`.

#### Traits, Generics and Trait Objects

##### Static vs dynamic dispatch

```rust
// edition 2018, rustc 1.31+
use std::fmt::Display;

fn show_all<T: Display>(items: &[T]) -> String {           // monomorphised, inlinable
    items.iter().map(|i| i.to_string()).collect::<Vec<_>>().join(", ")
}
fn show_dyn(items: &[Box<dyn Display>]) -> String {          // one copy, vtable calls, heterogeneous
    items.iter().map(|i| i.to_string()).collect::<Vec<_>>().join(", ")
}
fn print(x: impl Display) { println!("{}", x) }              // impl Trait in argument position (1.26)

fn main() {
    println!("{}", show_all(&[1, 2]));
    println!("{}", show_dyn(&[Box::new(1), Box::new("a")]));
    print(3.5);
}
```

- Argument-position `impl Trait` prevents callers from using turbofish (`f::<T>()`) — before 1.63 it was an error to pass *any* explicit generic arguments to such a function. Prefer named generics in public APIs that callers may need to specify.
- **Object safety** (dyn compatibility): a trait used as `dyn Trait` cannot have generic methods, `Self`-returning methods or `Self: Sized` supertraits, except on methods with `where Self: Sized`.
- **No trait-object upcasting** before 1.86: `&dyn Sub` does not coerce to `&dyn Super`; add an `as_super(&self) -> &dyn Super` method.
- `dyn Trait + Send + Sync` for objects shared between threads; the order of auto traits no longer matters since 1.36.

##### Coherence and the orphan rule

You may implement a trait for a type only if the trait or the type is local. Since 1.41 (RFC 2451), an impl whose local type comes before uncovered type parameters is also allowed, e.g. `impl<T> From<Wrapper<T>> for Vec<T>`; before 1.41 that is error E0210 "type parameter `T` must be used as the type parameter for some local type" (verified on 1.31.0; non-generic `impl From<My> for Vec<u8>` was already fine). On old MSRVs write `impl<T> Into<Vec<T>> for Wrapper<T>` instead — the only case where implementing `Into` directly is justified.

##### Standard traits to derive

- `Debug` on all public types (`missing_debug_implementations` lint).
- `Clone`, `Copy` only for small plain-data types; `Copy` is a SemVer promise.
- `PartialEq`/`Eq`/`Hash` consistently: `k1 == k2` must imply `hash(k1) == hash(k2)`. A manual `PartialEq` with a derived `Hash` is a bug pattern (clippy `derive_hash_xor_eq`, renamed `derived_hash_with_manual_eq`).
- `PartialOrd`/`Ord` consistent with `Eq`; inconsistent `Ord` can make sorting **panic** on 1.81+ and makes `BTreeMap` misbehave.
- `Default` — derived on enums only with 1.62+ (`#[default]` variant).

##### Generic code

- Put bounds on `impl` blocks and functions, not on struct definitions (bounds on structs must be repeated everywhere).
- `where` clauses for long bounds.
- `T: AsRef<str>`, `T: Into<String>` for flexible constructors; avoid `T: ToString` (allocates for `&str`).
- Const generics (1.51+) replace macro-generated impls for `[T; 0]…[T; 32]`. Before 1.47, many std traits (`Debug`, `PartialEq`, `Default`, …) were implemented only for arrays up to length 32 — `[0u8; 40] == [0u8; 40]` does not compile on 1.31 (verified). `Default` is still limited to `[T; 0..=32]` today.
- GATs (1.65+) and `async fn` in traits (1.75+) are not available to older MSRVs; the `async-trait` crate boxes futures (heap allocation per call, `Send` by default — use `#[async_trait(?Send)]` for non-`Send` futures).

#### Closures and Iterators

##### Capture semantics in 2018 (whole-variable capture)

- A closure that uses `self.field` captures `self` (by reference or, with `move`, by value) — this can make a `move` closure `!Send` because some *other* field of `self` is `!Send`, and it keeps the whole struct borrowed.
- To capture one field, bind it first: `let tx = self.tx.clone(); thread::spawn(move || tx.send(1));`.
- `move` closures copy `Copy` values — mutation inside the closure does not affect the original.

##### Iterator review points

```rust
// edition 2018, rustc 1.31+
fn main() {
    let words = vec!["alpha", "beta", "gamma"];
    // GOOD: lazy chain, single allocation at the end
    let lens: Vec<usize> = words.iter().map(|w| w.len()).filter(|&n| n > 4).collect();
    // GOOD: fallible collection — stops at the first error
    let nums: Result<Vec<i32>, _> = "1 2 x".split(' ').map(str::parse::<i32>).collect();
    // GOOD: enumerate/zip instead of index loops
    for (i, w) in words.iter().enumerate() { if i == 0 { println!("{} {}", i, w); } }
    println!("{:?} {}", lens, nums.is_err());
}
```

- `collect::<Vec<_>>()` just to call `.len()`, `.iter()` or `.is_empty()` again — use `count()`, chain further, or `any()`.
- `iter().map(...).collect::<Vec<_>>()` inside loops: hoist or reuse buffers.
- `for i in 0..v.len() { v[i] }` — use `iter()`/`iter_mut()` (bounds checks and off-by-one risk).
- `.iter().cloned()` vs `.copied()` (1.36): prefer `copied` for `Copy` types so that an accidental expensive clone is a type error.
- `fold` with `String` accumulation: use `collect::<String>()` or `join`.
- `Iterator::flatten` (1.29), `find_map` (1.30), `step_by` (1.28) are available on 1.31; `map_while` (1.57), `array_windows` (1.94), `repeat_n` (1.82) are not.
- Side effects in `map` are a smell; use `for` or `for_each`.
- `peekable()` + `next_if` (1.51).
- Laziness: an iterator chain without a consumer does nothing (`#[must_use]` warning "iterators are lazy and do nothing unless consumed").
- `chain` of many iterators and `Box<dyn Iterator>` cost dynamic dispatch; fine outside hot loops.

##### `array.into_iter()` in 2018

See [What a 2018 crate does NOT get](#what-a-2018-crate-does-not-get-editions-2021-and-2024): `[1, 2, 3].into_iter()` yields `&i32` in 2018. Flag it (the compiler warns) and rewrite to `.iter()` — the 2021 upgrade would silently change the item type and can change behaviour in generic code.

#### Collections

- `Vec::with_capacity(n)` when the size is known; `extend` instead of repeated `push` from an iterator.
- `HashMap` uses SipHash-1-3 with random keys (`RandomState`) — DoS-resistant but slow for small integer keys; `FxHashMap`/`ahash` are faster but **not** HashDoS-resistant: never for attacker-controlled keys. Since 1.36 the implementation is hashbrown (SwissTable).
- `HashMap`/`HashSet` iteration order is random per process — do not depend on it in output, tests, or serialization; use `BTreeMap` or sort.
- Entry API (`entry().or_insert_with(..)`, `or_default()` 1.28) instead of `contains_key` + `insert` (double lookup, and racy reasoning).
- `VecDeque` for FIFO; `Vec::remove(0)` is O(n).
- `retain` instead of index-based removal loops; `drain(..)` to move out; `dedup` needs sorted input for global uniqueness.
- `sort_unstable` (1.20) when stability is not needed; `sort_by_key` with a cloning key closure allocates per comparison — use `sort_by_cached_key` (1.34).
- `binary_search` on unsorted data returns garbage, not an error.
- Indexing `v[i]` panics on out-of-bounds; use `get(i)` for untrusted indices.
- `BTreeMap::range` for ordered queries; `first_key_value`/`pop_first` need 1.66.
- `slice::concat`/`join` for flattening; `[a, b].concat()`.
- `HashMap::get_disjoint_mut` (1.86) / `slice::get_disjoint_mut` are unavailable on older compilers — `split_at_mut` (1.0) is the classic way to get two `&mut` into one slice.

#### Strings and Text

```rust
// edition 2018, rustc 1.31+
fn main() {
    let s = String::from("grüße, 世界");
    println!("bytes={} chars={}", s.len(), s.chars().count());       // len() is bytes
    // BAD: &s[0..3] panics if 3 is not a char boundary ("byte index 3 is not a char boundary")
    let ok = s.get(0..3);                                              // Option<&str>, no panic
    println!("{:?}", ok);
    let first: String = s.chars().take(3).collect();
    println!("{}", first);
    // Building strings
    let mut out = String::with_capacity(32);
    for (i, w) in ["a", "b"].iter().enumerate() {
        if i > 0 { out.push_str(", "); }
        out.push_str(w);
    }
    use std::fmt::Write;                                               // write! into a String
    write!(out, " ({} items)", 2).unwrap();
    println!("{}", out);
}
```

- `str` indices are **byte** offsets; slicing at a non-boundary panics. `char` is a Unicode scalar value, not a user-perceived character (use `unicode-segmentation` for graphemes).
- `to_lowercase()`/`to_uppercase()` are Unicode-aware and may change length; for protocol tokens use `to_ascii_lowercase`/`eq_ignore_ascii_case`.
- `format!` in a loop allocates each time; `write!` into a reused `String`.
- `String::from_utf8(bytes)?` for untrusted bytes; `from_utf8_lossy` only for display; `from_utf8_unchecked` requires a proof.
- `OsStr`/`OsString` and `Path` for file names — `to_str()` returns `None` for non-UTF-8 names; `to_string_lossy()` is display-only. `Path::display()` for printing.
- `trim_start`/`trim_end` (1.30) instead of deprecated `trim_left`/`trim_right` (which suggest "left" even for RTL text).
- `strip_prefix`/`strip_suffix` (1.45), `split_once` (1.52) — on older MSRVs use `starts_with` + slicing and `splitn(2, ..)`.
- `char::is_alphanumeric` etc. are Unicode-aware; `is_ascii_digit` for ASCII-only parsing (note `'٣'.is_numeric()` is true).
- `str::parse::<f64>()` accepts `"inf"`, `"NaN"`, `"1e400"` (→ infinity) — validate ranges.

#### Integers, Floats, Overflow and Casts

##### Overflow behaviour

- Debug builds (`debug-assertions`/`overflow-checks` on): `+ - *` overflow **panics** ("attempt to add with overflow").
- Release builds (default profile): overflow **wraps** silently (two's complement) — not UB, but a logic bug.
- `[profile.release] overflow-checks = true` enables checks in release.

```rust
// edition 2018, rustc 1.31+
fn main() {
    let x: u8 = 255;
    println!("{} {:?} {}", x.wrapping_add(1), x.checked_add(1), x.saturating_add(1)); // 0 None 255
    let (v, overflowed) = x.overflowing_add(1);
    println!("{} {}", v, overflowed);                                                  // 0 true
}
```

Review: arithmetic on lengths, offsets, prices, timestamps and anything derived from input should use `checked_*` (returning an error) or be proven in range. `a - b` on `usize` when `b > a` is a classic panic-in-debug / huge-value-in-release bug.

##### `as` casts

- Integer `as` narrowing **truncates** silently (`300i32 as u8 == 44`), signed↔unsigned reinterprets (`-1i32 as u32 == 4294967295`). Use `u8::try_from(x)` (1.34) or explicit range checks.
- Float→int `as` saturates and maps NaN to 0 **since 1.45**; on 1.31–1.44 out-of-range values are **UB** and the result varies by build (verified on 1.31/1.44: 44, 80, 192 or 255; on 1.45+ always 255).
- `usize as u32` truncates on 64-bit; `u64 as usize` truncates on 32-bit targets.
- `as` between pointers and integers loses provenance; prefer `ptr.cast()`, `addr_of!`, and on 1.84+ the strict-provenance APIs.

##### Floats

- Never compare floats with `==` for computed values; use an epsilon appropriate to the magnitude.
- `f64` is not `Ord`/`Eq`/`Hash`: `sort_by(|a, b| a.partial_cmp(b).unwrap())` panics on NaN — use `total_cmp` (1.62) or filter NaNs first.
- Money: integers in the smallest unit or a decimal crate, never `f64`.
- `u32::MAX` style associated constants need 1.43; `std::u32::MAX` warns on 1.99.

#### Panics

- `panic = "abort"` in a profile makes every panic abort; `catch_unwind` and `Drop` during unwinding do not run then. Libraries must not assume either mode.
- `RefCell::borrow_mut` panics on double borrow at runtime; `Mutex::lock().unwrap()` panics if poisoned; slice indexing, `unwrap`, integer overflow (debug), division by zero, `Vec::remove` out of range, `str` slicing at non-boundaries all panic.
- `std::panic::catch_unwind` requires `UnwindSafe`; wrapping in `AssertUnwindSafe` asserts that broken invariants after a panic are acceptable — review carefully.
- A panic while panicking (in `Drop` during unwinding) aborts.
- Panic messages in 2018: single-argument `panic!("{}")` is **not** formatted (see above).
- `#[track_caller]` (1.46) on helper functions that panic on behalf of the caller.
- `unreachable!()` documents an invariant; `unreachable_unchecked()` is UB if reached.

#### Unsafe Code and FFI

##### Review rules

- The list of undefined behaviour is in the Reference.[^20] Every `unsafe` block carries a `// SAFETY:` comment proving the preconditions; every `pub unsafe fn` has a `# Safety` doc section (clippy `missing_safety_doc`, `undocumented_unsafe_blocks`).
- In edition 2018 the body of an `unsafe fn` is implicitly unsafe; enable `#![warn(unsafe_op_in_unsafe_fn)]` (1.52+) so each unsafe operation needs its own block.
- Keep `unsafe` small and wrapped in a safe abstraction whose invariants cannot be broken by safe callers (e.g. private fields, no `pub` setters for lengths).
- Run tests under Miri (nightly tool) and sanitizers when the crate has nontrivial `unsafe`.

##### Uninitialised memory: `mem::uninitialized` → `MaybeUninit` (1.36)

```rust
// BAD (edition 2018): deprecated since 1.39 and UB for most types — `bool`, references, enums,
// `NonZero*`, `char`, and any struct containing them. Compiles everywhere; behaviour varies by rustc.
#[allow(deprecated)]
fn make() -> [bool; 4] { unsafe { std::mem::uninitialized() } }
```

```rust
// GOOD (rustc 1.36+)
use std::mem::MaybeUninit;
fn make() -> [u32; 4] {
    let mut arr: [MaybeUninit<u32>; 4] = unsafe { MaybeUninit::uninit().assume_init() }; // array of MaybeUninit is valid uninit
    for (i, slot) in arr.iter_mut().enumerate() {
        *slot = MaybeUninit::new(i as u32 * 2);
    }
    // SAFETY: every element was initialised above; [MaybeUninit<u32>; 4] and [u32; 4] have the same layout.
    unsafe { std::mem::transmute::<_, [u32; 4]>(arr) }
}
fn main() { println!("{:?}", make()); }
```

For simple cases prefer safe code (`[0u32; 4]`, `Vec::with_capacity` + `push`, `array::from_fn` on 1.63+). `mem::zeroed()` is only sound for types where all-zero bytes are valid (integers, raw pointers, `Option<&T>`), never for `&T`, `Box<T>`, `NonNull<T>`, function pointers.

##### References to packed fields and raw places

```rust
// BAD: `&p.b` creates an unaligned reference — UB. Only a warning on old compilers
// (1.31: "borrow of packed field is unsafe"; 1.56: "reference to packed field is unaligned"),
// deny-by-default lint `unaligned_references` on 1.62–1.68, unconditional error[E0793] since 1.69.
#[repr(packed)]
struct P { a: u8, b: u32 }
fn read(p: &P) -> u32 { let r = &p.b; *r }
```

```rust
// GOOD (rustc 1.51+): raw pointer without an intermediate reference
#[repr(packed)]
struct P { a: u8, b: u32 }
fn read(p: &P) -> u32 {
    let r = std::ptr::addr_of!(p.b);
    unsafe { r.read_unaligned() }          // SAFETY: r points into *p, read_unaligned has no alignment requirement
}
fn main() { println!("{}", read(&P { a: 1, b: 2 })); }
```

(Copying the field by value, `let b = p.b;`, is also fine and needs no `unsafe`.) `&raw const p.b` is the 1.82+ spelling of `addr_of!`.

##### `static mut`

- Every access is `unsafe` and data-race-prone; `&STATIC_MUT` warns (`static_mut_refs`) in 2018 on current compilers and is an error in 2024.
- Replace with atomics, `Mutex` in a `static` (const `Mutex::new` since 1.63), `OnceLock` (1.70), `lazy_static!`/`once_cell` on older MSRVs, or `thread_local!`.

##### `transmute`

- `transmute` between types of different validity (`u8` → `bool`, `u32` → `char`, integer → reference) is UB for invalid values; use `bool::from`/`char::from_u32`/`TryFrom`.
- `transmute::<&T, &mut T>` is always UB (clippy and rustc deny it).
- Prefer `to_ne_bytes`/`from_ne_bytes` (1.32), `f32::to_bits`/`from_bits` (1.20), `ptr.cast()` (1.38) over transmute.

##### FFI

```rust
// edition 2018, rustc 1.31+
use std::ffi::{CStr, CString};
use std::os::raw::{c_char, c_int};

extern "C" {
    fn strlen(s: *const c_char) -> usize;
    fn abs(x: c_int) -> c_int;
}

fn c_len(s: &str) -> Result<usize, std::ffi::NulError> {
    let c = CString::new(s)?;                 // fails on interior NUL — never `unwrap` untrusted input
    // SAFETY: `c` is a valid NUL-terminated string that outlives the call.
    Ok(unsafe { strlen(c.as_ptr()) })
}

#[no_mangle]
pub extern "C" fn rust_greeting_len(p: *const c_char) -> usize {
    if p.is_null() { return 0; }
    // SAFETY: caller guarantees `p` is a valid NUL-terminated string.
    let s = unsafe { CStr::from_ptr(p) };
    s.to_bytes().len()
}

fn main() {
    println!("{:?} {}", c_len("hello"), unsafe { abs(-3) });
    let owned = CString::new("abc").unwrap();
    println!("{}", rust_greeting_len(owned.as_ptr()));
}
```

- **Dangling `CString` pointer**: `CString::new(s).unwrap().as_ptr()` in one expression frees the string at the end of the statement — the pointer dangles (rustc warns: `temporary_cstring_as_ptr`, renamed `dangling_pointers_from_temporaries`).
- **Panics must not unwind into C**: before 1.81 that was UB; since 1.81 it aborts. Wrap callback bodies in `catch_unwind` and convert to an error code.
- `#[repr(C)]` on every struct/enum shared with C; Rust enums received from C must be validated (an out-of-range discriminant is UB) — take a `c_int` and convert.
- `bool` across FFI requires C `_Bool`; `char` is not C `char` (`c_char`).
- `std::os::raw::*` works on 1.31; `core::ffi::c_*` needs 1.64.
- In edition 2018, `extern "C" { … }` and `#[no_mangle]` need no `unsafe` marker; `unsafe extern "C"` and `#[unsafe(no_mangle)]` are accepted on 1.82+ and required only in 2024.
- `#[no_mangle]` on a generic function is a hard error since 1.99 (previously the `no_mangle_generic_items` warning).

#### Concurrency and Global State

##### Threads, `Send`, `Sync`

```rust
// edition 2018, rustc 1.31+
use std::sync::{mpsc, Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0u64));
    let (tx, rx) = mpsc::channel();
    let handles: Vec<_> = (0..4).map(|i| {
        let counter = Arc::clone(&counter);
        let tx = tx.clone();
        thread::Builder::new()
            .name(format!("worker-{}", i))
            .spawn(move || {
                *counter.lock().unwrap() += 1;     // guard dropped at the end of the statement
                tx.send(i).unwrap();
            })
            .expect("spawn worker")
    }).collect();
    drop(tx);                                       // otherwise rx never sees the end
    for h in handles { h.join().expect("worker panicked"); }
    let mut got: Vec<i32> = rx.iter().collect();
    got.sort();
    println!("{} {:?}", *counter.lock().unwrap(), got);
}
```

- `thread::spawn` requires `'static` closures; borrowing locals needs `std::thread::scope` (1.63+) or `crossbeam::scope` / `rayon` on older MSRVs.
- `JoinHandle::join()` returns `Err` if the thread panicked — do not ignore it.
- A forgotten `drop(tx)` makes `rx.iter()` block forever.
- `std::sync::mpsc` before 1.67 had known bugs (it was replaced by a crossbeam-channel based implementation in 1.67); `Sender` is `Sync` only since 1.72. Old MSRVs often use `crossbeam-channel` instead.
- `Rc`, `RefCell`, `Cell` are `!Sync`/`!Send` as appropriate — the compiler enforces it; `unsafe impl Send/Sync` must be justified in review.

##### Locks

- `Mutex::lock()` returns `Err` when a thread panicked while holding the lock (**poisoning**). `.lock().unwrap()` propagates the panic — the usual choice. Recover with `.unwrap_or_else(|e| e.into_inner())` only if the protected data is still consistent; `Mutex::clear_poison` needs 1.77.
- Keep critical sections short: no I/O, no `.await`, no calls into unknown code under a lock.
- Lock ordering: acquiring two locks in different orders in different places deadlocks.
- `RwLock` writer starvation and recursive read locks are platform-dependent; recursive `read()` from the same thread may deadlock.
- Re-locking a `Mutex` in the `else` of `if let … = *m.lock().unwrap()` deadlocks in 2018 (temporary lives through `else`; see the 2024 section).
- `match m.lock().unwrap().get(..) { … }` keeps the guard for the whole `match` — bind the result first.
- `parking_lot` locks do not poison; current `parking_lot` 0.13 requires 1.95 — old MSRVs pin 0.11/0.12.

##### Atomics

- `Ordering::SeqCst` by default unless an ordering argument is written down; `Relaxed` for pure counters/statistics; `Acquire`/`Release` pairs for publication.
- A flag + data published with `Relaxed` is a data race on the data — the classic bug.
- `compare_exchange_weak` in loops, `compare_exchange` otherwise; `compare_and_swap` is deprecated.
- `AtomicU64` is unavailable on some 32-bit targets (`cfg(target_has_atomic = "64")`, 1.60+).

##### Global state: `lazy_static` → `once_cell` → `OnceLock`/`LazyLock`

```rust
// rustc 1.80+ (any edition): std only
use std::collections::HashMap;
use std::sync::{LazyLock, Mutex, OnceLock};

static CONFIG: OnceLock<String> = OnceLock::new();                       // 1.70
static CACHE: LazyLock<Mutex<HashMap<u32, String>>> =                    // 1.80
    LazyLock::new(|| Mutex::new(HashMap::new()));
static COUNTER: Mutex<u64> = Mutex::new(0);                              // const Mutex::new: 1.63

fn main() {
    CONFIG.set("prod".to_string()).expect("set once");
    CACHE.lock().unwrap().insert(1, "one".into());
    *COUNTER.lock().unwrap() += 1;
    println!("{} {:?} {}", CONFIG.get().unwrap(), CACHE.lock().unwrap().get(&1), COUNTER.lock().unwrap());
}
```

| MSRV | Use |
|---|---|
| < 1.63 | `lazy_static!` or `once_cell::sync::Lazy` (pin a once_cell release that supports the MSRV) |
| 1.63–1.69 | `static M: Mutex<T> = Mutex::new(..)` for const-initialisable values; `once_cell` for the rest |
| 1.70–1.79 | `std::sync::OnceLock` (+ `get_or_init`) |
| 1.80+ | `std::sync::LazyLock` / `std::cell::LazyCell` |

Do not recommend replacing a working `lazy_static!` purely for style when the MSRV is older than 1.70/1.80. Global mutable state is a design smell in libraries regardless of the mechanism.

#### Async Rust in Edition 2018

`async fn`, `async` blocks and `.await` require **edition 2018+ and rustc 1.39+** (in 2015 `async fn` is error E0670; on 1.38 they are unstable).[^16] Code written before 2020 often uses futures 0.1.

##### futures 0.1 / tokio 0.1 (legacy)

```rust
// futures 0.1 style (needs the `futures = "0.1"` crate) — recognise, do not write new code like this
// fn fetch(id: u32) -> impl Future<Item = User, Error = MyError> {
//     http_get(url(id)).and_then(|body| parse(&body)).map_err(MyError::from)
// }
// tokio::run(fut.map_err(|e| eprintln!("{}", e)));
```

- futures 0.1 `Future` has `type Item; type Error; fn poll(&mut self) -> Poll<Item, Error>` — incompatible with `std::future::Future<Output = T>` (1.36). `futures::compat` (futures 0.3, `compat` feature) bridges them.
- `wait()` on a 0.1 future inside a tokio 0.1 runtime blocks a worker thread — a deadlock pattern.
- tokio 0.1/0.2, hyper 0.12/0.13 and reqwest 0.9/0.10 are unmaintained; their upgrade to tokio 1.x requires rustc ≥ the tokio release's MSRV (tokio 1.54, October 2026: 1.85).

##### Modern async in a 2018 crate

```rust
// edition 2018 + tokio 1.x (rt-multi-thread, macros, time) — verified with tokio 1.54.1 on rustc 1.99.1
use std::sync::{Arc, Mutex};
use std::time::Duration;

async fn good(state: Arc<Mutex<u32>>) {
    {
        let mut g = state.lock().unwrap();
        *g += 1;
    } // std MutexGuard dropped before the await
    tokio::time::sleep(Duration::from_millis(1)).await;
}

#[tokio::main]
async fn main() {
    let s = Arc::new(Mutex::new(0));
    tokio::spawn(good(s.clone())).await.unwrap();
    println!("{}", *s.lock().unwrap());
}
```

Review points:

- **`std::sync::MutexGuard` held across `.await`** makes the future `!Send`, so `tokio::spawn` rejects it ("future cannot be sent between threads safely … has type `std::sync::MutexGuard<'_, u32>` which is not `Send`"). Even `drop(g);` before the `.await` does **not** fix this on any compiler up to 1.99.1 (verified) — the guard must go out of scope in an inner block. If the lock must be held across an await, use `tokio::sync::Mutex`.
- **Blocking calls in async** (`std::fs`, `std::thread::sleep`, blocking DNS, CPU-heavy loops, `reqwest::blocking`) stall the executor; use `tokio::task::spawn_blocking`, `tokio::fs`, `tokio::time::sleep`.
- `async fn` in traits is 1.75+; on older compilers use `async-trait` (boxing) or return `Pin<Box<dyn Future<Output = T> + Send + '_>>`.
- Async closures (`async || {}`) are 1.85+; in 2018 use `|| async move { … }`.
- `Future` is not in the 2018 prelude: `use std::future::Future;` to name it.
- Futures are lazy: calling an `async fn` without awaiting or spawning it does nothing (`unused_must_use` warning "futures do nothing unless you `.await` or poll them").
- `tokio::spawn` tasks that return `Result` — the `JoinHandle` result is `Result<Result<T, E>, JoinError>`; ignoring it silently drops errors and panics.
- Cancellation: dropping a future cancels it at its current `.await`; code between awaits must keep invariants (no half-written state) — `tokio::select!` drops the losing branches.
- Unbounded channels and unbounded `spawn` loops are DoS vectors; bound them.
- `Pin`: `Pin<&mut Self>` in manual `Future` impls; never move out of a pinned `!Unpin` value; `pin_project`/`pin-project-lite` instead of `unsafe` projections. `std::pin::pin!` needs 1.68; older code uses `futures::pin_mut!` or `Box::pin`.
- Recursion in `async fn` requires boxing (`Box::pin(recursive(..)).await` works directly on 1.77+; earlier, return `BoxFuture` from a non-async wrapper).

#### Macros

- In 2018 import macros with `use crate_name::macro_name;`; `#[macro_use] extern crate` still works. Within a crate, `macro_rules!` macros are textually scoped (defined before use) unless exported with `#[macro_export]` (then `crate::name!` in 2018).
- Use `$crate::path` inside exported macros so they work from other crates; never hard-code the crate name.
- Fragment specifiers: `$e:expr` does not match `const { … }` or `_` in 2018 (2024 only); `$p:pat` does not match top-level `A | B` (2021+); `$(…)?` needs 1.32 (2018) / 1.37 (2015).
- `literal` fragment 1.32; `$x:lifetime` 1.28; `vis` 1.30.
- A macro body that ends with `;` used in expression position (`let x = m!();`) is an error since 1.91 (the `semicolon_in_expressions_from_macros` lint became deny-by-default; warn on 1.56–1.90, silent on 1.31 — verified); since 1.99 the same pattern in a macro from another crate warns (`semicolon_in_expressions_from_non_local_macros`).
- A missing fragment specifier (`($x) => …`) is rejected on every compiler (deny-by-default `missing_fragment_specifier`, an unconditional error since 1.89).
- Hygiene: `macro_rules!` local variables are hygienic, items and paths are not — exported macros must use fully qualified paths (`::std::vec::Vec`, `$crate::…`).
- Procedural macros: depend on `syn`/`quote`/`proc-macro2` versions that match the MSRV (syn 2.0.0 required 1.56, current syn 2.0.x and syn 3.x declare 1.71); a proc-macro crate needs `[lib] proc-macro = true`. Before 1.42 a 2018 proc-macro crate still needs `extern crate proc_macro;`.
- Prefer functions and generics over macros; macros that hide `return`, `?` or `unsafe` need extra scrutiny.

#### API Design and SemVer

Cargo treats `0.x.y` → `0.(x+1).0` and `x.y.z` → `(x+1).0.0` as breaking. The Cargo SemVer reference lists what is breaking.[^17] Points a reviewer of a published 2018 crate checks:

- **Breaking**: removing/renaming public items; adding a field to a struct with all-public fields (unless `#[non_exhaustive]`); adding an enum variant (unless `#[non_exhaustive]`, 1.40+); adding a non-defaulted trait item; tightening generic bounds; changing a function signature; removing a trait impl (including auto traits — adding a `Rc` field makes a type `!Send`); making a `const fn` non-const; bumping a **public** dependency's major version.
- **Raising the MSRV** is not formally breaking under Cargo's rules but breaks users on old toolchains; do it in a minor (not patch) release and document it. Bumping `edition` does not affect downstream users — but raising it to 2021 raises the MSRV to 1.56, to 2024 raises it to 1.85.
- **Sealed traits** (`pub trait Ext: private::Sealed`) to allow adding methods later.
- `#[must_use]` on functions returning values that must be used (1.27+ for functions) and on builder types.
- Constructors: `new` for the common case, builders for many optional parameters; `Default` when there is a sensible default.
- Accept generics (`impl AsRef<Path>`), return concrete types; avoid `Box<dyn Error>` in library return types.
- Conversion traits: implement `From` (never `Into` directly, except the pre-1.41 orphan workaround for generic foreign types), `TryFrom` (1.34), `AsRef`, `FromStr`, `Display`.
- Do not expose `pub` fields when invariants exist.
- Feature flags must be additive (resolver-1 unification in 2018 makes non-additive features break unrelated crates); never use a feature to *remove* functionality or change behaviour incompatibly (`default-features = false` users rely on additivity).
- `#[doc(hidden)] pub` items are still public API in practice.
- Documentation: every public item, `# Errors`, `# Panics`, `# Safety` sections; doc examples are compiled as tests.

#### Performance

- Measure first: `cargo bench` with `criterion` (check its MSRV), `perf`/`cargo flamegraph`, `cargo build --timings` (1.60).
- Release profile settings: `lto = "thin"`/`"fat"`, `codegen-units = 1`, `panic = "abort"` (only for binaries that do not need unwinding), `debug = 1` or `"line-tables-only"` (1.70) for profiling symbols.
- Avoid needless allocation: `&str` over `String` parameters, `Cow<'_, str>` for maybe-owned data, `Vec::with_capacity`, reuse buffers (`clear()` keeps capacity), `String::with_capacity`.
- `Box<dyn Trait>`/`dyn Fn` per element in hot loops: consider generics or enums.
- `HashMap` SipHash cost for integer keys: faster hashers (`FxHash`, `ahash`) only when keys are not attacker-controlled.
- Iterators are usually as fast as indexed loops and avoid bounds checks; `chunks_exact` (1.31) helps vectorisation.
- `Rc`/`Arc` clones in hot paths are atomic operations (`Arc`); pass `&T` where possible.
- Large `enum` variants make every value large (clippy `large_enum_variant`) — box the big variant.
- `#[inline]` matters across crates for small generic-free functions; generic functions are inlinable anyway. Avoid `#[inline(always)]` without measurements.
- `BufReader`/`BufWriter` for file and socket I/O; `stdout()` is line-buffered (each `println!` takes the lock and flushes a line) — for bulk output wrap `stdout().lock()` in a `BufWriter`.
- `collect::<Vec<_>>()` then iterate again is a double pass; `sort` then `dedup` is O(n log n) — a `HashSet` may be better.
- Compile times: heavy generic code and proc-macros; `cargo tree -d` (1.44) to find duplicate dependency versions.

#### Testing

```rust
// edition 2018, rustc 1.31+ — unit tests next to the code
pub fn checked_percent(part: u64, total: u64) -> Option<u64> {
    if total == 0 { return None; }
    part.checked_mul(100).map(|p| p / total)
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn percent_basic() {
        assert_eq!(checked_percent(1, 4), Some(25));
    }

    #[test]
    fn percent_zero_total_is_none() {
        assert_eq!(checked_percent(1, 0), None);
    }

    #[test]
    fn percent_overflow_is_none() {
        assert_eq!(checked_percent(u64::max_value(), 1), None);   // `u64::MAX` needs 1.43; `max_value()` warns on 1.99
    }

    #[test]
    fn returns_result() -> Result<(), std::num::ParseIntError> {   // tests returning Result: 1.28+
        let n: u64 = "42".parse()?;
        assert_eq!(checked_percent(n, 42), Some(100));
        Ok(())
    }

    fn ratio(a: u64, b: u64) -> u64 { a / b }

    #[test]
    #[should_panic(expected = "divide by zero")]
    fn panics_with_message() {
        ratio(1, 0);
    }
}
```

Note: the example uses `u64::max_value()` to stay compilable on 1.31; with an MSRV ≥ 1.43 write `u64::MAX` (and on rustc 1.99+ `max_value()` emits a deprecation warning).

- Integration tests in `tests/` see only the public API; shared helpers go in `tests/common/mod.rs` (not `tests/common.rs`, which would be compiled as its own test crate).
- Doc tests run with `cargo test`; a doc test that uses `?` needs an explicit `fn main() -> Result<…>` or an `Ok::<(), E>(())` trailing line.
- `#[should_panic]` without `expected = "…"` accepts any panic, including the wrong one.
- Tests run in parallel threads in one process: global state (env vars, current directory, statics) causes flaky tests; serialize or isolate. `std::env::set_var` in tests is racy (and `unsafe` in 2024).
- Since 1.49, output of threads spawned by tests is captured too.
- Property testing (`proptest`, `quickcheck`) and fuzzing (`cargo fuzz`, nightly) for parsers; check MSRVs.
- `#[bench]` is nightly-only (and a hard error without `#![feature(test)]` since 1.88); use `criterion` on stable.
- Test with `--release` too when overflow behaviour or timing matters; run `cargo test --all-features` and `--no-default-features` for libraries with features (resolver 1 may hide missing feature dependencies).
- Run the test suite on the MSRV toolchain in CI (`cargo +1.NN test`), not only on stable.

#### Cargo, Dependencies and Builds

##### Manifest checklist for a 2018 crate

```toml
[package]
name = "billing"
version = "0.4.2"
edition = "2018"
rust-version = "1.56"          # enforced by Cargo 1.56+; ignored (with a warning) by older Cargo
resolver = "2"                 # Cargo 1.51+; avoid feature unification surprises (default in 2018 is "1")
license = "MIT OR Apache-2.0"
description = "…"
repository = "…"

[dependencies]
serde = { version = "1", features = ["derive"] }
log = "0.4"

[dev-dependencies]             # not `dev_dependencies` (deprecated, error in edition 2024)
assert_matches = "1"

[profile.release]
overflow-checks = true         # optional hardening
```

- `Cargo.lock`: commit it for binaries and applications; for libraries it is a project choice (Cargo's guidance changed in 2023 to "commit it if it helps"). A committed lockfile makes old-toolchain CI reproducible — and `cargo update` on a new toolchain can pull dependencies whose MSRV is newer than the project's.
- **MSRV-aware resolution**: Cargo 1.84+ can prefer dependency versions compatible with `rust-version` (`resolver = "3"` in the package — accepted on an edition-2018 package by current Cargo, but rejected by older Cargo with "`resolver` setting `3` is not valid" (verified on 1.56.0) — or `.cargo/config.toml` `[resolver] incompatible-rust-versions = "fallback"`). On older Cargo, pin with `cargo update -p dep --precise 1.2.3` and `=1.2.3` requirements where needed.
- Version requirements `"1.2"` mean `^1.2` (any compatible `1.x ≥ 1.2`). `"*"` is rejected by crates.io; `">= 1"` admits future majors.
- **Git and path dependencies** cannot be published; git dependencies without `rev`/`tag` are not reproducible.
- `[patch.crates-io]` for temporary forks; remove before release.
- `build.rs`: emit `cargo:rerun-if-changed=…`/`rerun-if-env-changed` or the script reruns on every change in the package; never download from the network in build scripts without an opt-in; the single-colon `cargo:` prefix works on all Cargo versions, `cargo::` needs 1.77.
- Features: additive, documented; in 2018 with resolver 1, build/dev-dependency features leak into the normal build (see edition section).
- `default-features = false` on a dependency is ignored if any other crate in the graph enables defaults (unification).
- Workspaces: one `Cargo.lock` and `target/`; `[workspace] resolver = "2"` must be set at the workspace root for virtual workspaces.
- `cargo install --locked` for reproducible binary installs.
- Sparse registry protocol is the default since 1.70 (`CARGO_REGISTRIES_CRATES_IO_PROTOCOL=sparse` from 1.68); very old Cargo clones the full git index — slow CI.
- Toolchain files: `rust-toolchain.toml` with `channel = "1.56.0"`, `components = ["clippy", "rustfmt"]`; keep it in sync with `rust-version` and CI.

#### Tooling: Clippy, rustfmt and Lints

- **Lint groups for 2018 code**: `#![warn(rust_2018_idioms)]` (unused `extern crate`, `'_` in paths, bare trait objects, ellipsis patterns, explicit outlives requirements); before upgrading, `#![warn(rust_2021_compatibility)]` shows what `cargo fix --edition` will change.
- Useful additional lints: `missing_docs`, `missing_debug_implementations`, `unreachable_pub`, `unsafe_op_in_unsafe_fn` (1.52+), `unused_qualifications`.
- **Clippy** respects `rust-version`/`msrv`: with `rust-version = "1.40"` it does not suggest `strip_prefix` (`manual_strip`), verified on 1.99.1. Without it, clippy suggests APIs the MSRV lacks — set the MSRV rather than ignoring lints. Clippy `incompatible_msrv` flags std APIs newer than the declared MSRV.
- Tool-lint syntax `#[allow(clippy::lint_name)]` is stable since 1.31; old code uses `#[cfg_attr(feature = "cargo-clippy", allow(lint_name))]` — replace it: current Clippy no longer sets that cfg (it warns "`feature = "cargo-clippy"` was replaced by `clippy`"), so the `allow` silently stops applying, and rustc reports `unexpected_cfgs` (verified on 1.99.1).
- Clippy lints worth enforcing in reviews of production 2018 code: `unwrap_used`/`expect_used` (libraries), `indexing_slicing` (parsers), `cast_possible_truncation`/`cast_sign_loss` (numeric code), `await_holding_lock`, `await_holding_refcell_ref`, `let_underscore_lock`, `mutex_atomic`, `large_enum_variant`, `needless_collect`, `redundant_clone`, `missing_safety_doc`, `undocumented_unsafe_blocks`, `uninit_assumed_init`, `mem_replace_with_default`, `dbg_macro`, `todo`.
- `let _ = mutex.lock();` drops the guard immediately (`let_underscore_lock`), `let _guard = …` keeps it — a frequent mistake.
- **rustfmt**: `cargo fmt` uses the package edition; a `rustfmt.toml` with `edition = "2018"` is needed for direct `rustfmt` calls. Unstable options (`imports_granularity`, `group_imports`) are ignored on stable with a warning.
- `cargo fix` applies compiler suggestions; `cargo clippy --fix` applies clippy's.
- `cargo audit` (RustSec) and `cargo deny` (licenses, bans, advisories, duplicate versions) in CI.
- `cargo +1.NN check` / `cargo msrv` to verify the MSRV; `cargo hack --feature-powerset check` for feature combinations.

##### Logging and observability

- Libraries log through a facade (`log` 0.4 macros, or `tracing`) and **never** install a logger; binaries choose the backend (`env_logger`, `tracing-subscriber`). Current `log` 0.4.x declares `rust-version` 1.71 and `tracing` 0.1.44 declares 1.65 (crates.io, October 2026) — old MSRVs must pin older patch releases.
- In 2018, import the macros with `use log::{debug, info, warn};` instead of `#[macro_use] extern crate log;`.
- `println!`/`eprintln!` in library code is a finding (clippy `print_stdout`/`print_stderr`); `dbg!` must not be committed (`dbg_macro`).
- Log errors with their source chain (`{}` of each `source()`), not just the top-level `Display`; never log secrets or full request bodies.
- Install a panic hook (`std::panic::set_hook`) in services to route panics into the logging system; remember that a panic in another thread does not stop the process.
- Name threads (`thread::Builder::name`) so panics and profiles identify them.

#### Security

- **Unsafe code** is the main source of memory-safety bugs: review every `unsafe` block, `unsafe impl Send/Sync`, `transmute`, raw-pointer arithmetic, `set_len`, `from_raw_parts`, `get_unchecked`, FFI signature mismatches.
- **Dependencies**: `cargo audit` against RustSec; legacy 2018 dependency trees often contain `failure` (unsound), `time` 0.1 / old `chrono` (local-time segfault), `atty` and `net2` (unsound), `serde_cbor`/`yaml-rust` (unmaintained, past DoS issues) and `tempdir`.
- **Integer overflow** in size/offset calculations: release builds wrap — an attacker-controlled length can wrap to a small allocation; use `checked_*` and `try_from`.
- **Denial of service**: unbounded `Vec::with_capacity(len_from_input)`, `read_to_end` without limits, recursive parsers (stack overflow aborts the process), regex on attacker input (the `regex` crate is linear-time; `fancy-regex` is not), `HashMap` with weak hashers on attacker keys, unbounded channels.
- **Panics as DoS**: `unwrap`/indexing/`str` slicing/division on untrusted input in servers; one panic in a request handler can poison shared `Mutex`es for all other requests.
- **Path traversal**: `Path::join` with an absolute component replaces the base (`Path::new("/srv").join("/etc/passwd")` is `/etc/passwd`); `..` components are not normalised — canonicalize and check `starts_with` (symlinks!).
- **Command injection**: `std::process::Command::new(prog).arg(user)` passes arguments without a shell — safe from shell injection; `Command::new("sh").arg("-c").arg(format!(…))` is not. On Windows, `.bat`/`.cmd` argument escaping had CVE-2024-24576 (fixed in 1.77.2) — old toolchains are affected.
- **`std::fs::remove_dir_all` race** (CVE-2022-21658, symlink TOCTOU) fixed in 1.58.1 — another reason not to stay on old compilers.
- **Secrets**: compare MACs/tokens with constant-time functions (`subtle`, `ring::constant_time`), not `==`; zeroize secrets (`zeroize` crate); do not `Debug`-print secrets (custom `Debug` impl).
- **Randomness**: `rand::thread_rng()` (rand ≤ 0.8) / `rand::rng()` (0.9+) is a CSPRNG; `SmallRng` is not; check the `rand` version's API and MSRV (rand 0.10 needs 1.85, edition 2024).
- **TLS/crypto**: use `rustls`/`native-tls`, `ring`/RustCrypto; no hand-written crypto; certificate verification must not be disabled (`danger_accept_invalid_certs(true)`).
- **Deserialization**: `serde` with `#[serde(deny_unknown_fields)]` where strictness matters; limit input size before parsing; `bincode` with size limits.
- **Environment**: `std::env::set_var` in multi-threaded programs is unsound with concurrent `getenv` from C code (why it became `unsafe` in 2024) — set environment before spawning threads, or pass configuration explicitly.
- **Toolchain**: only the latest stable receives security fixes; a project pinned to 1.41 lacks every std fix since 2020.

#### Upgrading Editions — Migration Notes

Editions are upgraded one at a time; there is no direct 2015 → 2021 or 2018 → 2024 migration.[^18]

##### 2015 → 2018

1. Make sure the crate builds without warnings on the current toolchain.
2. `cargo fix --edition` (with the crate still on 2015) applies the `rust_2018_compatibility` fixes: `crate::` paths for local `use` and `::` paths, `_` names for anonymous trait parameters, `r#` for new keywords used as identifiers.
3. Set `edition = "2018"` in `Cargo.toml` **by hand** — `cargo fix --edition` does not edit the manifest (verified on Cargo 1.99.1).
4. Build and test; then optionally `cargo fix --edition-idioms` (or `#![warn(rust_2018_idioms)]` + `cargo fix`) to remove `extern crate`, add `'_` etc.
5. Replace `#[macro_use] extern crate` with `use` imports where convenient.

Verified example: `cargo fix --edition` on a 2015 crate rewrote `use util::hi;` → `use crate::util::hi;`, `::util::hi()` → `crate::util::hi()`, `fn scale(&self, f64)` → `fn scale(&self, _: f64)`, and left `Box<Shape>` (only a warning in 2018) for the 2021 step.

##### 2018 → 2021 (rustc 1.56+)

1. `cargo fix --edition` applies `rust_2021_compatibility`: inserts `let _ = &s;` into closures whose capture/drop order would change, rewrites `array.into_iter()` to `array.iter()` (verified), `Box<Trait>` → `Box<dyn Trait>`, `...` → `..=`, adds spaces in reserved-prefix macro input, rewrites `$x:pat` to `$x:pat_param` where needed, and fixes `panic!` calls.
2. Set `edition = "2021"`; this also switches the default resolver to `"2"` — **check feature-dependent behaviour** (`cargo tree -e features` before/after), especially for `no_std`, WASM and binaries that relied on unified features.
3. Review the `let _ = &x;` insertions: most can be removed if the drop order does not matter.
4. The MSRV becomes ≥ 1.56; update `rust-version` and CI.

##### 2021 → 2024 (rustc 1.85+)

1. `cargo fix --edition` handles RPIT `use<..>` bounds, `unsafe extern`, `#[unsafe(..)]` attributes, `unsafe {}` around unsafe operations in `unsafe fn`, `if let` rescoping suggestions (rewrite to `match`), `expr_2021` fragments, `gen` → `r#gen`, `Box<[T]>::into_iter()`.
2. Manual work: `static mut` references, `env::set_var` now `unsafe`, never-type fallback, tail-expression temporary scope (rarely needs code changes but can change drop order), Cargo key spellings, `resolver = "3"` (MSRV-aware) default, rustfmt style edition 2024 (`cargo fmt` reformats).
3. The MSRV becomes ≥ 1.85.

##### Staying on 2018

Staying on edition 2018 is legitimate (no deadline, full compiler support). Do not file "upgrade the edition" as a defect; do flag 2018-specific hazards (array `into_iter`, single-argument `panic!`, resolver 1 feature leaks, missing `use std::convert::TryFrom`, whole-struct closure captures, `if let`-guard-in-`else` deadlocks).

#### Production / Review Checklist

##### Version and edition

- [ ] Edition determined from `Cargo.toml` (no key = 2015); 2015 path/keyword rules applied where relevant
- [ ] MSRV determined (`rust-toolchain(.toml)`, `rust-version`, CI, `clippy.toml`, lockfile version) before suggesting any post-1.31 API
- [ ] No 2021/2024-only features suggested (let chains, `c"…"`, prelude `TryInto`/`FromIterator`/`Future`, disjoint captures)
- [ ] Toolchain bumps checked for 1.100 (beta: never-type fallback becomes `!` in every edition), 1.80 (`time` < 0.3.35, `unexpected_cfgs`), 1.81 (FFI panic abort, sort panics), 1.88 (`#[bench]`), 1.90 (lld), 1.91 (macro semicolons), 1.92 (never-type fallback), 1.99 (legacy constants deprecation + `deny(warnings)`)
- [ ] Dependency upgrades checked against the MSRV (crate `rust-version`, edition 2021 ⇒ 1.56+, edition 2024 ⇒ 1.85+)
- [ ] `resolver = "2"` considered for 2018 packages/virtual workspaces with build/dev/proc-macro or target-specific dependencies

##### Edition-2018 hazards

- [ ] `array.into_iter()` / `boxed_slice.into_iter()` intended to yield references (else `.iter()` / by-value `for` on 1.53+)
- [ ] Single-argument `panic!`/`assert!` messages contain no `{}`/`{x}` placeholders
- [ ] `move` closures do not move whole structs unintentionally (2018 whole-variable capture)
- [ ] No re-locking/re-borrowing inside the `else` of `if let … = *guard_expr`
- [ ] No `try!`, `...` patterns, bare trait objects, anonymous trait parameters (2015)
- [ ] `use std::convert::{TryFrom, TryInto}` present where `try_from`/`try_into` are used

##### Correctness

- [ ] No `unwrap`/`expect`/indexing/slicing on untrusted data in library or server code
- [ ] Arithmetic on sizes/offsets uses `checked_*`/`try_from`; no truncating `as` on untrusted values; float→int casts checked on ≤ 1.44
- [ ] `PartialEq`/`Eq`/`Hash`/`Ord` consistent; float sorting uses `total_cmp`/`partial_cmp` without NaN panics
- [ ] Errors implement `Display` + `source()`; no `description()`/`cause()`; public error enums `#[non_exhaustive]`
- [ ] No `HashMap` iteration order dependence
- [ ] `JoinHandle::join()` and spawned-task results checked

##### Unsafe and FFI

- [ ] Every `unsafe` block has a `SAFETY:` justification; `unsafe fn` documents `# Safety`
- [ ] No `mem::uninitialized`; `mem::zeroed` only for all-zero-valid types; `MaybeUninit` used correctly
- [ ] No references to packed fields; `addr_of!`/`read_unaligned` instead
- [ ] No `static mut` references; no `transmute` to types with invalid bit patterns
- [ ] FFI: `#[repr(C)]`, `CString` kept alive, no panics across `extern "C"`, C enums validated

##### Concurrency and async

- [ ] No `std::sync::MutexGuard`/`RefCell` borrow alive across `.await` (inner scope, not `drop()`)
- [ ] No blocking I/O or sleeps in async tasks
- [ ] Lock ordering consistent; critical sections short; poisoning handled deliberately
- [ ] Atomics use orderings that publish data correctly
- [ ] Global state uses the MSRV-appropriate mechanism (`lazy_static`/`once_cell` → `OnceLock` 1.70 → `LazyLock` 1.80)
- [ ] futures 0.1 / tokio 0.1 code isolated or migrated; no `wait()` inside a runtime

##### Build, tooling, security

- [ ] CI runs `cargo test` on the MSRV and on stable; `cargo clippy` with the MSRV configured; `cargo fmt --check`
- [ ] No `#![deny(warnings)]` in published libraries
- [ ] `cargo audit`/`cargo deny` clean or advisories triaged (`failure`, `time` 0.1, `chrono` < 0.4.20, `atty`, `net2`, …)
- [ ] `Cargo.lock` committed for binaries; lockfile version readable by the CI toolchain
- [ ] Build scripts declare `rerun-if-changed`, do not fetch from the network
- [ ] Toolchain not older than needed: old pinned compilers miss std security fixes (e.g. CVE-2022-21658 `remove_dir_all`, CVE-2024-24576 Windows `Command`)

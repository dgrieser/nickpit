### Rust (Edition 2024): The Complete Production Developer Guide

> **Edition**: Rust 2024 (`edition = "2024"` in `Cargo.toml`), stabilized in **Rust 1.85.0 (2025-02-20)**.[^1][^2]
> **Toolchain status (October 2026)**: current stable is **Rust 1.99.1 (2026-10-15)**; 1.99.0 shipped 2026-10-01. **1.100.0 is in beta** (scheduled for 2026-11-12) and **1.101.0 is nightly** (scheduled for 2026-12-24).[^3][^4] Rust has no LTS channel: a new stable ships every six weeks, and the project only provides support and security updates for the most recent stable release, so 1.99.1 is the only supported toolchain today.[^5]
> **Scope**: Everything a reviewer needs to judge code written for edition 2024 — the edition's semantic changes versus 2021, every language/library/Cargo change from 1.85 to 1.99 with the release that introduced it, and the idioms and pitfalls of production Rust (ownership, errors, `unsafe`, concurrency, async, API design, Cargo, tooling, security).
> **Note**: This document is self-contained. Sections marked **[2024]** describe behaviour that depends on the edition; sections or items marked **(1.N+)** describe features that need at least toolchain 1.N. All behaviour shown was compiled and run on rustc 1.85.0 and 1.99.1 (and on each release in between for "1.N+" boundaries).

#### Two Axes: Edition vs. Toolchain

A Rust crate is described by **two independent version numbers**, and a reviewer must keep them apart:

| Axis | Where it is declared | What it controls | Values for this guide |
|---|---|---|---|
| **Edition** | `edition = "2024"` in `[package]` (or `edition.workspace = true` + `[workspace.package] edition`) | Language *semantics and syntax* that are allowed to change in a backwards-incompatible way: keyword set, temporary scopes, RPIT capture rules, prelude contents, which attributes need `unsafe`, lint levels, Cargo resolver default, rustfmt style edition, doctest merging | 2024 |
| **Toolchain (compiler + std)** | `rust-version = "1.N"` in `[package]` (the MSRV), `rust-toolchain.toml` (`channel = "1.N.0"`), CI images | Which *features and APIs exist*: everything stabilized in 1.86 … 1.99 is unavailable on an older compiler, whatever the edition | 1.85.0 … 1.99.1 |

Key facts:

- **Edition 2024 needs rustc ≥ 1.85.** Older compilers reject the manifest ("the crate requires edition 2024, but the latest edition supported by this Rust version is 2021"), and Cargo rejects `edition = "2024"` combined with `rust-version` below 1.85 ("rust-version 1.63 is incompatible with the version (1.85.0) required by the specified edition (2024)").
- **New std APIs and most new language features are edition-independent.** `Vec::pop_if` (1.86) works in 2015, 2018, 2021 and 2024 crates compiled by ≥ 1.86. Do not label such features "Rust 2024 features".
- **A few features are edition-gated as well as version-gated.** `let` chains need edition 2024 **and** rustc ≥ 1.88; on 1.99 an edition-2021 crate gets `error: let chains are only allowed in Rust 2024 or later`.
- **Editions interoperate.** A 2024 crate can depend on 2015/2018/2021 crates and vice versa; each crate is compiled with its own edition's rules. Macros expand with the edition of the crate that *defines* them.
- **Edition 2024 is the newest edition** on every stable toolchain up to 1.99 (and on 1.100 beta). There is no stable `edition = "2027"`.

#### Version-Aware Review

Before claiming that code is wrong, outdated, or could use a newer API:

1. **Read `Cargo.toml`.** Note `edition` (or `edition.workspace = true` → look in the root `[workspace.package]`), `rust-version` (or `rust-version.workspace = true`), and any `rust-toolchain.toml` / `rust-toolchain` file. In a workspace, each member can have its own edition and MSRV.
2. **The MSRV caps every suggestion.** If `rust-version = "1.85"`, do not suggest `let` chains (1.88), `Vec::extract_if` (1.87), `if let` guards (1.95), `assert_matches!` (1.96) or anything else newer than 1.85 — the code would no longer build on the declared minimum. If `rust-version` is absent, the effective minimum for an edition-2024 crate is 1.85; a pinned `rust-toolchain.toml` is the next best indication. Suggest raising `rust-version` explicitly when a newer feature is worth it.
3. **Clippy already does this.** Clippy reads `rust-version` (or `msrv` in `clippy.toml`) and suppresses MSRV-sensitive suggestions. Verified on clippy 0.1.99: with `rust-version = "1.85"`, `x % 3 == 0` produces no `manual_is_multiple_of` warning and a nested `if let … { if … }` produces no `collapsible_if` warning; with `rust-version = "1.99"` both fire (the latter suggesting a `let` chain).
4. **Say "not available in 1.N" only when the release table below proves it.** Every feature in this guide carries the release that stabilized it, verified by compiling on that release and on the one before it. If an API is not in this guide, check its `Stable since` badge in the std docs before claiming it is missing or present.
5. **Edition-dependent behaviour changes silently.** When a crate's edition changed from 2021 to 2024 in the diff (or recently), re-check lock guards in `if let … else`, tail expressions returning borrows of temporaries, `impl Trait` return types, `Box<[T]>::into_iter()`, macro `$e:expr` matchers and `std::env::set_var` calls — see [What Edition 2024 Changes](#what-edition-2024-changes-vs-2021).
6. **Nightly features are never acceptable** in a crate built with stable Rust: `#![feature(...)]` fails with `error[E0554]: #![feature] may not be used on the stable release channel`. See [Do Not Use or Recommend](#do-not-use-or-recommend).

##### Not stable on any toolchain ≤ 1.99 (nightly-only or not yet released)

Each of these fails on 1.99.1 with `error[E0658]` (or "not found"); never suggest them for stable code:

- **`!` as a type** anywhere except as the bare return type of a function (`Option<!>`, `Result<T, !>`, `let x: ! = …`) — stable only from **1.100** (beta). A diverging function `fn f() -> !` is fine on every toolchain. Use `std::convert::Infallible` for "cannot fail".
- **`bool::toggle`** and the **`Allocator`** trait (both listed as stabilized for 1.100 in the beta changelog), and allocator-parameterized collections such as `Vec::new_in` (`allocator_api`, unstable on 1.99).
- **`gen` blocks** (`gen { yield 1; }`), `async gen`, `yield`, coroutines; **`try` blocks** (`try { … }`); `become` tail calls; `super let`.
- **`impl Trait` in type aliases** (TAIT, `type It = impl Iterator<…>;`) and in associated types; **return-type notation** (`T: Trait<method(..): Send>`); **`async fn` in `dyn Trait`** (traits with `async fn` are not dyn-compatible: `error[E0038]`).
- **specialization** (`default fn`), **const traits** (`const trait`, `impl const`, `~const`), trait aliases (`trait A = Clone + Send;`), negative impls, auto traits.
- **`adt_const_params`** (`const S: &'static str` generic parameters; only integers, `bool` and `char` are allowed), `generic_const_exprs`.
- **Default field values** (`struct S { a: u8 = 1 }`), `unsafe` fields, box patterns (`box x`), deref patterns (`deref!(…)`).
- **`f16` / `f128`** primitive types.
- **`#[derive(CoercePointee)]`**, `arbitrary_self_types` (`impl Receiver`), `SyncUnsafeCell`, `portable_simd` (`std::simd`), `std::sync::nonpoison::Mutex`, `std::sync::mpmc`.
- **Library APIs**: `Iterator::intersperse`, `Iterator::array_chunks`, `Iterator::try_collect`, `OnceLock::get_or_try_init`, `Vec::push_within_capacity`, `Ipv4Addr::is_global`, `std::error::Request`/`Error::provide`, `std::cfg_match!` (stabilized under the name **`cfg_select!`** in 1.95).
- **`let` chains in edition 2021** — never available there; the crate must move to 2024.
- **`#![feature(...)]`** of any kind, `cargo +nightly`-only flags (`-Z …`, `cargo -Zminimal-versions`), and Miri as a *build* requirement (Miri itself is a nightly-only tool; using it in CI on a nightly toolchain is fine).

#### What Edition 2024 Changes (vs. 2021)

Edition 2024 was defined by RFC 3501 and shipped with 1.85.0.[^1][^2] The list below covers every item in the Edition Guide, plus the edition-specific behaviour added in later releases. Each example was compiled with `--edition 2021` and `--edition 2024` on the same compiler (1.85.0 and 1.99.1).

| Change | Kind | 2021 behaviour | 2024 behaviour | Migration lint (`rust_2024_compatibility` group) |
|---|---|---|---|---|
| RPIT lifetime capture | semantics | `-> impl Trait` captures only type/const params (and lifetimes named in the bounds) | captures **all** in-scope generic params incl. lifetimes | `impl_trait_overcaptures` (adds `+ use<…>`) |
| `if let` temporary scope | drop order | scrutinee temporaries live until the end of the whole `if let … else` | dropped **before the `else` block** | `if_let_rescope` (rewrites to `match`) |
| Tail-expression temporary scope | drop order | tail-expression temporaries dropped *after* the block's locals | dropped *before* the block's locals | `tail_expr_drop_order` (warn only) |
| `let` chains | new syntax | error | allowed (1.88+) | — |
| Match ergonomics reservations | patterns | `mut`/`ref`/`&` allowed under a non-`move` default binding mode | error | `rust_2024_incompatible_pat` |
| `unsafe extern` blocks | syntax | `extern "C" {}` | `unsafe extern "C" {}` required | `missing_unsafe_on_extern` |
| Unsafe attributes | syntax | `#[no_mangle]` | `#[unsafe(no_mangle)]` (also `export_name`, `link_section`) | `unsafe_attr_outside_unsafe` |
| `unsafe_op_in_unsafe_fn` | lint level | allow | **warn** | `unsafe_op_in_unsafe_fn` |
| References to `static mut` | lint level | `static_mut_refs` warn | **deny** | none (manual) |

##### [2024] RPIT lifetime capture and `use<..>`

In 2024, a return-position `impl Trait` in a free function or inherent method captures every in-scope generic parameter, *including lifetimes*, unless a `use<..>` bound says otherwise. This matches what `async fn`, trait-impl RPITs and RPITIT already did in every edition.[^8]

```rust
// Compiles in 2024. In 2021: error[E0700]: hidden type for `impl Iterator<Item = u32>`
// captures lifetime that does not appear in bounds.
fn evens(v: &Vec<u32>) -> impl Iterator<Item = u32> {
    v.iter().copied().filter(|x| x % 2 == 0)
}

fn main() {
    let v = vec![1, 2, 3, 4];
    println!("{:?}", evens(&v).collect::<Vec<_>>()); // [2, 4]
}
```

The flip side is **over-capturing**: the returned value now borrows its arguments even if the hidden type does not use them, which can create new borrow errors in callers.

```rust
// BAD in 2024: the opaque type captures the lifetime of `s` although `0..n` does not borrow it.
fn len_iter(s: &str) -> impl Iterator<Item = usize> {
    let n = s.len();
    0..n
}

fn main() {
    let mut s = String::from("abc");
    let it = len_iter(&s);
    s.push('d'); // error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
    println!("{}", it.count());
}
```

```rust
// GOOD: precise capturing (works in all editions on any toolchain that supports 2024).
fn len_iter(s: &str) -> impl Iterator<Item = usize> + use<> {
    let n = s.len();
    0..n
}

fn main() {
    let mut s = String::from("abc");
    let it = len_iter(&s);
    s.push('d');
    println!("{}", it.count()); // 3
}
```

Review rules:

- `+ use<>` / `+ use<'a, T>` is the precise way to state captures. `cargo fix --edition` inserts `+ use<…>` wherever 2024 would capture more than 2021 did; reviewers should ask whether each inserted bound is still wanted — dropping it lets the function's implementation borrow arguments later without an API break.
- `use<..>` must list **all** type and const parameters in scope (it can only omit lifetimes). An argument-position `impl Trait` parameter cannot be named; convert it to a named type parameter if the bound must mention it.
- The old workarounds — the `Captures<'a>` trait trick and `+ 'a` "outlives trick" — still compile but are unnecessary in 2024; the outlives trick also imposes a spurious `T: 'a` on callers.
- In **trait** definitions and impls (RPITIT), `use<..>` is accepted from **1.87**; on 1.85/1.86 it is `error: use<...> precise capturing syntax is currently not allowed in return-position impl Trait in traits`.

##### [2024] `if let` temporary scope — the lock-guard fix

In 2021, temporaries created in an `if let` scrutinee (lock guards, `RefCell` borrows) live until the end of the *entire* `if let … else` statement, so the `else` branch still holds them. In 2024 they are dropped before the `else` branch runs.[^9]

```rust
use std::sync::RwLock;

fn ensure_set(value: &RwLock<Option<bool>>) {
    if let Some(x) = *value.read().unwrap() {
        println!("value is {x}");
    } else {
        // 2021: the read guard from the scrutinee is still alive here, so `write()` would deadlock
        //       (try_write reports WouldBlock).
        // 2024: the read guard was dropped before entering `else`.
        match value.try_write() {
            Ok(mut v) => *v = Some(true),
            Err(_) => println!("would deadlock: read guard still held"),
        }
    }
}

fn main() {
    let l = RwLock::new(None);
    ensure_set(&l); // 2021 prints "would deadlock…"; 2024 sets the value
    println!("{:?}", *l.read().unwrap());
}
```

What did **not** change, verified on 1.99 in both editions:

- In the **then-branch** of `if let`, the scrutinee's temporaries are still alive (a `try_lock` on the same mutex fails there).
- **`match`** scrutinee temporaries live until the end of the `match` statement — the classic `match *m.lock().unwrap() { … => m.lock() }` self-deadlock still exists in 2024.
- **`while let`** keeps the scrutinee's temporaries alive for the whole loop body of each iteration.
- A temporary in a plain `let` statement (`let n = m.lock().unwrap().len();`) is dropped at the end of that statement.

```rust
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(Some(1));

    // BAD (any edition): the guard from the scrutinee lives for the whole match.
    match *m.lock().unwrap() {
        Some(_) => println!("in arm, lock free = {}", m.try_lock().is_ok()), // false
        None => {}
    }

    // GOOD: bind the value, end the guard's statement, then branch.
    let current = *m.lock().unwrap();
    match current {
        Some(_) => println!("in arm, lock free = {}", m.try_lock().is_ok()), // true
        None => {}
    }
}
```

`cargo fix --edition` rewrites `if let` with significant-drop scrutinees into `match` to preserve the **2021** behaviour — which re-introduces exactly the deadlock above. Review every such rewrite and revert it to `if let` when the earlier drop is what the code needs.

Per the 1.91 release notes, edition-2024 crates also apply this rescoping to temporaries that the `pin!`, `format_args!`, `write!` and `writeln!` macros create internally in an `if let` scrutinee; before 1.91 those macro-internal temporaries kept the longer lifetime in every edition.[^10]

##### [2024] Tail-expression temporary scope

Temporaries in a block's tail expression are now dropped *before* the block's local variables instead of after them.[^11] This fixes a long-standing borrow error:

```rust
use std::cell::RefCell;

fn len() -> usize {
    let c = RefCell::new("..");
    c.borrow().len() // 2021: error[E0597]: `c` does not live long enough; 2024: OK
}

fn main() {
    println!("{}", len());
}
```

…but it can also break code that relied on a tail temporary outliving its block:

```rust
fn main() {
    // Compiles in 2021; in 2024: error[E0716]: temporary value dropped while borrowed
    let x = { &String::from("1234") }.len();
    println!("{x}");
}
```

```rust
fn main() {
    // GOOD: lift the value into a `let` so temporary lifetime extension applies.
    let s = { &String::from("1234") };
    let x = s.len();
    println!("{x}");
}
```

There is no automatic rewrite; `tail_expr_drop_order` only warns. When a tail expression creates a value with a meaningful `Drop` (a guard, a span, a transaction), review whether the drop now happens earlier than the code assumes.

##### [2024] `let` chains (1.88+)

`&&`-chains of `let` patterns and boolean conditions in `if` and `while` are stable from **1.88** and **only in edition 2024** (the feature depends on the 2024 `if let` rescoping).[^12]

```rust
fn sum_first_two(nums: &[u8]) -> Option<u8> {
    let mut iter = nums.iter();
    if let Some(first) = iter.next()
        && let Some(second) = iter.next()
    {
        first.checked_add(*second)
    } else {
        None
    }
}

fn main() {
    println!("{:?}", sum_first_two(&[1, 2])); // Some(3)
}
```

- `let` may only appear at the top level of the chain: `if let A = a || let B = b` and `if (let A = a)` remain errors.
- Bindings from earlier `let`s are in scope for later conditions, and each `let` may be refutable or irrefutable (`irrefutable_let_patterns` does not fire inside chains since 1.95).
- On 1.85–1.87 a 2024 crate gets `` error[E0658]: `let` expressions in this position are unstable ``. If `rust-version` is below 1.88, keep nested `if let` or use `match`/`let … else`.
- Clippy's `collapsible_if` suggests a let chain only when the MSRV is ≥ 1.88.

##### [2024] Match ergonomics reservations

When a pattern has implicitly dereferenced a reference (the default binding mode is `ref`/`ref mut`), 2024 rejects writing `mut`, `ref`, `ref mut`, `&` or `&mut` on the bindings inside it.[^13] These forms had surprising meanings in 2021 (`mut` silently switched back to by-value binding, a single `&` stripped two layers of references).

```rust
fn main() {
    let pair = &[1u8, 2];
    // let [x, mut y] = pair;  // 2024: error: cannot mutably bind by value within an implicitly-borrowing pattern
    let &[ref x, mut y] = pair; // GOOD: fully explicit pattern, same meaning in every edition
    y += 1;
    println!("{x} {y}"); // 1 3

    let refs = &[&1u8, &2u8];
    // let [&a, b] = refs;     // 2024: error: cannot explicitly dereference within an implicitly-borrowing pattern
    let &[&a, b] = refs;       // GOOD
    println!("{a} {b}");
}
```

The error wording changed between releases (1.85: "binding modifiers may only be written when the default binding mode is `move`"); the rule did not.

##### [2024] `unsafe extern` blocks and `safe` items

Every `extern` block must be written `unsafe extern`; the `unsafe` keyword states that the author vouches for the declared signatures. Items inside can be marked `safe` (callable without `unsafe`) or `unsafe` (the default).[^14]

```rust
unsafe extern "C" {
    // `abs` is defined for every input: expose it as safe.
    pub safe fn abs(x: i32) -> i32;
    // `strlen` requires a valid NUL-terminated pointer: keep it unsafe.
    pub unsafe fn strlen(p: *const std::ffi::c_char) -> usize;
}

fn main() {
    println!("{}", abs(-3)); // no unsafe block needed
    // SAFETY: the C-string literal is NUL-terminated and lives for 'static.
    println!("{}", unsafe { strlen(c"hello".as_ptr()) });
}
```

`extern "C" { … }` without `unsafe` is `error: extern blocks must be unsafe` in 2024. Review rule: **`safe fn` in an extern block is an `unsafe` assertion.** Flag `safe` on any foreign function that takes raw pointers, has preconditions, is not thread-safe, or can invoke undefined behaviour for some inputs; flag `safe static` for anything mutable from C.

##### [2024] Unsafe attributes

`no_mangle`, `export_name` and `link_section` must be written as `#[unsafe(...)]` because they can break soundness through symbol collisions (e.g. `#[export_name = "malloc"]` in safe code crashes the process).[^15]

```rust
// SAFETY: no other object in the final link defines `my_plugin_init`.
#[unsafe(no_mangle)]
pub extern "C" fn my_plugin_init() -> i32 {
    0
}

fn main() {
    println!("{}", my_plugin_init());
}
```

Plain `#[no_mangle]` is `error: unsafe attribute used without unsafe` in 2024. Require a `// SAFETY:` comment explaining why the symbol name is unique. The `unsafe_code` lint fires on these attributes, so `#![forbid(unsafe_code)]` crates cannot use them (1.98 made the lint consistent across all unsafe attributes). Since 1.99, `#[unsafe(no_mangle)]` on a function generic over types or consts is a hard error (a warning before).

##### [2024] `unsafe_op_in_unsafe_fn` warns

The body of an `unsafe fn` is no longer an implicit `unsafe` block: each unsafe operation needs its own `unsafe { … }` (warn-by-default in 2024).[^16] This separates "callers must uphold a contract" from "this line does something unchecked".

```rust
/// Returns the element at `i` without bounds checking.
///
/// # Safety
/// `i` must be less than `x.len()`.
unsafe fn get<T>(x: &[T], i: usize) -> &T {
    // SAFETY: the caller guarantees `i < x.len()`.
    unsafe { x.get_unchecked(i) }
}

fn main() {
    let v = [1, 2];
    // SAFETY: 1 < 2.
    println!("{}", unsafe { get(&v, 1) });
}
```

Treat the warning as an error in reviews (many projects set `unsafe_op_in_unsafe_fn = "deny"` in `[lints.rust]`). An `unsafe fn` must document its contract in a `# Safety` section (Clippy `missing_safety_doc`, on by default).

##### [2024] References to `static mut` are denied

Creating a shared or mutable reference to a `static mut` — including implicitly through method autoref (`NUMS.len()`), formatting (`println!("{X}")`) or `ref` patterns — is `deny(static_mut_refs)` in 2024 (warn in 2021). Merely creating such a reference while another exists is instant undefined behaviour.[^17]

```rust
static mut COUNTER: u32 = 0;

fn main() {
    unsafe {
        COUNTER += 1;          // direct place access: allowed (still racy if threads exist)
        // let r = &COUNTER;   // 2024: error: creating a shared reference to mutable static
        let p = &raw const COUNTER; // raw borrow: allowed
        println!("{}", *p);
    }
}
```

Preferred replacements, in order: no global at all; an atomic (`static COUNTER: AtomicU64`); `static M: Mutex<T>` (`Mutex::new` is `const`); `OnceLock`/`LazyLock` for one-time initialization; raw pointers via `&raw const`/`&raw mut` when FFI requires an address. `cargo fix` cannot migrate these — every `#[allow(static_mut_refs)]` needs a review.

##### [2024] Never-type fallback

When the type of a diverging expression (`panic!()`, `return`, `?` on an error path, `loop {}`) cannot be inferred, 2021 falls back to `()`, 2024 falls back to `!`.[^18] Code that silently relied on `()` stops compiling:

```rust
fn f<T: Default>() -> Result<T, ()> {
    Ok(T::default())
}

fn run() -> Result<(), ()> {
    // f()?;          // 2024: error[E0277]: the trait bound `!: Default` is not satisfied
    f::<()>()?;       // GOOD: state the type
    () = f()?;        // GOOD: alternative
    Ok(())
}

fn main() {
    println!("{:?}", run());
}
```

The same applies to closures that only panic (`run(|| panic!())` where `R: SomeTrait` is implemented for `()`): give the closure an explicit `-> ()`. In 2021 crates this pattern is `error: this function depends on never type fallback being ()` since 1.92 (deny-by-default `dependency_on_unit_never_type_fallback`). From **1.100** the fallback becomes `!` in all editions.

##### [2024] Macro fragment `expr` matches `const {}` and `_`

```rust
macro_rules! example {
    ($e:expr) => { println!("first rule (expr)") };
    (const $e:expr) => { println!("second rule (const)") };
}

fn main() {
    example!(const { 1 + 1 }); // 2021: "second rule (const)"; 2024: "first rule (expr)"
}
```

A `macro_rules!` matcher that relies on `$e:expr` *not* matching `const { … }` or `_` silently picks a different arm in 2024. `cargo fix --edition` rewrites every `$x:expr` to `$x:expr_2021`, which keeps the old behaviour but also makes the macro reject the new expressions; prefer reverting to `expr` unless a later arm really depends on the old matching. Macros are expanded with the edition of the crate that defines them, so a 2021 library macro keeps 2021 matching inside a 2024 crate.

##### [2024] `gen` keyword and reserved guarded strings

- `gen` is a reserved keyword: `fn gen()`, `let gen`, `rng.gen()` must become `r#gen` (the `rand` 0.9+ API renamed `Rng::gen` to `Rng::random` for this reason). `gen` blocks themselves remain unstable.
- `#"foo"#` (a guarded string without `r` prefix) and two or more adjacent `#` (`##`) are reserved and are errors in 2024; they matter only to macros that matched them as separate tokens.[^19]

##### [2024] Prelude adds `Future` and `IntoFuture`

`Future` and `IntoFuture` are in the 2024 prelude, so `use std::future::Future;` is redundant. Because traits in the prelude participate in method resolution, a call to a crate-local trait method named `poll` or `into_future` can become ambiguous or silently resolve to the `Future` method instead (verified: with a blanket `trait MyPoller { fn poll(&self) }`, `pin!(async {}).poll()` calls `MyPoller::poll` in 2021 but resolves to `Future::poll` in 2024 and fails with `error[E0061]: this method takes 1 argument`). The fix is fully qualified syntax (`<_ as MyPoller>::poll(&x)`).[^20] (`AsyncFn`, `AsyncFnMut`, `AsyncFnOnce` were added to the prelude of **all** editions in 1.85.)

##### [2024] `Box<[T]>::into_iter()` yields values

```rust
fn main() {
    let b: Box<[String]> = vec![String::from("a"), String::from("b")].into_boxed_slice();
    // 2021: `b.into_iter()` resolves through auto-deref to `<&[String]>::into_iter` and yields &String.
    // 2024: it calls `<Box<[String]> as IntoIterator>::into_iter` and yields String (by value).
    let owned: Vec<String> = b.into_iter().collect();
    println!("{owned:?}");
}
```

In 2021 the same line is `error[E0277]: a value of type Vec<String> cannot be built from an iterator over elements of type &String`. Code that only *reads* through `.into_iter()` on a boxed slice may compile in both editions with different item types; use `.iter()` when references are meant. `for x in boxed_slice` iterates by value in all editions. (`Box<[T; N]>` gained `IntoIterator` impls in 1.99; `.into_iter()` on it yields values in every edition because auto-deref reaches the array's by-value impl.)

##### [2024] `std::env::set_var` / `remove_var` are `unsafe`

On most Unix platforms, modifying the environment while another thread reads it (including via `getenv` inside libc, DNS resolution, or time-zone code) is undefined behaviour. In 2024 both functions are `unsafe fn`.[^21]

```rust
fn main() {
    // SAFETY: called at the very start of `main`, before any thread is spawned
    // and before any library that may read the environment from another thread is initialized.
    unsafe { std::env::set_var("APP_MODE", "test") };
    println!("{:?}", std::env::var("APP_MODE"));
}
```

`cargo fix --edition` wraps calls in `unsafe { … }` with a `// TODO`/`FIXME: Audit that the environment access only happens in single-threaded code.` comment; such a wrapper without an actual audit is a review finding. In async services (`#[tokio::main]` has already started worker threads) and in tests (the libtest harness runs tests on several threads), `set_var` is almost never sound — pass configuration explicitly, or use `Command::env` for child processes.

##### [2024] Cargo: resolver 3, manifest keys, inherited `default-features`

- `edition = "2024"` implies **`resolver = "3"`**, which makes dependency resolution **MSRV-aware** (`incompatible-rust-versions = "fallback"`): Cargo prefers dependency versions whose `rust-version` is compatible with the package's `rust-version` (or with the running toolchain when none is set).[^22] Verified: with `rust-version = "1.85"` and `time = "0.3"`, resolver 3 locks `time 0.3.45` ("available: v0.3.55, requires Rust 1.88.0"); an edition-2021 package locks 0.3.55.
- **Virtual workspaces do not get the edition default.** A root `Cargo.toml` with only `[workspace]` defaults to `resolver = "1"` and Cargo warns: "virtual workspace defaulting to `resolver = "1"` despite one or more workspace members being on edition 2024". Always set `[workspace] resolver = "3"` explicitly.
- `[project]`, `default_features`, `dev_dependencies`, `build_dependencies`, `crate_type`, `proc_macro` are rejected (e.g. "`dev_dependencies` is unsupported as of the 2024 edition; instead use `dev-dependencies`").[^23]
- `{ workspace = true, default-features = false }` when the workspace entry enables default features: ignored with a warning before 2024; **an error on 1.85–1.98**; on **1.99+** the member's setting overrides the workspace (Cargo feature unification can still turn defaults back on if another member enables them).[^24]
- `rust-version` must be ≥ 1.85 in a 2024 package.

##### [2024] Rustdoc: merged doctests

Doctests of a 2024 crate are compiled into one binary (each test still runs in its own process), which is much faster.[^25] Tests that depend on their own crate layout break: `std::panic::Location::caller().line()` and `std::any::type_name::<T>()` give different results (verified: `rust_out::main::_doctest_main_src_lib_rs_1_0::Foo` in 2021 vs `doctest_bundle_2024::__doctest_0::main::Foo` in 2024). Mark such examples ```` ```standalone_crate ````. Doctests with `compile_fail`, an `edition` tag, crate-level attributes (`#![…]`) or `#[global_allocator]` are never merged. Paths in `include_str!`/`include_bytes!` inside Markdown pulled in with `#![doc = include_str!("../README.md")]` are resolved relative to the Markdown file in 2024.

##### [2024] rustfmt style edition

`cargo fmt` uses the package edition as the **style edition**; rustfmt invoked directly (editor format-on-save) defaults to style edition 2015. Style edition 2024 changes import sorting to "version sorting" (`NonZeroU8, NonZeroU16, NonZeroU32, NonZeroU64` instead of `NonZeroU16, NonZeroU32, NonZeroU64, NonZeroU8`; `self, Read, Write, stdout`), formats `((1,),).0.0` without the old extra space, and fixes many comment/indentation quirks.[^26] Add a `rustfmt.toml` with `style_edition = "2024"` so editors and CI agree; a diff that only reorders imports this way is formatting churn, not a code change.

#### What's New per Release, 1.86 → 1.99

Everything here is edition-independent unless marked [2024], and requires at least the stated release. All items were compiled on the stated release and failed on the release before it.[^6]

##### Available from 1.85 (every edition-2024 toolchain)

- **Async closures** `async |x| …` and the `AsyncFn`, `AsyncFnMut`, `AsyncFnOnce` traits. Unlike `|x| async move { … }`, an async closure can return a future that *borrows from the closure's captures*, and `F: AsyncFn(u8) -> u8` is the natural bound for "async callback".

```rust
use std::task::{Context, Poll, Waker};

async fn call_twice<F: AsyncFn(u8) -> u8>(f: F) -> u8 {
    f(1).await + f(2).await
}

fn main() {
    let offset = vec![10u8];
    let add = async |x: u8| x + offset[0]; // borrows `offset`
    let mut fut = std::pin::pin!(call_twice(add));
    let mut cx = Context::from_waker(Waker::noop());
    if let Poll::Ready(v) = fut.as_mut().poll(&mut cx) {
        println!("{v}"); // 23
    }
}
```

- `#[diagnostic::do_not_recommend]` on trait impls (better error messages for library authors); `std::ptr::fn_addr_eq` for an explicit (still unreliable) function-pointer comparison; `u32::midpoint`, `f64::midpoint`; `Waker::noop()`.

##### 1.86

- **Trait upcasting**: `&dyn Sub` / `Box<dyn Sub>` / `Arc<dyn Sub>` coerce to the supertrait object. Previously this needed an `as_super(&self) -> &dyn Super` helper method — such helpers can be removed once the MSRV is ≥ 1.86.

```rust
trait Shape { fn name(&self) -> &'static str; }
trait Polygon: Shape { fn sides(&self) -> u32; }
struct Square;
impl Shape for Square { fn name(&self) -> &'static str { "square" } }
impl Polygon for Square { fn sides(&self) -> u32 { 4 } }

fn describe(s: &dyn Shape) -> &'static str { s.name() }

fn main() {
    let p: Box<dyn Polygon> = Box::new(Square);
    println!("{} has {} sides", describe(&*p), p.sides()); // upcast &dyn Polygon -> &dyn Shape
}
```

- `#[target_feature(enable = "avx2")]` on a **safe** `fn`: calling it from code that does not itself enable the feature still requires `unsafe` (the caller asserts the CPU supports it, e.g. after `is_x86_feature_detected!`).
- **`get_disjoint_mut`** on slices and `HashMap`: several `&mut` at once, with an error (slices) or a panic (`HashMap`, on duplicate keys) instead of `split_at_mut` gymnastics.

```rust
use std::collections::HashMap;

fn main() {
    let mut v = [1, 2, 3];
    if let Ok([a, b]) = v.get_disjoint_mut([0, 2]) {
        std::mem::swap(a, b);
    }
    assert!(v.get_disjoint_mut([1, 1]).is_err()); // overlapping indices are rejected
    println!("{v:?}"); // [3, 2, 1]

    let mut accounts = HashMap::from([("alice", 100), ("bob", 5)]);
    let [Some(from), Some(to)] = accounts.get_disjoint_mut(["alice", "bob"]) else {
        panic!("missing account");
    };
    *from -= 10;
    *to += 10;
    println!("{accounts:?}");
}
```

- `Vec::pop_if(|x| …)`, `Once::wait`, `OnceLock::wait` (block until another thread initialized it), `f64::next_up`/`next_down`.

#### Ownership, Borrowing & Lifetimes

##### Core rules a reviewer applies

- One owner per value; moving transfers ownership; `Copy` types are copied instead. At any time either **one `&mut T`** or **any number of `&T`** — and a `&mut` is a promise of exclusivity that `unsafe` code must never forge.
- Prefer borrowing parameters: `&str` over `&String`, `&[T]` over `&Vec<T>`, `&Path` over `&PathBuf`, `impl AsRef<Path>` for convenience APIs (Clippy `ptr_arg`). Take ownership (`String`, `Vec<T>`) only when the function stores or consumes the value; then callers can move instead of clone.
- `clone()` to silence the borrow checker is a smell in hot paths and in long-lived structures, acceptable at cold boundaries. Look for `.clone()` of `String`/`Vec` inside loops, `Arc<Mutex<…>>` cloned per iteration, or `to_owned()` immediately borrowed again.
- Returning references: a function can only return a reference derived from its arguments (or `'static`). `fn f() -> &str` returning a local is a compile error; the fix is returning `String` or `Cow<'_, str>`.
- `Cow<'a, str>` avoids allocation when a value is usually borrowed but sometimes modified.

```rust
use std::borrow::Cow;

fn normalize(input: &str) -> Cow<'_, str> {
    if input.contains('\t') {
        Cow::Owned(input.replace('\t', "    ")) // allocate only when needed
    } else {
        Cow::Borrowed(input)
    }
}

fn main() {
    println!("{}", normalize("no tabs"));
    println!("{}", normalize("a\tb"));
}
```

##### Common borrow-checker pitfalls in review

```rust
use std::collections::HashMap;

fn main() {
    let mut counts: HashMap<String, u32> = HashMap::new();
    let words = ["a", "b", "a"];

    // BAD: two lookups, and `get` + `insert` cannot hold a reference across the insert.
    for w in words {
        if let Some(c) = counts.get_mut(w) {
            *c += 1;
        } else {
            counts.insert(w.to_string(), 1);
        }
    }

    // GOOD: the entry API does one lookup.
    let mut counts2: HashMap<&str, u32> = HashMap::new();
    for w in words {
        *counts2.entry(w).or_insert(0) += 1;
    }
    println!("{counts:?} {counts2:?}");
}
```

- **Mutating a collection while iterating it** does not compile (`for x in &v { v.push(..) }`); the fixes are `retain`, `extract_if` (1.87+), collecting indices first, or building a new collection.
- **Self-referential structs** (a struct holding a value and a reference into it) cannot be expressed with plain references. Store indices/ranges instead, or use `Arc`/arena crates (`ouroboros`/`self_cell` exist, but question the need first). Any `unsafe` "self-referential" trick without `Pin` is almost always unsound.
- **Interior mutability** (`Cell`, `RefCell`, `Mutex`, `RwLock`, atomics, `OnceCell`/`OnceLock`) moves borrow checks to runtime: `RefCell::borrow_mut` **panics** when a borrow is outstanding (`try_borrow_mut` returns `Err`). A `RefCell` borrow held across a callback is a reentrancy panic waiting to happen.
- **Two-phase borrows** let `v.push(v.len())` compile; `v.push(v.pop().unwrap())`-style patterns that need a second `&mut` do not. Do not "fix" such errors with `unsafe`.
- **Lifetime elision**: in `fn f(&self, x: &str) -> &str` the output borrows from `self`, not `x`. If the result actually comes from `x`, annotate `fn f<'a>(&self, x: &'a str) -> &'a str`. The 1.89 lint `mismatched_lifetime_syntaxes` flags signatures that elide a lifetime in one position and name it in another (`fn wrap<'a, T>(x: &'a T) -> Ref<T>` → write `Ref<'a, T>`).
- `'static` bounds (`T: 'static`) mean "contains no non-static borrows", not "lives forever"; `String` is `'static`. Spawned threads and `tokio::spawn` require `'static` futures — use `thread::scope` (or `Arc`) instead of leaking (`Box::leak`) to satisfy the bound.

##### Smart pointers

| Type | Use | Pitfall |
|---|---|---|
| `Box<T>` | single owner on the heap, recursive types, trait objects | `Box<Vec<T>>` double indirection; `Box::leak` for "global" config leaks permanently |
| `Rc<T>` | shared ownership, single thread | not `Send`; cycles leak (use `Weak` for back-references) |
| `Arc<T>` | shared ownership across threads | `Arc<T>` is `Send`/`Sync` only if `T: Send + Sync`; `Arc<RefCell<T>>` is not `Sync` |
| `Arc<Mutex<T>>` / `Arc<RwLock<T>>` | shared mutable state | lock held too long, across `.await`, or across calls that re-lock |
| `Weak<T>` | non-owning back-reference | `upgrade()` returns `None` after the last strong ref drops — handle it |

`Rc::clone(&a)` / `Arc::clone(&a)` instead of `a.clone()` makes it obvious that only a reference count is incremented (Clippy `clone_on_ref_ptr`, restriction group).

#### Temporaries, Drop Order & Guards

Drop order is observable behaviour whenever `Drop` releases a lock, commits/rolls back a transaction, flushes a buffer, ends a tracing span, or joins a thread.

- Locals are dropped in **reverse declaration order** at the end of their scope; struct fields in **declaration order**; temporaries at the end of the enclosing statement unless extended. In 2024, tail-expression temporaries are dropped before the block's locals and `if let` scrutinee temporaries before `else` (see above).
- **`let _ = expr;` drops the value immediately; `let _guard = expr;` keeps it until the end of the scope.** For lock guards, `let _ = m.lock().unwrap();` is `error: non-binding let on a synchronization lock` (deny-by-default `let_underscore_lock`) — for other RAII values (spans, `tempfile` guards, `scopeguard`) it compiles and silently does nothing useful.

```rust
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(0);
    {
        let _guard = m.lock().unwrap(); // held until the end of this block
        println!("locked: {}", m.try_lock().is_err()); // true
    }
    println!("released: {}", m.try_lock().is_ok()); // true
}
```

- `drop(guard)` ends a guard early; prefer an explicit block when several statements need the lock.
- `std::mem::forget` and reference cycles prevent `Drop` from running; code must never rely on `Drop` for **soundness** (that is why `thread::scope` exists instead of the old scoped-thread guard APIs).
- `match`/`while let` scrutinee temporaries live through the arms/body in every edition (see the `if let` section) — `match self.state.lock().unwrap().take() { … }` holds the lock in every arm.
- Since 1.98, `assert_eq!`/`assert_ne!` wrap their operands in their own temporary scope, so temporaries created in the operands do not outlive the assertion.

#### Error Handling

##### `Result`, `?` and `Option`

- Fallible operations return `Result<T, E>`; absence is `Option<T>`. Never use sentinel values (`-1`, `""`, `0`) for errors.
- `?` converts the error with `From::from` and returns early; in `Option`-returning functions it propagates `None`. `?` in `main` works when `main` returns `Result<(), E>` with `E: Debug` (prints `Error: {e:?}` and exits with code 1) — use `std::process::ExitCode` or `anyhow::Result<()>` for nicer output.
- Convert between `Option` and `Result` with `ok_or`/`ok_or_else` (lazy — use it when building the error allocates), `ok()`, `transpose()`; for booleans use `bool::then`/`then_some` and, from 1.98, `bool::ok_or`.
- `let … else` keeps the happy path unindented:

```rust
fn parse_port(s: &str) -> Result<u16, String> {
    let Some(port) = s.strip_prefix("port=") else {
        return Err(format!("expected `port=<n>`, got {s:?}"));
    };
    port.parse::<u16>().map_err(|e| format!("invalid port {port:?}: {e}"))
}

fn main() {
    println!("{:?}", parse_port("port=8080"));
    println!("{:?}", parse_port("8080"));
    println!("{:?}", parse_port("port=99999"));
}
```

##### Library errors: typed enums (`thiserror`)

Libraries expose **structured, matchable** errors; applications **report** them. `thiserror` (2.x, current 2.0.21) derives `Display`, `Error`, `source()` and `From`:

```rust
// needs: thiserror
use std::num::ParseIntError;

#[derive(Debug, thiserror::Error)]
#[non_exhaustive]
pub enum ConfigError {
    #[error("config file {path} could not be read")]
    Read {
        path: String,
        #[source]
        source: std::io::Error,
    },
    #[error("invalid port {0}")]
    BadPort(u32),
    #[error(transparent)]
    Parse(#[from] ParseIntError),
}

pub fn read_port(text: &str) -> Result<u16, ConfigError> {
    let n: u32 = text.trim().parse()?; // ParseIntError -> ConfigError::Parse via #[from]
    u16::try_from(n).map_err(|_| ConfigError::BadPort(n))
}

fn main() {
    println!("{:?}", read_port("70000").map_err(|e| e.to_string())); // Err("invalid port 70000")
    println!("{:?}", read_port("x").map_err(|e| e.to_string()));     // Err("invalid digit found in string")
}
```

Review points:

- **Do not include the source's message in the outer `Display`** when you also return it from `source()` (`#[source]`/`#[from]`): reporters that walk the chain print it twice. `#[error(transparent)]` forwards both `Display` and `source` to the inner error.
- Add `#[non_exhaustive]` to public error enums so new variants are not a breaking change; matching code then needs a `_` arm.
- Keep error types `Send + Sync + 'static` so they cross threads and fit into `anyhow::Error`/`Box<dyn Error + Send + Sync>`.
- Do not expose dependency error types in the public API unless the dependency is part of the API anyway (a major version bump of the dependency becomes a breaking change for you).
- `impl From<E>` for every conceivable `E` makes `?` convert silently and loses context; prefer `map_err` with a variant that carries context (the path, the key, the request id).

##### Application errors: `anyhow` (or `eyre`)

```rust
// needs: anyhow
use anyhow::{bail, Context, Result};

fn load_port(path: &str) -> Result<u16> {
    let text = std::fs::read_to_string(path)
        .with_context(|| format!("reading config {path}"))?; // lazy context
    let port: u16 = text.trim().parse().context("parsing port")?;
    if port < 1024 {
        bail!("port {port} is privileged");
    }
    Ok(port)
}

fn main() {
    let err = load_port("/nonexistent/app.conf").unwrap_err();
    println!("{err}");    // reading config /nonexistent/app.conf
    println!("{err:#}");  // reading config /nonexistent/app.conf: No such file or directory (os error 2)
    for cause in err.chain() {
        println!("  caused by: {cause}");
    }
}
```

- Log errors with `{:#}` (anyhow) or by walking `source()`; `{}` alone shows only the outermost context and loses the root cause.
- Use `.with_context(|| format!(…))` rather than `.context(format!(…))` on hot paths (the closure only runs on error).
- `anyhow` in a **library's public API** is a review finding: callers cannot match on the failure kind.
- `Box<dyn std::error::Error + Send + Sync>` is the dependency-free equivalent for small binaries.
- `core::error::Error` is the same trait as `std::error::Error`; `no_std` libraries implement the `core` path.

##### Panics vs. errors

Panics are for **bugs** (violated invariants), not for expected failures (bad input, I/O, network). In library code, every `unwrap()`, `expect()`, indexing `v[i]`, slicing `&s[a..b]`, `RefCell::borrow_mut`, integer division and `.try_into().unwrap()` is a potential panic that callers cannot handle.

- `expect("…")` messages should state the **invariant** that makes the call infallible (`expect("regex literal is valid")`), not restate the failure.
- Document panics in a `# Panics` section (Clippy `missing_panics_doc`, pedantic). Clippy `unwrap_used`/`expect_used`/`indexing_slicing`/`panic` (restriction group) can enforce a no-panic policy in libraries.
- `catch_unwind` is not an error-handling mechanism: it does not catch panics with `panic = "abort"`, does not catch aborts or `std::process::exit`, and requires `UnwindSafe` reasoning. Use it only at FFI boundaries (a panic unwinding out of an `extern "C" fn` aborts the process) and in thread-pool workers.
- `Mutex` poisoning: after a thread panics while holding a `std::sync::Mutex`, `lock()` returns `Err(PoisonError)`. `lock().unwrap()` propagates the panic (usually the right call); recover deliberately with `PoisonError::into_inner` and `Mutex::clear_poison` only when the protected data is known to be consistent (see Concurrency).

#### Panics, Integer Overflow & Casts

##### Overflow depends on the build profile

Arithmetic overflow on `+ - * ` and `abs`/`neg` **panics in debug builds** (`overflow-checks` on) and **wraps silently in release builds** (the `release` profile sets `overflow-checks = false`). Division by zero and `i32::MIN / -1` panic in every profile. Verified on 1.99:

```rust
fn main() {
    let x: u8 = std::hint::black_box(250);
    let r = std::panic::catch_unwind(|| x + 10);
    println!("x + 10 -> {r:?}"); // debug: Err(panic) ; release (-O): Ok(4)

    println!("{:?}", x.checked_add(10));     // None        — handle overflow as a value
    println!("{}", x.wrapping_add(10));      // 4           — modular arithmetic is intended
    println!("{}", x.saturating_add(10));    // 255         — clamp
    println!("{:?}", x.overflowing_add(10)); // (4, true)
    println!("{:?}", std::panic::catch_unwind(|| x.strict_add(10)).is_err()); // true in every profile (1.91+)
}
```

Review rules:

- Arithmetic on untrusted sizes, lengths, offsets, prices or timestamps must use `checked_*` (or `strict_*` when overflow is a bug and must panic in release too). A size computation that wraps in release (`len * size_of::<T>()`) followed by an allocation and `unsafe` copy is a memory-safety bug.
- Consider `[profile.release] overflow-checks = true` for services where a panic is preferable to silent corruption.
- `Wrapping<T>` / `Saturating<T>` make the intent part of the type.
- `i32::abs(i32::MIN)` overflows (panics in debug, returns `i32::MIN` in release); use `unsigned_abs()` or `checked_abs()`.

##### `as` casts are lossy and silent

```rust
fn main() {
    println!("{}", 300i32 as u8);        // 44   — truncation
    println!("{}", -1i32 as u32);        // 4294967295 — reinterpretation
    println!("{}", 1e10f64 as i32);      // 2147483647 — float->int saturates
    println!("{}", f64::NAN as i32);     // 0    — NaN becomes 0
    println!("{:?}", u8::try_from(300i32)); // Err(TryFromIntError(PosOverflow)) — GOOD
}
```

Use `From`/`TryFrom` (`u64::from(x)`, `u8::try_from(x)?`) for integer conversions, `cast_signed`/`cast_unsigned` (1.87+) when reinterpretation is intended, and reserve `as` for float conversions and documented truncation. Clippy pedantic lints `cast_possible_truncation`, `cast_sign_loss`, `cast_possible_wrap`, `cast_lossless` flag them. `ptr as usize` and `usize as *const T` lose provenance — use `ptr.addr()`, `ptr::with_exposed_provenance`, `ptr::without_provenance` (strict-provenance APIs, stable long before 1.85).

##### Panicking std APIs to watch

| Expression | Panics when | Non-panicking form |
|---|---|---|
| `v[i]`, `&v[a..b]` | out of bounds / `a > b` | `v.get(i)`, `v.get(a..b)` |
| `&s[a..b]` on `str` | out of bounds **or not on a char boundary** | `s.get(a..b)`, `floor_char_boundary` (1.91+) |
| `x / y`, `x % y` (integers) | `y == 0`, `MIN / -1` | `checked_div`, `checked_rem` |
| `Duration - Duration` | negative result | `checked_sub`, `saturating_sub` (note: `Instant - Instant` does not panic, it saturates to zero — a clock-skew bug can hide behind it) |
| `RefCell::borrow_mut` | already borrowed | `try_borrow_mut` |
| `Vec::with_capacity(n)`, `vec![x; n]` | capacity overflow; huge `n` aborts on OOM | validate `n` from untrusted input |
| `slice::sort_by` / `sort_unstable_by` | comparator is not a total order (the sort may detect it and panic) | `f64::total_cmp`, consistent `Ord` |
| `HashMap::get_disjoint_mut` | duplicate keys | dedupe keys first |
| `iter::repeat(x).count()` / `.last()` | always (1.92+; looped forever before) | do not call on infinite iterators |
| `.unwrap()` on `Mutex::lock()` | lock poisoned | handle `PoisonError` deliberately |

Sorting floats: `v.sort_by(|a, b| a.partial_cmp(b).unwrap())` panics on NaN; a comparator like `unwrap_or(Ordering::Less)` violates total order and can make the sort panic (verified on 1.99). Use `v.sort_by(f64::total_cmp)`.

#### Unsafe Code & Soundness

`unsafe` does not switch off the borrow checker; it allows five extra operations (dereferencing raw pointers, calling `unsafe` functions including FFI, accessing `static mut`, implementing `unsafe` traits, accessing `union` fields) and makes the author responsible for upholding Rust's rules. A **sound** safe API can never cause undefined behaviour (UB), whatever safe code calls it — "callers will not do that" is not an argument.

##### Required discipline

- Every `unsafe { … }` block has a `// SAFETY:` comment directly above it that proves each precondition of each unsafe operation inside (Clippy `undocumented_unsafe_blocks`, restriction group — enable it for crates with `unsafe`).
- Every `unsafe fn` and `unsafe trait` has a `# Safety` doc section stating the caller's obligations (Clippy `missing_safety_doc`, on by default).
- [2024] Unsafe operations inside an `unsafe fn` need their own `unsafe {}` block (`unsafe_op_in_unsafe_fn` warns).
- Keep `unsafe` blocks minimal and encapsulate them in a small module whose **safe** API maintains the invariants; fields that the invariants depend on must be private.
- `#![forbid(unsafe_code)]` (or `[lints.rust] unsafe_code = "forbid"`) in crates that need no `unsafe`; it also rejects unsafe attributes such as `#[unsafe(no_mangle)]`.
- Run tests under **Miri** (`cargo +nightly miri test`; a nightly-only tool) for crates with `unsafe` — it detects use-after-free, out-of-bounds, invalid values, data races and aliasing violations (Stacked/Tree Borrows) that ordinary tests miss.[^28]

##### Undefined behaviour checklist

Each of these is UB even if "it works in tests":

- Creating a `&T`/`&mut T` that is null, dangling, misaligned, or points to an invalid value — *creating* it is enough, reading is not required. Two live `&mut` to the same place, or a `&mut` while a `&` is live (this is why `&STATIC_MUT` is denied in 2024).
- Mutating through a `&T` (casting `&T` to `*mut T` and writing) unless the data is inside an `UnsafeCell` (`Cell`, `RefCell`, `Mutex`, atomics are built on it). rustc's deny lint `invalid_reference_casting` catches the obvious cases.
- Producing an invalid value: a `bool` other than 0/1, a `char` outside Unicode scalar values, an invalid enum discriminant, a null `&T`/`Box`/`fn`, uninitialized memory read as an integer. `mem::zeroed::<&T>()` is UB (`invalid_value` warns); use `MaybeUninit<T>` and `assume_init` only after full initialization.
- Data races (unsynchronized concurrent access with at least one write) — including through `static mut` and through `unsafe impl Sync` on a type that is not actually thread-safe.
- Calling a function with the wrong ABI/signature (wrong `extern` declaration), unwinding out of an `extern "C" fn` (the runtime aborts the process — still a bug), violating a `#[target_feature]` precondition.
- `transmute` between types with different validity or layout (e.g. `Vec<T>` ↔ `Vec<U>`, `&[u8]` → `&[u32]` with misalignment, integer → pointer: use `ptr::with_exposed_provenance`, lint `integer_to_ptr_transmutes`, 1.91+). Default `repr(Rust)` layout is unspecified and changes between compiler versions (1.97 changed some enum encodings).
- `slice::from_raw_parts(ptr, len)` with a `ptr` that is null/unaligned even when `len == 0`, or `len * size_of::<T>() > isize::MAX`.
- `String::from_utf8_unchecked` / `str::from_utf8_unchecked` on non-UTF-8 bytes.
- `Pin` violations: moving a `!Unpin` value after pinning it (the documented safety invariants of `Pin::new_unchecked` were adjusted in 1.99).

```rust
/// A fixed-capacity stack buffer; the invariant is `len <= N` and `buf[..len]` is initialized.
pub struct StackVec<T, const N: usize> {
    buf: [std::mem::MaybeUninit<T>; N],
    len: usize,
}

impl<T, const N: usize> StackVec<T, N> {
    pub fn new() -> Self {
        Self { buf: [const { std::mem::MaybeUninit::uninit() }; N], len: 0 }
    }

    pub fn push(&mut self, value: T) -> Result<(), T> {
        if self.len == N {
            return Err(value);
        }
        self.buf[self.len].write(value);
        self.len += 1;
        Ok(())
    }

    pub fn as_slice(&self) -> &[T] {
        // SAFETY: the invariant guarantees the first `len` elements are initialized,
        // and `MaybeUninit<T>` has the same layout as `T`.
        unsafe { std::slice::from_raw_parts(self.buf.as_ptr().cast::<T>(), self.len) }
    }
}

impl<T, const N: usize> Drop for StackVec<T, N> {
    fn drop(&mut self) {
        for slot in &mut self.buf[..self.len] {
            // SAFETY: slots below `len` are initialized and dropped exactly once here.
            unsafe { slot.assume_init_drop() };
        }
    }
}

fn main() {
    let mut s: StackVec<String, 2> = StackVec::new();
    s.push("a".into()).unwrap();
    s.push("b".into()).unwrap();
    assert!(s.push("c".into()).is_err());
    println!("{:?}", s.as_slice());
}
```

Review heuristics for `unsafe`:

- A `pub` field or a safe `pub fn` that can break the invariant (`set_len`-like methods) makes the whole module unsound.
- `unsafe impl Send/Sync for T {}` needs a justification of why every `&T` access from multiple threads is synchronized; wrappers around raw pointers or `Rc` are the usual culprits.
- Panics inside `unsafe` code can leave invariants broken while `Drop` still runs (e.g. `len` incremented before the write). Update bookkeeping only after the operation that can panic.
- `Vec::set_len` without initializing the new elements; `Vec::from_raw_parts` with a pointer not allocated by `Vec` with the same element type and capacity (prefer `Vec::into_raw_parts` 1.93+/`into_parts` 1.99+ round-trips).
- `ptr::copy_nonoverlapping` on overlapping ranges; `ptr::read` of a value that is later dropped again (double drop).

#### FFI

- [2024] Declarations live in `unsafe extern "C" { … }`; mark an item `safe` only when every possible argument is valid (no pointers, no global state, no preconditions).
- Use `core::ffi::{c_int, c_char, c_void, CStr}` and `std::ffi::CString`; `c_char` is `i8` or `u8` depending on the target (on many ARM/RISC-V targets it is unsigned) — never hard-code `i8`. Since 1.98 the warn lint `c_void_returns` flags `-> c_void` (C `void` returns are `()` in Rust).
- `CString::new(s)?` fails on interior NUL bytes; `c"literal"` gives a `&'static CStr`. `CString::as_ptr()` on a temporary (`CString::new(x)?.as_ptr()`) dangles immediately (`dangling_pointers_from_temporaries` warns).
- Types crossing the boundary need `#[repr(C)]` (or `#[repr(transparent)]` for newtypes); `bool` is C `_Bool`; Rust enums with fields have no C layout unless `repr(C)`/`repr(u8)`. Receiving an enum from C whose value may be outside the declared variants is UB — receive an integer and convert with `TryFrom`.
- Ownership across FFI: memory allocated by Rust must be freed by Rust (`Box::into_raw` → `Box::from_raw` in a Rust `free` function), memory from C by C's allocator.
- Panics must not unwind across `extern "C"`: such a panic aborts the process. Wrap callbacks in `std::panic::catch_unwind` and convert to an error code, or declare `extern "C-unwind"` when unwinding through foreign frames is intended.
- [2024] Exported symbols use `#[unsafe(no_mangle)]` / `#[unsafe(export_name = "…")]`; the 1.98 deny lint `invalid_runtime_symbol_definitions` rejects definitions of `memcpy`, `strlen`, etc. with mismatching signatures.
- Prefer generated bindings (`bindgen`, `cbindgen`) over hand-written declarations; a wrong signature is UB that no compiler check catches.
- C-variadic **definitions** (`args: ...` in a Rust function body) need 1.99; *calling* C variadic functions such as `printf` declared in an `extern` block has always been possible.
- Upgrade to **1.99.1**: it fixes a miscompilation of FFI `bool` return values on x86_64.

#### Concurrency

##### `Send` and `Sync`

- `T: Send` — ownership may move to another thread. `T: Sync` — `&T` may be shared across threads (`T: Sync` ⇔ `&T: Send`). Both are auto traits derived from the fields.
- Not `Send`: `Rc<T>`, raw pointers (by default), `MutexGuard` (it must be unlocked on the locking thread), `RefCell` borrows. Not `Sync`: `Cell<T>`, `RefCell<T>`, `Rc<T>`. Since 1.98, `std::env::Vars`/`VarsOs` are neither.
- A `std::thread::spawn`/`tokio::spawn` error mentioning `Rc` or `MutexGuard` "cannot be sent between threads safely" must be fixed structurally (use `Arc`, drop the guard earlier), never with `unsafe impl Send`.

##### Threads and scoped threads

```rust
use std::thread;

fn parallel_sum(data: &[u64]) -> u64 {
    let mid = data.len() / 2;
    let (left, right) = data.split_at(mid);
    // Scoped threads may borrow from the stack; all are joined before `scope` returns.
    thread::scope(|s| {
        let h = s.spawn(|| left.iter().sum::<u64>());
        let r: u64 = right.iter().sum();
        h.join().expect("worker panicked") + r
    })
}

fn main() {
    let v: Vec<u64> = (1..=100).collect();
    println!("{}", parallel_sum(&v)); // 5050
}
```

- A `JoinHandle` dropped without `join()` detaches the thread; its panic is lost. Join and propagate.
- `thread::Builder::new().name(…).stack_size(…)` names threads (names show up in panic messages and debuggers); since 1.91 a failure to set the stack size returns an error instead of panicking.

##### `Mutex`, `RwLock` and poisoning

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let state = Arc::new(Mutex::new(vec![1]));
    let s2 = Arc::clone(&state);
    let _ = thread::spawn(move || {
        let mut v = s2.lock().unwrap();
        v.push(2);
        panic!("crashed mid-update"); // poisons the mutex
    })
    .join();

    println!("poisoned: {}", state.is_poisoned()); // true
    let recovered = match state.lock() {
        Ok(g) => g,
        // Only recover when the data is valid regardless of where the panic happened.
        Err(poisoned) => poisoned.into_inner(),
    };
    println!("{:?}", *recovered); // [1, 2]
    drop(recovered);
    state.clear_poison();
}
```

- `lock().unwrap()` is the conventional choice: a poisoned lock means an invariant may be broken, so propagating the panic is correct for most code. Silently ignoring poison (`unwrap_or_else(|e| e.into_inner())` everywhere) hides corruption — require a comment explaining why the data is still consistent.
- Keep critical sections short; never call user callbacks, perform I/O, or `.await` while holding a `std::sync::Mutex` guard.
- `std::sync::Mutex` is **not reentrant**: locking it again on the same thread deadlocks or panics.
- Lock ordering: when two locks are taken, every code path must take them in the same order.
- `RwLock` gives no fairness or writer-preference guarantee across platforms; a steady stream of readers can starve writers. Since 1.92, `RwLockWriteGuard::downgrade` converts a write guard to a read guard without a gap.
- `parking_lot` locks do not poison and are smaller; the semantic difference (no poisoning) must be intentional.
- `Mutex::new`, `RwLock::new`, `Condvar::new`, `OnceLock::new` and `LazyLock::new` are `const`, so `static` locks need no lazy initialization crate.
- `Condvar::wait` must be called in a loop checking the predicate (spurious wakeups); prefer `wait_while`.

##### Atomics and memory ordering

| Ordering | Use for | Note |
|---|---|---|
| `Relaxed` | counters, statistics, ID generation — no other data depends on the value | no happens-before |
| `Release` (store) / `Acquire` (load) | publishing data: write data, then `store(true, Release)`; reader `load(Acquire)` then reads data | the canonical "flag + payload" pattern |
| `AcqRel` | read-modify-write that both consumes and publishes (`fetch_add` in reference counts, `compare_exchange` in lock-free structures) | |
| `SeqCst` | when several atomics must be observed in a single total order (Dekker-style flags) | default when in doubt; not a fix for data races on non-atomic data |

```rust
use std::sync::atomic::{AtomicBool, AtomicU64, Ordering};
use std::sync::Arc;
use std::thread;

static REQUESTS: AtomicU64 = AtomicU64::new(0);

fn main() {
    REQUESTS.fetch_add(1, Ordering::Relaxed); // pure counter

    let ready = Arc::new(AtomicBool::new(false));
    let data = Arc::new(AtomicU64::new(0));
    let (r2, d2) = (Arc::clone(&ready), Arc::clone(&data));
    let producer = thread::spawn(move || {
        d2.store(42, Ordering::Relaxed);
        r2.store(true, Ordering::Release); // publishes the store above
    });
    while !ready.load(Ordering::Acquire) {
        std::hint::spin_loop();
    }
    println!("{}", data.load(Ordering::Relaxed)); // guaranteed 42
    producer.join().unwrap();
    println!("requests = {}", REQUESTS.load(Ordering::Relaxed));
}
```

- A `load` followed by a `store` is not atomic; use `fetch_*`, `compare_exchange` (in a loop, with `compare_exchange_weak`), or `fetch_update`/`update` (1.95+).
- **`const` atomics are a bug**: `const COUNTER: AtomicU32 = AtomicU32::new(0);` creates a fresh atomic at every use, so increments are lost. Use `static` (1.93+ warns with `const_item_interior_mutations`).
- Spin loops need `std::hint::spin_loop()` and a fallback to blocking (`thread::park`, `Condvar`) — unbounded spinning burns CPU and can livelock on oversubscribed machines.

##### Channels, one-time init and global state

- `std::sync::mpsc` (multi-producer single-consumer; `sync_channel(n)` is bounded); `crossbeam-channel` for MPMC/`select!`. Unbounded channels are a memory-exhaustion risk under load — prefer bounded ones in servers.
- `OnceLock<T>` (set once, possibly from runtime input) and `LazyLock<T>` (initialized by a closure on first access) replace `lazy_static!`/`once_cell`. `LazyLock::get` (1.94+) peeks without forcing. A panic inside the `LazyLock` initializer poisons it: every later access panics.
- `thread_local!` with `const { … }` initializers avoid lazy-init overhead; TLS destructors may not run for the main thread or at process exit.

#### Async Rust

Futures are lazy state machines: nothing runs until the future is polled by an executor, and **dropping a future cancels it** at its current `.await` point. The standard library defines `Future`, `IntoFuture` (both in the 2024 prelude), `Poll`, `Context`, `Waker`, `pin!` and async closures; the runtime (I/O, timers, scheduling) comes from a crate — almost always **Tokio** (1.x; 1.54.1 is current and declares `rust-version = "1.85"`).

##### Runtime basics (Tokio)

```rust
// needs: tokio
use std::time::Duration;

#[tokio::main] // multi-threaded runtime by default (feature "rt-multi-thread")
async fn main() {
    let handle = tokio::spawn(async {
        tokio::time::sleep(Duration::from_millis(10)).await;
        21 * 2
    });
    // A JoinHandle that is dropped detaches the task (it keeps running); await or abort it.
    let v = handle.await.expect("task panicked"); // JoinError if the task panicked or was aborted
    println!("{v}");

    let mut set = tokio::task::JoinSet::new();
    for i in 0..3u64 {
        set.spawn(async move { i * 10 });
    }
    while let Some(res) = set.join_next().await {
        println!("{}", res.unwrap());
    }
}
```

- `tokio::spawn` requires the future to be `Send + 'static`. Do not satisfy `'static` with `Box::leak`; move owned data (`Arc`, clones) into the task.
- A spawned task's panic does not crash the program; it surfaces as `Err(JoinError)` on `.await`. Ignoring the `JoinHandle` silently loses panics and errors — use `JoinSet` or `TaskTracker` (tokio-util) for structured lifetimes.
- `#[tokio::main(flavor = "current_thread")]` runs everything on one thread: any blocking call stalls *all* tasks.
- `#[tokio::test]` gives each test its own runtime (current-thread by default; `flavor = "multi_thread"` for concurrency tests).

##### Never block the executor

```rust
// needs: tokio
use std::time::{Duration, Instant};

#[tokio::main(flavor = "current_thread")]
async fn main() {
    // BAD: std::thread::sleep / blocking I/O / CPU loops inside async code stall the runtime thread.
    let t = Instant::now();
    let blocker = tokio::spawn(async { std::thread::sleep(Duration::from_millis(100)) });
    let ticker = tokio::spawn(async move { tokio::time::sleep(Duration::from_millis(10)).await; t.elapsed() });
    blocker.await.unwrap();
    println!("10 ms timer fired after {:?}", ticker.await.unwrap()); // ~100 ms

    // GOOD: move blocking work to the blocking pool.
    let t = Instant::now();
    let blocker = tokio::task::spawn_blocking(|| std::thread::sleep(Duration::from_millis(100)));
    let ticker = tokio::spawn(async move { tokio::time::sleep(Duration::from_millis(10)).await; t.elapsed() });
    println!("10 ms timer fired after {:?}", ticker.await.unwrap()); // ~10 ms
    blocker.await.unwrap();
}
```

Blocking calls to flag inside `async fn`: `std::thread::sleep`, `std::fs::*` and `std::net::*` I/O (use `tokio::fs`/`tokio::net` or `spawn_blocking`), `std::sync::mpsc::Receiver::recv`, blocking HTTP clients (`reqwest::blocking`), heavy CPU work (hashing passwords, compression, large JSON) — offload CPU-bound work with `spawn_blocking` or a `rayon` pool. `block_on` / `Runtime::new()` inside an async context panics ("Cannot start a runtime from within a runtime").

##### Locks across `.await`

A `std::sync::MutexGuard` is not `Send`; holding one across `.await` makes the future non-`Send` (`tokio::spawn` rejects it: "future cannot be sent between threads safely … `MutexGuard` … is used across an await") and risks deadlocks even on a current-thread runtime. Clippy `await_holding_lock` (on by default) flags it.

```rust
// needs: tokio
use std::sync::{Arc, Mutex};

async fn persist(_v: u64) {}

#[tokio::main]
async fn main() {
    let counter = Arc::new(Mutex::new(0u64));
    let c = Arc::clone(&counter);
    tokio::spawn(async move {
        let snapshot = {
            let mut g = c.lock().unwrap();
            *g += 1;
            *g
        }; // guard dropped here, before the await
        persist(snapshot).await;
    })
    .await
    .unwrap();
    println!("{}", *counter.lock().unwrap());
}
```

Use `tokio::sync::Mutex` only when the lock must be held across an `.await` (it is slower, and its `lock()` is not cancellation-safe with respect to queue position). For plain shared data, a `std::sync::Mutex` with short, non-async critical sections is the recommended default.

##### Cancellation safety

When a future is dropped (`select!` picks another branch, `timeout` expires, the task is aborted, the client disconnects in an HTTP handler), it stops at its current `.await` and runs destructors — work after that point never happens.

```rust
// needs: tokio
use std::time::Duration;
use tokio::sync::mpsc;
use tokio::time::{sleep, timeout};

async fn two_step(log: &mut Vec<&'static str>) {
    log.push("debit");
    sleep(Duration::from_millis(50)).await;
    log.push("credit"); // never reached if the future is dropped at the await above
}

#[tokio::main]
async fn main() {
    let mut log = Vec::new();
    let r = timeout(Duration::from_millis(10), two_step(&mut log)).await;
    println!("timed out: {}, log: {:?}", r.is_err(), log); // timed out: true, log: ["debit"]

    let (tx, mut rx) = mpsc::channel::<u32>(8);
    tokio::spawn(async move {
        sleep(Duration::from_millis(20)).await;
        tx.send(7).await.unwrap();
    });
    loop {
        tokio::select! {
            // `recv` is cancellation-safe: if the tick wins, no message is lost.
            msg = rx.recv() => match msg {
                Some(v) => println!("got {v}"),
                None => break,
            },
            _ = sleep(Duration::from_millis(5)) => println!("tick"),
        }
    }
}
```

Tokio documents which methods are safe to use as a `select!` branch in a loop:[^29] **safe** — `mpsc::Receiver::recv`, `broadcast::Receiver::recv`, `watch::Receiver::changed`, `TcpListener::accept`, `AsyncReadExt::read`/`read_buf`, `AsyncWriteExt::write`/`write_buf`, `StreamExt::next`; **not safe** (may lose data) — `read_exact`, `read_to_end`, `read_to_string`, `write_all`; **not safe** (lose their queue position) — `tokio::sync::Mutex::lock`, `RwLock::read`/`write`, `Semaphore::acquire`, `Notify::notified`. For unsafe operations, create the future once outside the loop and `select!` on `&mut fut` (pinned), or move the work into a spawned task.

Other review points:

- Multi-step state changes (debit/credit, write file then rename, send then record) must be idempotent or protected so that cancellation between steps leaves a consistent state.
- `tokio::select!` polls branches in random order; use `biased;` when priority matters (e.g. a shutdown branch first).
- Graceful shutdown: propagate a cancellation signal (`tokio_util::sync::CancellationToken`, a `watch` channel) instead of aborting tasks mid-operation.
- Timeouts belong around every network call (`tokio::time::timeout`, client-level timeouts).

##### `Send` futures and `async fn` in traits

- `async fn` in traits (and `-> impl Future` in traits) are stable since long before 1.85, but callers **cannot require the returned future to be `Send`**, and such traits are **not dyn-compatible** (`error[E0038]`). rustc warns on public traits ("use of `async fn` in public traits is discouraged as auto trait bounds cannot be specified").
- For a public trait used with multi-threaded runtimes, declare the `Send` bound in the signature (implementations can still use `async fn`):

```rust
use std::future::Future;

pub trait Store {
    fn get(&self, key: u32) -> impl Future<Output = Option<String>> + Send;
}

struct Memory;

impl Store for Memory {
    async fn get(&self, key: u32) -> Option<String> {
        (key == 1).then(|| "one".to_owned())
    }
}

fn assert_send<T: Send>(_: T) {}

fn main() {
    assert_send(Memory.get(1)); // compiles: the trait promises Send
}
```

- For trait objects, return `Pin<Box<dyn Future<Output = T> + Send + '_>>` (what the `async-trait` crate generates) or use a dyn-compatible wrapper; return-type notation (`T::method(..): Send`) is **not stable**.
- `Rc`, `RefCell` borrows and `MutexGuard`s alive across an `.await` make the future `!Send`; the compiler error names the offending variable.
- Async closures (1.85) and `AsyncFn*` bounds replace `F: Fn() -> Fut, Fut: Future` pairs and allow the returned future to borrow captured state.

##### Pinning

- `Pin<&mut T>` guarantees a `!Unpin` value (most compiler-generated futures) will not move. Use `std::pin::pin!(fut)` for stack pinning and `Box::pin(fut)` for heap pinning; avoid `Pin::new_unchecked` unless writing a combinator with documented projections (prefer `pin-project-lite`).
- Since 1.97, `pin!(x)` with `x: &mut T` yields `Pin<&mut &mut T>`; code that relied on the old coercion to `Pin<&mut T>` must call `Pin::new` / re-borrow explicitly.

#### Traits, Generics & Closures

- **Static vs. dynamic dispatch**: generics (`fn f<T: Trait>(x: T)` or `impl Trait` arguments) monomorphize (fast, larger binaries, longer compile times); `&dyn Trait`/`Box<dyn Trait>` uses a vtable (one copy, indirect calls). Prefer generics on hot paths, trait objects for heterogeneous collections and plugin boundaries.
- **Dyn compatibility** (formerly "object safety"): a trait is usable as `dyn Trait` only if its methods have a receiver, no generic type parameters and do not return `Self`, and it has no `async fn`/RPITIT. Add `where Self: Sized` to methods that should be excluded from the vtable.
- **Trait upcasting** (1.86): `&dyn Sub` → `&dyn Super` works directly; remove hand-written `as_super` methods when MSRV ≥ 1.86.
- **Coherence/orphan rule**: implement a foreign trait for a foreign type through a newtype (`struct Meters(f64)`). Blanket impls (`impl<T: Display> MyTrait for T`) in a library constrain future impls — adding one later is a breaking change.
- **`impl Trait` in argument position** cannot be turbofished; use a named generic when callers may need to specify the type.
- **Associated types vs. generic parameters**: use an associated type when each implementor has exactly one natural choice (`Iterator::Item`), a generic parameter when a type may implement the trait several times (`From<T>`).
- **Sealed traits** (a public trait with a private supertrait) prevent downstream implementations, so methods can be added without a breaking change.
- **`#[derive]` bounds**: `#[derive(Clone)]` on `struct W<T>(Arc<T>)` requires `T: Clone` even though `Arc<T>: Clone` always — implement `Clone` manually when that bound is wrong.
- **`PartialEq`/`Eq`/`Hash`/`Ord` consistency**: `a == b` ⇒ `hash(a) == hash(b)`; `Ord` must agree with `PartialOrd` and `PartialEq`. Since 1.98, deriving both `PartialOrd` and `Ord` makes `partial_cmp` call `cmp`, so a manual `Ord` that disagrees with a derived `PartialOrd` (or vice versa) changes behaviour. `BTreeMap`/`sort` with an inconsistent `Ord` may panic or misbehave (1.96 notes `BTreeMap::append`).
- **Closures**: `Fn` (shared borrow), `FnMut` (mutable borrow), `FnOnce` (consumes captures). `move` closures capture by value — needed for threads and `'static` tasks. Edition 2021+ closures capture disjoint *fields*, not whole variables; dropping order of captured fields follows that.
- **Const generics**: `struct Buf<const N: usize>`; only integers, `bool` and `char` are allowed as const parameter types on stable. `[T; N]` APIs (`array::from_fn`, `each_ref`, `map`) avoid `Vec` allocation; `_` can stand for an inferred const argument since 1.89.
- **Generic bounds placement**: put bounds on `impl` blocks and functions, not on struct definitions (struct bounds must then be repeated everywhere).

```rust
use std::fmt::Display;

// Static dispatch: one copy per T, inlined.
fn print_all<T: Display>(items: &[T]) -> String {
    items.iter().map(|i| i.to_string()).collect::<Vec<_>>().join(",")
}

// Dynamic dispatch: heterogeneous values.
fn print_mixed(items: &[&dyn Display]) -> String {
    items.iter().map(|i| i.to_string()).collect::<Vec<_>>().join(",")
}

fn main() {
    println!("{}", print_all(&[1, 2, 3]));
    println!("{}", print_mixed(&[&1, &"two", &3.0]));
}
```

#### Iterators & Collections

##### Iterator idioms

- Prefer iterator chains to index loops: no bounds checks, no off-by-one errors. `for i in 0..v.len() { v[i] … }` is a Clippy `needless_range_loop` finding.
- Iterators are lazy: `v.iter().map(f);` without a consumer does nothing (`unused_must_use` warns).
- Avoid `collect()` into a `Vec` only to iterate again (Clippy `needless_collect`, nursery); avoid `.iter().count()` on slices (`len()`).
- `collect::<Result<Vec<_>, _>>()` stops at the first error; `Option` likewise.
- `into_iter()` on a `Vec` consumes it; `iter()` borrows; `iter_mut()` borrows mutably. On arrays, `into_iter()` yields values (2021+); on `Box<[T]>` it yields values only in edition 2024.
- `zip` silently stops at the shorter iterator — check lengths if they must match.
- `chunks_exact` + `remainder`, `as_chunks::<N>()` (1.88+), `array_windows::<N>()` (1.94+), `windows(n)`.
- `Iterator::max_by(|a, b| a.partial_cmp(b).unwrap())` panics on NaN — use `f64::total_cmp`.
- `extract_if` (1.87/1.88/1.91) removes and yields in one pass; `retain`/`retain_mut` when the removed elements are not needed.
- `Peekable::next_if`/`next_if_eq` and `next_if_map` (1.94) for small parsers.

```rust
fn main() {
    let lines = ["10", "20", "x", "30"];
    let parsed: Result<Vec<u32>, _> = lines.iter().map(|s| s.parse::<u32>()).collect();
    println!("{parsed:?}"); // Err(ParseIntError { kind: InvalidDigit })

    let valid: Vec<u32> = lines.iter().filter_map(|s| s.parse().ok()).collect();
    println!("{valid:?}"); // [10, 20, 30]

    let mut readings = vec![2.5, f64::NAN, 1.0];
    readings.sort_by(f64::total_cmp); // NaN sorts last, no panic
    println!("{readings:?}");
}
```

##### Collections

| Need | Use | Notes |
|---|---|---|
| sequence | `Vec<T>` | `with_capacity` when the size is known; `VecDeque` for queue/deque |
| key → value | `HashMap<K, V>` | iteration order is **randomized** (differs between runs and between map instances) — never rely on it in output, tests or hashing; use `BTreeMap` or sort |
| sorted map / range queries | `BTreeMap<K, V>` | deterministic order |
| set | `HashSet` / `BTreeSet` | same ordering caveats |
| priority queue | `BinaryHeap<T>` | max-heap; wrap in `Reverse` for min-heap |
| small inline vectors | `smallvec`/`arrayvec` crates | measure first |

- The default `HashMap` hasher (SipHash-1-3, randomly keyed) resists HashDoS; replacing it with `FxHash`/`ahash` is fine for trusted keys, a DoS risk for attacker-controlled keys.
- Mutating a key so that its `Hash`/`Ord` changes while it is in a map is a logic error (the entry becomes unreachable).
- `Vec::remove(0)` is O(n) — use `VecDeque::pop_front` or `swap_remove` when order does not matter.
- `retain_back(n)` on `VecDeque` (1.99) truncates from the front keeping the last `n`; it is not a predicate filter.
- `HashMap::get_disjoint_mut` (1.86) for multiple mutable values; it panics on duplicate keys.
- `Vec::push_mut`/`insert_mut` (1.95) return a reference to the new element, replacing `push` + `last_mut().unwrap()`.

#### Strings, UTF-8, Paths & OS Strings

- `String`/`&str` are always valid UTF-8; `len()` is in **bytes**. Slicing `&s[a..b]` panics if `a`/`b` are not char boundaries — common with user names, emoji, non-ASCII input.

```rust
fn main() {
    let s = "héllo";
    println!("{} bytes, {} chars", s.len(), s.chars().count()); // 6 bytes, 5 chars
    println!("{:?}", s.get(0..2));                                // None: index 2 is inside 'é'
    println!("{:?}", std::panic::catch_unwind(|| &s[0..2]).is_err()); // true — slicing panics
    let cut = s.floor_char_boundary(2);                            // 1.91+
    println!("{}", &s[..cut]);                                     // "h"
}
```

- "Characters" as users perceive them are grapheme clusters (`unicode-segmentation` crate), not `char`s.
- `to_lowercase`/`to_uppercase` are Unicode-aware and may change length (`"ß".to_uppercase() == "SS"`); use `eq_ignore_ascii_case`/`to_ascii_lowercase` for protocol tokens, headers and identifiers.
- `String::from_utf8(bytes)?` validates; `from_utf8_lossy` replaces invalid sequences with U+FFFD (data loss — never for binary data or round-tripping); `from_utf8_lossy_owned` (1.99) reuses the `Vec`.
- Build strings with `format!`, `write!` into a `String` (`use std::fmt::Write`), or `push_str`; `s = s + &t` in a loop reallocates. `to_string()` on `&str` is fine; `format!("{}", s)` for a plain copy is wasteful.
- Formatting: inline arguments `format!("{name}: {count}")`; `{:?}` for debug output in logs and errors involving user input (quotes and escapes control characters — log-injection resistant), `{}` for user-facing text. Since 1.98, more characters are escaped by `Debug` for `str`/`char`.
- **Paths are not strings.** `Path`/`PathBuf`/`OsStr` may contain non-UTF-8 data on Unix and unpaired surrogates on Windows. `path.to_str().unwrap()` panics on such names; use `display()` for output (`OsStr::display` since 1.87) and keep `PathBuf` end-to-end. `Path::join` with an **absolute** component replaces the base: `Path::new("/srv/data").join("/etc/passwd") == "/etc/passwd"` — a classic path-traversal bug with user-controlled names (also `..` components). Validate with `components()` and reject `ParentDir`/`RootDir`/`Prefix`, or canonicalize and check `starts_with` the base directory.
- `Path::file_prefix` (1.91) vs. `file_stem`: `"archive.tar.gz"` → `"archive"` vs `"archive.tar"`.

#### Macros

- Prefer functions and generics; use `macro_rules!` for syntax that functions cannot express (variadic patterns, compile-time string building), and procedural macros (derive/attribute/function-like) for code generation.
- Macro hygiene covers local variables but **not** items or paths: inside exported macros refer to items as `$crate::path::Item` and std items as `::core::…`/`::std::…` so the macro works regardless of the caller's imports.
- [2024] `$x:expr` matches `const { … }` and `_`; `$x:expr_2021` keeps the 2021 behaviour. A missing fragment specifier (`$name` without `:kind`) is a hard error.
- A `macro_rules!` macro used in expression position must not expand to a trailing `;` (deny-by-default `semicolon_in_expressions_from_macros` since 1.91; from 1.99 also reported for macros from other crates via `semicolon_in_expressions_from_non_local_macros`).
- `cfg_select!` (1.95) replaces `cfg-if` for new code with a sufficient MSRV; `#[cfg(true)]`/`#[cfg(false)]` (1.88) replace `#[cfg(any())]`/`#[cfg(all())]` tricks.
- `cfg` names must be known: Cargo passes `--check-cfg`, so `#[cfg(feature = "typo")]` or a custom `#[cfg(my_flag)]` warns (`unexpected_cfgs`). Declare custom cfgs in `[lints.rust] unexpected_cfgs = { level = "warn", check-cfg = ['cfg(my_flag)'] }` or via `cargo::rustc-check-cfg` in `build.rs`.
- Procedural macros run arbitrary code at build time with the developer's/CI's privileges — part of the supply-chain review (see Security).

#### API Design & SemVer Hazards

Follow the Rust API Guidelines; for published crates, every public item is a compatibility promise. Run `cargo-semver-checks` in CI before releases.[^30]

##### Naming and conversions

- `as_*` (cheap borrow → borrow), `to_*` (expensive or owned conversion), `into_*` (consumes `self`); getters without `get_` prefix (`fn len(&self)`); `iter`/`iter_mut`/`into_iter`; constructors `new`, `with_capacity`, `from_*`.
- Implement standard traits eagerly where meaningful: `Debug` (always, for public types), `Clone`, `Default`, `PartialEq`/`Eq`/`Hash`, `Display` for user-facing types, `From`/`TryFrom` for conversions (never implement `Into` directly), `AsRef`, `Send`/`Sync` by construction, `serde` behind a feature.
- Accept generic inputs (`impl AsRef<Path>`, `impl Into<String>`) at API edges; return concrete types.
- Use newtypes and enums instead of `bool`/`String`/integer parameters (`fn connect(addr: SocketAddr, tls: Tls)` rather than `fn connect(addr: &str, tls: bool)`), and the builder pattern for many optional parameters.
- `#[must_use]` on functions whose result must not be ignored (builders, `Result`-like types, pure functions; Clippy `must_use_candidate` in pedantic).

##### Changes that break downstream code

| Change | Breaking? | Mitigation |
|---|---|---|
| Adding a public field to a struct with all-public fields | yes (struct literals and exhaustive patterns break) | `#[non_exhaustive]` from the start, or private fields + constructor |
| Adding an enum variant | yes | `#[non_exhaustive]` on public enums that may grow (errors, kinds) |
| Adding a trait method without default | yes | default method, or a sealed trait |
| Adding a blanket impl | yes (conflicting impls downstream) | avoid in minor releases |
| Making a type lose `Send`/`Sync`/`Unpin` (e.g. adding an `Rc` field) | yes — auto traits leak | add static assertions in tests (`fn assert_send<T: Send>() {}`) |
| Changing an `impl Trait` return's hidden type so it loses an auto trait | yes (auto traits leak through `impl Trait`) | same assertions |
| [2024] Dropping a `use<..>` bound or editing RPIT capture | yes (callers may rely on the opaque type not borrowing) | treat captures as API |
| Raising `rust-version` (MSRV) | policy-dependent; many crates treat it as minor | document the policy; resolver 3 shields MSRV-respecting users |
| Re-exporting a dependency type and bumping that dependency's major version | yes | do not expose dependency types, or re-export the dependency |
| Removing or renaming a Cargo feature | yes | keep the old name as an alias feature |
| Making a function `const` | no; removing `const` is | — |
| Changing `#[repr]` or field order of a `repr(Rust)` type | not a type-level break, but breaks anyone transmuting it (which is already UB-prone) | never rely on `repr(Rust)` layout |

- `#[non_exhaustive]` structs cannot be constructed with literals outside the crate; enums require a wildcard arm. Inside the defining crate it has no effect.
- `#[doc(hidden)] pub` items are still public API in the semver sense if downstream code can name them; reviewers should ask whether they are covered by the stability promise.
- `pub(crate)` by default; widen visibility deliberately. `dead_code_pub_in_binary` (allow-by-default, 1.97) can flag `pub` items unused in binary crates.

#### Performance

Measure before optimizing (`cargo bench` with `criterion`/`divan`, `perf`/`samply`/`cargo flamegraph`, `cargo build --timings` for compile time). Review for the obvious costs:

- **Allocation in loops**: `format!`/`to_string()`/`clone()` per iteration, `collect()` into temporary `Vec`s, `Vec::new()` without `with_capacity` when the size is known, `String` concatenation via `+` in loops. Reuse buffers (`clear()` keeps capacity).
- **Cloning large values** to satisfy the borrow checker; `Arc<str>`/`Arc<[T]>` for shared immutable data instead of cloning `String`/`Vec`.
- **Dynamic dispatch and boxing** on hot paths; `Box<dyn Fn>` where a generic `F: Fn` works.
- **Bounds checks** in tight index loops (iterators or `chunks_exact`/`as_chunks` let LLVM elide them); do not reach for `get_unchecked` without a benchmark and a `SAFETY` proof.
- **Hashing**: SipHash is DoS-resistant but slower; `HashMap::with_capacity`; avoid hashing large keys repeatedly (entry API).
- **I/O**: wrap `File`/`TcpStream` in `BufReader`/`BufWriter` (and call `flush()` — a `BufWriter` dropped with an error silently loses data; `into_inner()` reports it); lock `stdout()` once for many writes (`let mut out = std::io::stdout().lock();`).
- **Async**: `spawn_blocking` for CPU work; avoid `Arc<Mutex<…>>` contention hot spots; bounded channels.
- **Logging**: `tracing`/`log` macros skip formatting when the level is disabled; `debug!("{}", expensive())` still calls `expensive()` only if enabled — but `let s = expensive(); debug!("{s}")` always does.

Build configuration (in `Cargo.toml`):

```toml
[profile.release]
lto = "thin"            # or "fat": smaller/faster binaries, slower builds
codegen-units = 1       # better optimization, slower builds
panic = "abort"         # smaller binaries; no unwinding, catch_unwind stops working
debug = "line-tables-only"  # usable backtraces/profiles at small size cost
# overflow-checks = true  # consider for services handling money/sizes

[profile.dev.package."*"]
opt-level = 2           # optimize dependencies in debug builds
```

- `panic = "abort"` changes semantics: `Drop` does not run on panic, `catch_unwind` cannot recover, tests using `#[should_panic]` need the unwind runtime (Cargo ignores `panic` for the test profile).
- rustc's `-O` means `-C opt-level=3` since 1.86 (matching Cargo's release profile).
- `std::hint::black_box` keeps benchmarks from being optimized away; `#[inline]` matters only across crates for non-generic functions; `#[cold]`/`hint::cold_path()` (1.95) for error paths.
- Since 1.90, `x86_64-unknown-linux-gnu` links with `rust-lld` (faster links).

#### Testing

##### Unit, integration, doc tests

```rust
/// Splits `total` into `parts` shares that differ by at most one.
///
/// ```
/// # fn split(total: u64, parts: u64) -> Vec<u64> {
/// #     let (base, rem) = (total / parts, total % parts);
/// #     (0..parts).map(|i| base + u64::from(i < rem)).collect()
/// # }
/// assert_eq!(split(10, 3), vec![4, 3, 3]);
/// ```
///
/// # Panics
/// Panics if `parts` is zero.
pub fn split(total: u64, parts: u64) -> Vec<u64> {
    assert!(parts > 0, "parts must be non-zero");
    let (base, rem) = (total / parts, total % parts);
    (0..parts).map(|i| base + u64::from(i < rem)).collect()
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn splits_evenly() {
        assert_eq!(split(10, 3), vec![4, 3, 3]);
    }

    #[test]
    #[should_panic(expected = "parts must be non-zero")]
    fn zero_parts_panics() {
        split(1, 0);
    }

    #[test]
    fn returns_result() -> Result<(), std::num::ParseIntError> {
        assert_eq!("42".parse::<u64>()?, 42);
        Ok(())
    }
}
```

- Unit tests live in `#[cfg(test)] mod tests` beside the code and may test private items; integration tests in `tests/*.rs` see only the public API (each file is a separate crate — share helpers via `tests/common/mod.rs`).
- `#[should_panic]` without `expected = "…"` passes for *any* panic, including an unrelated `unwrap` — require `expected`.
- Tests run **in parallel threads** of one process: tests touching global state (env vars — `unsafe` in 2024 —, current directory, files with fixed names, ports) race. Use `tempfile`, port 0, explicit configuration, or `serial_test`. `cargo test -- --test-threads=1` is the blunt fallback.
- Doctests compile against the public API; in 2024 they are merged into one binary (see above). Use `no_run` for examples that need network/files, `compile_fail` for negative examples (fragile: any error passes — add the error code, e.g. ```` ```compile_fail,E0502 ````), `ignore` sparingly (not tested at all).
- Assertions: `assert_eq!(left, right)` gives a diff of `Debug` output; `assert_matches!` (1.96+) for enum shapes; `assert!(matches!(x, Pat))` on older MSRV.
- Determinism: no reliance on `HashMap` order, timing (`sleep` in tests), or wall-clock time. Inject clocks; for Tokio use `#[tokio::test(start_paused = true)]` with `tokio::time::advance` (feature `test-util`).
- `cargo test` does not run `#[ignore]`d tests (`-- --ignored`); `cargo test --all-targets` excludes doctests and `cargo test --doc` runs only doctests — CI needs both.

- Run `unsafe` code under Miri (nightly) and with sanitizers (`-Zsanitizer=address`, nightly) in CI.
- `loom` for exhaustive checking of lock-free/atomic code.
- `cargo-mutants` finds untested code paths; coverage via `cargo llvm-cov`.

serde.workspace = true
tokio = { workspace = true, features = ["rt-multi-thread", "macros"] }  # features add to the workspace's

[lints]
workspace = true
```

- Members inherit fields only when they say `x.workspace = true`; `[workspace.lints]` applies only to members with `[lints] workspace = true`.
- `features = [...]` on an inherited dependency is additive to the workspace's list; `default-features = false` on a member overrides the workspace only on 1.99+ in edition 2024 (an error on 1.85–1.98).
- `priority = -1` on lint groups lets individual lints override the group.

##### Features must be additive

Cargo unifies features: if any crate in the build enables `foo/feature-x`, every user of `foo` gets it. Therefore:

- Enabling a feature must never remove functionality or change behaviour incompatibly. Mutually exclusive features (`backend-a` vs `backend-b`, `std` vs `no_std` as two features) break when two dependents choose differently; prefer one additive `std` feature (enabled by default) and runtime/type-level selection.
- `#[cfg(feature = "x")]` names are checked (`unexpected_cfgs`); typos in feature names warn.
- Use `dep:name` in `[features]` to avoid creating implicit features for optional dependencies, and `name?/feature` to enable a feature of an optional dependency only if it is otherwise enabled.
- Test feature combinations in CI (`cargo hack --feature-powerset check`), including `--no-default-features`.
- Resolver 2/3 does not unify features between build-dependencies/proc-macros and normal dependencies, nor dev-dependency features into normal builds.

##### MSRV and resolution

- `rust-version` is enforced: `cargo +1.85.0 check` on a package with `rust-version = "1.88"` fails with "rustc 1.85.0 is not supported by the following package: … requires rustc 1.88" (`--ignore-rust-version` bypasses it).
- Resolver 3 (default for 2024 packages, explicit in virtual workspaces) picks dependency versions compatible with `rust-version`; it falls back to incompatible versions when nothing compatible exists, so CI must still **build with the MSRV toolchain** to prove it.
- `cargo update --precise` / `cargo update -p foo` for targeted updates; check what changed in `Cargo.lock` in review.

##### Lockfiles and reproducibility

- Commit `Cargo.lock` for applications **and** libraries — `cargo new` tracks it by default for both (only `/target` is in the generated `.gitignore`). It makes CI and `git bisect` reproducible; it never affects consumers of a library (only `Cargo.toml` does).[^32] Add a CI job that tests with the latest compatible dependencies (`cargo update` then test) to catch breakage early.
- Build in CI with `--locked` (fail if `Cargo.lock` would change) and install tools with `cargo install --locked`.
- Since 1.97, `resolver.lockfile-path` lets read-only source trees keep the lockfile elsewhere; since 1.99, incremental compilation is off by default when `CI` is set.
- `[patch.crates-io]` and git dependencies in published crates are not allowed / not honoured downstream; flag them in library manifests.

##### Build scripts

- `build.rs` runs at build time with the user's privileges. It should emit `cargo::rerun-if-changed=…` (otherwise any file change in the package reruns it), never write outside `OUT_DIR`, never download from the network (breaks offline/vendored builds and is a supply-chain risk).
- Use `cargo::rustc-check-cfg=cfg(name)` for custom cfgs set by the script.
- Prefer the `cc`/`pkg-config`/`bindgen` crates over hand-rolled compiler invocation.

#### Tooling: rustfmt, Clippy, Lints

- **rustfmt**: run `cargo fmt --check` in CI; commit a `rustfmt.toml` with `style_edition = "2024"` so editors that call `rustfmt` directly agree with `cargo fmt`. Do not hand-align code.
- **Clippy**: `cargo clippy --all-targets --all-features -- -D warnings` (or `[lints]` levels + `build.warnings = "deny"` in `.cargo/config.toml` on 1.97+). Clippy respects `rust-version`, so MSRV-sensitive suggestions only appear when allowed.
- Useful lints beyond the defaults (verified names on clippy 0.1.99):

| Lint | Group | Catches |
|---|---|---|
| `await_holding_lock`, `await_holding_refcell_ref` | suspicious (default) | guards held across `.await` |
| `missing_safety_doc` | style (default) | `unsafe fn` without `# Safety` |
| `undocumented_unsafe_blocks` | restriction | `unsafe {}` without `// SAFETY:` |
| `unwrap_used`, `expect_used`, `panic`, `indexing_slicing` | restriction | panics in libraries |
| `missing_panics_doc`, `missing_errors_doc` | pedantic | undocumented failure modes |
| `cast_possible_truncation`, `cast_sign_loss`, `cast_possible_wrap` | pedantic | lossy `as` casts |
| `manual_let_else`, `uninlined_format_args`, `manual_midpoint` | pedantic | modernization |
| `manual_is_multiple_of` (MSRV ≥ 1.87), `collapsible_if` → let chain (MSRV ≥ 1.88) | style (default) | modernization gated on MSRV |
| `large_enum_variant`, `needless_range_loop`, `ptr_arg` | default | size/perf/idiom |
| `needless_collect`, `redundant_clone`, `future_not_send` | nursery | performance, non-`Send` futures |
| `arithmetic_side_effects` | restriction | unchecked arithmetic in critical code |
| `dbg_macro`, `print_stdout`, `todo` | restriction | debug leftovers |

- rustc lints worth setting in `[lints.rust]`: `unsafe_code` (forbid where possible), `unsafe_op_in_unsafe_fn = "deny"`, `missing_docs` for libraries, `unreachable_pub`, `unused_qualifications`, `rust_2024_compatibility` (when preparing a migration).
- `#[expect(lint)]` (instead of `#[allow]`) warns when the suppressed lint no longer fires — use it with a `reason = "…"` for every suppression in reviewed code.
- `cargo doc --no-deps` with `RUSTDOCFLAGS="-D warnings"` catches broken intra-doc links; `#![warn(rustdoc::broken_intra_doc_links)]` is on by default.

#### Security

- **Dependencies**: run `cargo audit` (RustSec advisory DB) or `cargo deny check advisories bans licenses sources` in CI; review new dependencies (maintenance, `unsafe` usage, transitive tree size, typosquatting); pin tools with `cargo install --locked`; consider `cargo vet` for audited supply chains. Build scripts and proc macros execute arbitrary code at build time.
- **Toolchain**: stay on the latest point release. Cargo fixed CVE-2026-33055/33056 (tar extraction, 1.94.1), CVE-2026-5222 (sparse-registry credential leak across registries on the same domain, 1.96.0) and CVE-2026-5223 (symlinks in crate tarballs from third-party registries, 1.96.0); 1.96.1 patched libssh2 CVEs.[^31]
- **`unsafe` and FFI** are the main memory-safety risk; see the sections above. Count and review `unsafe` in dependencies of security-sensitive code.
- **Integer overflow** in release builds wraps — check arithmetic on untrusted sizes, offsets, and quantities (`checked_*`).
- **Panics are DoS vectors** in servers: `unwrap()` on request data, indexing with untrusted indices, slicing strings at untrusted byte offsets, unbounded recursion (stack overflow aborts the process), unbounded allocation from length prefixes (`Vec::with_capacity(len_from_wire)`).
- **Deserialization**: limit input size before parsing; `serde_json` limits recursion depth to 128 by default (do not disable without a stack-size plan); `#[serde(deny_unknown_fields)]` where strictness matters; never deserialize untrusted data into types whose invariants are only checked in constructors (use `#[serde(try_from = "…")]`).
- **Processes**: `std::process::Command::new(prog).arg(user_input)` does not invoke a shell; `Command::new("sh").arg("-c").arg(format!(…user_input…))` is command injection. On Windows, arguments to `.bat`/`.cmd` files are interpreted by `cmd.exe` — std escapes them since the 2024 BatBadBut fix, but avoid passing untrusted input to batch files.
- **Paths**: user-controlled path components → `..`/absolute-path traversal (`Path::join` with an absolute path replaces the base). Canonicalize and verify the prefix, and beware of symlink races (TOCTOU) between the check and the use.
- **Secrets**: do not `#[derive(Debug)]` on types holding secrets (or implement a redacting `Debug`); use `zeroize`/`secrecy` for key material; compare MACs/tokens with constant-time comparison (`subtle::ConstantTimeEq`), not `==`.
- **Randomness**: `rand::rng()`/`OsRng`/`getrandom` for security-relevant values; never seed from time.
- **Crypto/TLS**: use maintained crates (`rustls`, `ring`, `aws-lc-rs`, RustCrypto) — never hand-rolled crypto. Verify certificates (no `danger_accept_invalid_certs(true)` outside tests).
- **SQL**: parameterized queries (`sqlx::query!("… WHERE id = $1", id)`, `bind`), never `format!` into SQL.
- **Regex**: the `regex` crate guarantees linear-time matching (no catastrophic backtracking) but large patterns from users still cost memory — set `size_limit`; `fancy-regex` (backtracking) is ReDoS-prone.
- **Environment**: [2024] `env::set_var` is `unsafe`; mutating the environment in multi-threaded programs is UB on many platforms.
- **Logging**: log user input with `{:?}` to escape control characters; never log secrets, tokens, or full request bodies.

#### Observability

- Use `tracing` (spans + structured events) for services; `log` facade for simple libraries. Libraries emit events but never install a global subscriber/logger — that is the binary's job.
- Structured fields over interpolated strings: `tracing::info!(user_id = %id, elapsed_ms = ms, "request done")`.
- `#[tracing::instrument(skip(password, body), err)]` creates a span per call; `skip` large or secret arguments explicitly (all arguments are recorded with `Debug` by default).
- In async code, attach spans to futures (`.instrument(span)`), not with `span.enter()` held across `.await` (the guard would be attributed to whatever task runs next on that thread).
- Panics: install a panic hook that logs through the logging pipeline (`std::panic::set_hook`, `PanicHookInfo::payload_as_str()` since 1.91); since 1.91 the default message includes the thread ID. Set `RUST_BACKTRACE=1` (or capture with `std::backtrace::Backtrace::capture()`); with `panic = "abort"`, unwind tables are still emitted since 1.92 so backtraces keep working.
- Name threads (`thread::Builder::name`) and Tokio worker threads (`runtime::Builder::thread_name`).
- Since 1.97 symbols use v0 mangling: update profilers/demanglers (`rustfilt`, recent `perf`, `addr2line`) if stack traces show raw `_R…` names.
- Metrics: `metrics`/`prometheus`/OpenTelemetry crates; count with `Relaxed` atomics.

#### Migrating 2021 → 2024

`cargo new` creates edition-2024 packages on current toolchains. To migrate an existing crate:[^2]

1. Update to a recent toolchain and make sure the crate builds warning-free on 2021.
2. Run `cargo fix --edition` (add `--all-targets --all-features` or run per feature set; it only fixes code that is compiled). It applies the `rust_2024_compatibility` lints **but does not change `edition` in `Cargo.toml`**.
3. Set `edition = "2024"` (and `rust-version` ≥ 1.85; set `resolver = "3"` explicitly in a virtual workspace root), then build, test and run `cargo fmt` (style edition 2024 reorders imports).
4. **Review the mechanical rewrites** — they preserve 2021 semantics, not intent:

| Rewrite by `cargo fix --edition` | What to check |
|---|---|
| `extern "C" {}` → `unsafe extern "C" {}` | signatures still correct? mark provably safe items `safe fn` |
| `#[no_mangle]` → `#[unsafe(no_mangle)]` | add `// SAFETY:` (symbol uniqueness) |
| `unsafe fn` bodies wrapped in `unsafe { … }` | split into minimal blocks with `SAFETY` comments |
| `-> impl Trait` → `-> impl Trait + use<…>` | is the narrow capture still wanted? |
| `if let` (significant drop) → `match` | keeps the 2021 lock/borrow lifetime — often the original bug; consider reverting to `if let` |
| `$e:expr` → `$e:expr_2021` | usually revert to `expr` unless arms depend on the old matching |
| `gen` → `r#gen` | consider renaming the identifier |
| `std::env::set_var(…)` → `unsafe { … }` + "Audit that the environment access only happens in single-threaded code" | perform the audit; prefer removing the call |
| `boxed_slice.into_iter()` → `.iter()` | intended? by-value iteration may now be simpler |
| patterns → fully explicit (`&[ref x, mut y]`) | simplify if the binding modes are not needed |
| Cargo: `dev_dependencies` → `dev-dependencies`, removal of inherited `default-features = false` | re-add `default-features = false` on 1.99+ if wanted |

Changes with **no automatic migration** (search for them manually): `&`/`&mut` to `static mut` (now deny), never-type fallback (`f()?` with an unconstrained `T`, closures that only panic), tail-expression drop order (`tail_expr_drop_order` only warns), doctests that depend on `Location`/`type_name` (mark `standalone_crate`), `include_str!` paths in Markdown pulled into doctests, and macros matching `#"…"#`/`##` tokens.

Verified example (`cargo +stable fix --edition --allow-no-vcs` on a 2021 crate): `extern "C"` gained `unsafe`, `#[no_mangle]` became `#[unsafe(no_mangle)]`, `fn gen` became `fn r#gen`, an `-> impl Iterator<Item = usize>` borrowing nothing gained `+ use<>`, `$e:expr` became `$e:expr_2021`, an `unsafe fn` body got an inner `unsafe {}`, an `if let … else` on a `RwLock` read guard became a `match`, `set_var` was wrapped in `unsafe` with a `FIXME: Audit…` comment, `b.into_iter()` on a `Box<[u8]>` became `b.iter()`, and `let [x, mut y] = &[1u8, 2]` became `let &[ref x, mut y] = &[1u8, 2]`; `Cargo.toml` still said `edition = "2021"`.

#### Production / Review Checklist

##### Edition & toolchain

- [ ] `edition = "2024"` with `rust-version` ≥ 1.85 declared; CI builds with the MSRV toolchain **and** latest stable (1.99.1)
- [ ] No API/syntax newer than `rust-version` (release table); no nightly features or `#![feature]`
- [ ] Virtual workspace root sets `resolver = "3"`
- [ ] `rustfmt.toml` sets `style_edition = "2024"`; `cargo fmt --check` and `cargo clippy --all-targets --all-features -D warnings` in CI
- [ ] Toolchain is the latest point release of its minor (security and miscompilation fixes)

##### Edition-2024 semantics

- [ ] `if let … else` with guards/borrows in the scrutinee: relies on the 2024 drop-before-`else`; `match`/`while let`/then-branch still hold temporaries
- [ ] Tail expressions with significant `Drop` reviewed for the earlier drop point
- [ ] RPIT `-> impl Trait` captures intended; `+ use<..>` where callers must not be borrowed
- [ ] `unsafe extern` blocks: every `safe fn`/`safe static` justified
- [ ] `#[unsafe(no_mangle)]`/`export_name`/`link_section` have `SAFETY` comments
- [ ] No references to `static mut`; atomics/`Mutex`/`OnceLock`/`LazyLock`/`&raw` instead
- [ ] `env::set_var`/`remove_var` only in audited single-threaded code (never in async services or tests)
- [ ] No reliance on `()` never-type fallback; macro `expr` vs `expr_2021` choice deliberate

##### Correctness & errors

- [ ] Libraries return typed errors (`thiserror`, `#[non_exhaustive]`); applications add context (`anyhow`, `{:#}` when logging)
- [ ] No `unwrap`/`expect`/indexing/slicing on untrusted input; `expect` messages state invariants; `# Panics` documented
- [ ] Arithmetic on untrusted values uses `checked_*`/`strict_*`; no lossy `as` casts (use `TryFrom`)
- [ ] String slicing on char boundaries only; paths kept as `Path`/`OsStr`; `Path::join` inputs validated
- [ ] Float sorting/comparison via `total_cmp`; `Ord`/`PartialOrd`/`Eq`/`Hash` consistent
- [ ] `let _ = guard` not used for RAII values that must live

##### Unsafe & FFI

- [ ] Every `unsafe {}` has a `// SAFETY:` proof; every `unsafe fn` a `# Safety` section; `unsafe_op_in_unsafe_fn` clean
- [ ] Invariants encapsulated behind private fields; no safe API can trigger UB
- [ ] No invalid values, aliasing `&mut`, misaligned/dangling references, `transmute` of layouts, integer→pointer transmutes
- [ ] `#[repr(C)]` on FFI types; panics never unwind across `extern "C"`; ownership of FFI memory clear
- [ ] Miri (nightly) and sanitizers run for crates with `unsafe`

##### Concurrency & async

- [ ] No `std::sync::MutexGuard`/`RefCell` borrow held across `.await`; no blocking calls in async code
- [ ] Spawned tasks/threads joined or tracked; `JoinError`s and panics surfaced
- [ ] `select!` branches cancellation-safe; multi-step operations safe under cancellation; timeouts on network calls
- [ ] Public async traits declare `Send` futures where needed
- [ ] Mutex poisoning handled deliberately; lock order consistent; no `const` atomics/mutexes
- [ ] Atomic orderings justified (`Relaxed` only for independent counters)

##### Cargo & supply chain

- [ ] Features additive; `--no-default-features` and feature powerset tested
- [ ] `Cargo.lock` committed; CI uses `--locked`; latest-deps job exists
- [ ] `cargo audit`/`cargo deny` in CI; new dependencies reviewed; build scripts minimal and offline
- [ ] Public API changes checked with `cargo-semver-checks`; public enums/structs that may grow are `#[non_exhaustive]`

##### Testing & observability

- [ ] Unit + integration + doc tests (`cargo test --all-targets` **and** `cargo test --doc`); `#[should_panic(expected = …)]`
- [ ] Tests independent of global state, `HashMap` order and wall-clock timing; property tests for parsers/encoders
- [ ] `tracing` spans/fields; secrets skipped/redacted; panic hook logs; threads and tasks named
